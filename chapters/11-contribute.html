第 11 章 · 第四阶段 成为贡献者

测试、CI 与提交你的第一个 PR

前面十章你已经比大多数使用者更懂这个项目了。 这一章把知识变成贡献：本地跑通全部 CI、挑一个能做的活、 写出会被合入的 PR。

学完这章你应该能

  • 在本地一次性跑通 CI 的全部检查项，不用等 GitHub Actions
  • 写出符合项目规范的测试（表驱动 + 边界用例）
  • 从本教程沿途标记的问题清单里，挑出一个适合自己的切入点
  • 知道 HAMi 的六条「贡献门槛」，尤其是 AI 辅助的披露要求
  • 提交一个格式正确、评审友好的 PR
先读这一条：HAMi 的 AI 辅助披露要求非常严格

CONTRIBUTING.md 里明确规定： 任何形式的 AI 辅助都必须在 PR 描述里披露， 并说明使用程度（只写文档 vs 生成代码）。

还有六条硬性门槛（Contribution Gates），其中最关键的三条：

  • 作者理解门槛：维护者问「这段怎么工作的」，答不上来 → PR 直接关闭。
  • 大型 AI 生成 PR 不接受：小修复之外的改动必须先开 issue，拆成可评审的多个 commit。 commit message 必须自己写。
  • 不允许把 AI 列为 co-author：不要 Co-authored-by / assisted-by 等 trailer， 披露只写在 PR 描述里。

这套教程能帮你达到「理解门槛」，但代码必须你自己写、自己懂。

1. 本地跑通 CI：五分钟自查

GitHub Actions 的 lint job 一共跑 4 项检查 （）。 全部可以在本地跑，别浪费时间等 CI 告诉你少了个 license 头。

2. 怎么写 HAMi 风格的测试

HAMi 的测试清一色是表驱动。照着写，评审会顺畅很多。 

func TestSomething(t *testing.T) {
	tests := []struct {
		name    string                  // 用例名，出问题时靠它定位
		args    struct{ /* 输入 */ }
		want    /* 期望输出 */
		wantErr bool
	}{
		{
			name: "正常路径：显存刚好够",
			// ...
		},
		{
			name: "边界：显存差 1MB",       // 边界用例是评审最看重的
			// ...
		},
		{
			name: "异常：负数输入",
			wantErr: true,
		},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {      // 子测试，可以单独跑
			got, err := DoSomething(tt.args)
			if (err != nil) != tt.wantErr {
				t.Errorf("DoSomething() error = %v, wantErr %v", err, tt.wantErr)
				return
			}
			assert.Equal(t, tt.want, got)         // 项目用 testify
		})
	}
}
测试需要 DevicesMap 时，记得先初始化

第 02 章讲过：device.GetDevices() 默认是空的。 看 的 TestMain 是怎么做的，照抄。
否则你的测试会「什么都没发生就通过了」—— 这种假绿比失败更糟。

# 正则匹配多个

# 看某个包的覆盖率

3.1 自己找活的几个办法

# ① 全项目的 TODO / FIXME（每一条都是作者留下的线索）
grep -rn "TODO\|FIXME\|XXX\|HACK" --include=*.go pkg/ cmd/ | grep -v _test

# ② 被注释掉的代码（往往是「有问题但没想好怎么修」）
grep -rn "^\s*//\s*[a-z].*(" --include=*.go pkg/ | grep -v "^\s*//\s*[A-Z]" | head -20

# ③ 覆盖率低的地方
make test
go tool cover -func=_output/coverage/coverage.out | sort -k3 -n | head -30

# ④ 最近改动频繁的文件（说明还在演进，容易有遗留问题）
git log --since="3 months ago" --name-only --pretty=format: -- 'pkg/**/*.go' \
  | grep -v '_test' | sort | uniq -c | sort -rn | head -15

# ⑤ 只有实现没有测试的函数
for f in $(find pkg -name '*.go' ! -name '*_test.go'); do
  t="${f%.go}_test.go"
  [ -f "$t" ] || echo "无测试文件: $f"
done

4. 提交 PR 的完整流程

  1. Fork + 建分支 
    git remote add upstream https://github.com/Project-HAMi/HAMi.git
git fetch upstream
git checkout -b fix/node-deleted-interface upstream/master

    分支名用 fix/、feat/、docs/、test/ 前缀，跟 commit 前缀对应。

  2. 改代码 + 补测试

    改行为必须带测试。没测试的功能 PR 基本不会被合。 修 bug 的话，最好先写一个能复现 bug 的失败测试，再修。

  3. 本地跑全部检查 
    hack/verify-all.sh
go test ./pkg/... ./cmd/... -short -race -count=1
  4. 写 commit message（自己写，别用 AI 生成） 
    fix(scheduler): validate NUMA refit quota with container positions
feat(nvidia): score MIG placements and add backtracking fallback
test(scheduler): add Go benchmarks for the Filter scoring path
docs(develop): align handshake description with current health check
build(deps): bump github/issue-labeler from 3.4 to 3.5

    格式：<类型>(<范围>): <做了什么>，动词开头，小写，不加句号。
    不要加任何 AI 相关的 trailer（Co-authored-by: Claude 之类）， 这是明文禁止的。

  5. 推送并开 PR 
    git push origin fix/node-deleted-interface
gh pr create --repo Project-HAMi/HAMi --fill   # 或者在网页上开
  6. 写 PR 描述（这是最容易被忽视、也最影响评审速度的一步） 
    ## What this PR does / why we need it

onDelNode 里用类型断言硬编码了 *nvidia.NvidiaGPUDevices 来调用 NodeDeleted。
改成一个可选接口，其他后端将来需要清理每节点状态时不用再改这里。
行为完全不变。

## Which issue(s) this PR fixes

Fixes #xxxx        （没有对应 issue 就写 NONE）

## Special notes for your reviewer

- 纯重构，无行为变更
- 新增 TestOnDelNodeCallsNodeDeleted 验证接口断言仍然命中 NVIDIA 后端
- 已在本地跑过 hack/verify-all.sh 和 go test ./pkg/... -race

## Testing

- [x] 单元测试：go test ./pkg/scheduler/ -run TestOnDelNode -race -count=1
- [ ] 真实 GPU 硬件验证：不适用（仅调度器扩展器范围）

## AI assistance disclosure

I used Claude Code to explore the codebase and locate this pattern.
The change and its test were written by me; I reviewed and understand
every line.
  7. 回应评审

    回复必须自己写，而且要正面回应对方提的具体那一点。 套话式的、AI 生成的回复会导致 PR 被关闭。
    不同意评审意见也没关系，把理由说清楚 —— 但先确认自己真的理解了对方的顾虑。

关于「硬件验证」这条门槛

CONTRIBUTING.md 规定：影响设备分配或容器内隔离的改动， 必须在真实 GPU 上验证过，并在 PR 里写明测了什么、什么型号、什么驱动版本。
但「仅限于调度器扩展器范围」的改动可以只用单元测试或 mock。
如果你没有 GPU，这就框定了你能做的范围： pkg/scheduler/、pkg/device/*/ 的纯逻辑、文档、测试 —— 而这恰好是本教程覆盖最深的部分。

5. 一个完整的示范：从发现到 PR

拿第 07 章那个类型断言的例子，走一遍完整流程：

① 发现问题 
	// Clear per-device health bookkeeping for the deleted node.
	// Devices that track per-node state (e.g. NvidiaGPUDevices) implement
	// NodeDeleted to prune their internal maps; others are a no-op.
	for _, devInstance := range device.GetDevices() {
		if nd, ok := devInstance.(*nvidia.NvidiaGPUDevices); ok {
			nd.NodeDeleted(nodeName)
		}
	}

问题：注释说「其他后端是 no-op」，但代码硬编码了具体类型。 别的后端就算实现了 NodeDeleted 也不会被调用。

② 确认是不是真问题（别急着改） 
# 有没有别的后端也实现了 NodeDeleted？
grep -rn "func.*NodeDeleted" pkg/device/ --include=*.go

# 是不是有意为之？看这行是什么时候、为什么加的
git log -L 308,315:pkg/scheduler/scheduler.go | head -60

# GitHub 上有没有相关讨论
# 搜 issue: "NodeDeleted" / "type assertion"

这一步不能省。很多「看起来不对」的代码其实有原因， 直接提 PR 会显得没做功课。

③ 改动 
// nodeDeletedNotifier is implemented by device backends that keep per-node
// bookkeeping and need to prune it when a node leaves the cluster. Backends
// that keep no per-node state simply do not implement it.
type nodeDeletedNotifier interface {
	NodeDeleted(nodeName string)
}

// ... 在 onDelNode 里：
	for _, devInstance := range device.GetDevices() {
		if nd, ok := devInstance.(nodeDeletedNotifier); ok {
			nd.NodeDeleted(nodeName)
		}
	}

注意：项目里已经有这个模式了（第 05 章的 policyNeutralScorer）。 跟随代码库已有的惯例，比引入新写法更容易被接受。

④ 补测试 
func TestOnDelNodeNotifiesBackends(t *testing.T) {
	// 验证：NVIDIA 后端（真实类型）仍然会被通知到
	// 验证：一个假的实现了 nodeDeletedNotifier 的后端也会被通知到
	// 验证：没实现该接口的后端不会 panic
}

第三条尤其重要 —— 证明改动没有引入新的崩溃路径。

⑤ 自查 + 提交 
hack/verify-all.sh
go test ./pkg/scheduler/ -race -count=1

git add -p
git commit    # 自己写 message：
              # refactor(scheduler): notify device backends of node deletion via interface
git push origin refactor/node-deleted-interface

6. 除了写代码，还能怎么贡献

方式说明门槛
改文档比如第 01 章发现的：docs/develop/protocol.md 仍描述 Reported + 5 分钟，当前实现是 Requesting + 60 秒 + Allocatable低
补测试给某个后端的 Fit 补边界用例；给覆盖率低的函数补测试低
改进错误信息让 event / 日志更能指导用户「该怎么改」低
复现并报告 bug带最小复现步骤的 issue，对维护者价值很高低
翻译 / 本地化项目有 README_cn.md / README_ja.md低
评审别人的 PR你现在有能力看懂调度逻辑了，指出问题就是贡献中
性能优化用 score_bench_test.go 量化，拿数据说话中
新增设备后端第 02 章那个清单；需要对应硬件高

7. 本章自测

你用 AI 帮忙理解代码，但改动是自己写的。PR 里该怎么处理？
A不用提，因为代码是自己写的
B在 commit 里加 Co-authored-by: Claude
C在 PR 描述里披露，说明使用程度；不要加任何 AI 相关的 commit trailer
D在代码注释里标注
CONTRIBUTING.md 说得很明确： 任何形式的 AI 辅助都要披露（包括只用来理解代码）， 而且披露只写在 PR 描述里。
Gate 5「Commit trailer hygiene」明文禁止把 AI 列为 co-author， 或用 assisted-by / co-developed-by 之类的 trailer。
唯一的例外是「单个关键词或短语的 tab 补全」不用披露。
你没有 GPU 硬件。下面哪类 PR 可以只用单元测试就提交？
A改 HAMi-core 的显存 OOM 判断逻辑
B给 pkg/scheduler/score.go 的打分逻辑修一个边界 bug
C改设备插件注入的环境变量
D改 MIG 实例的创建流程
Gate 2 规定：影响设备分配或容器内隔离的改动必须真机验证， 但「scoped to the scheduler extender」的改动可以用 mock 或单元测试。
A（容器内隔离）、C（设备分配）、D（MIG 实例创建）都需要真实硬件。
这也意味着：没有 GPU 的贡献者，主战场是调度器扩展器、纯逻辑、测试和文档。正好是本教程第 01-07 章覆盖的部分。
CI 的 lint job 会跑哪几项？
Averify-license、make tidy、golangci-lint v2.13.1、verify-import-aliases
B只有 golangci-lint
C只有单元测试
De2e 测试
见 .github/workflows/ci.yaml 的 lint job。 golangci-lint 的版本 v2.13.1 同时钉在 CI 配置和 hack/verify-staticcheck.sh 里 —— 本地一定要用同一个版本， 不同版本的检查项不一样，本地过了 CI 可能挂。
单元测试和 e2e 是另外的 job。hack/verify-all.sh 一次跑完 lint 相关的几项。

8. 小结

  • 提交前本地跑 hack/verify-all.sh + go test ./pkg/... -short -race -count=1，别等 CI。
  • 三个高频坑：License 头、K8s import 别名、import 三段分组。
  • 测试写表驱动 + 子测试 + 边界用例；需要 DevicesMap 记得在 TestMain 初始化。
  • HAMi 的六条贡献门槛里，最关键的是作者理解门槛、AI 披露、不加 AI trailer。
  • 没有 GPU 也能贡献：调度器扩展器逻辑、测试、文档、错误信息。
  • 找活的四个渠道：TODO/FIXME、被注释掉的代码、覆盖率洼地、good first issue。
  • 改之前先 git log -L 查历史 —— 确认这不是有意为之。
