Devices 接口与核心数据结构

全项目只有一个核心抽象：13 个方法的 Devices 接口。 13 家硬件厂商各自实现它，调度器只跟接口打交道。 看懂这一章，你就知道「加一个新硬件」到底要写哪些代码。

学完这章你应该能

  • 把 13 个接口方法按「生命周期阶段」正确归类，说出各自在什么时候被调用
  • 分清 DeviceInfo / DeviceUsage / ContainerDeviceRequest / ContainerDevice 四个结构体的职责
  • 解释 PodDevices 三层嵌套 map 的每一层是什么
  • 说出「新增一个厂商设备后端」需要改哪几个文件
  • 读懂最简单的 kunlun 后端全部 245 行代码

1. 一个接口撑起 13 家厂商

这个抽象换来了什么

调度器全程只跟 Devices 接口打交道，不知道背后是哪家的硬件。 NVIDIA 的显存切分、寒武纪的 MLU、昇腾的 NPU，内部实现天差地别， 对调度器却是同一组方法。
结果是：加一个新厂商，调度器一行代码都不用改。本章最后会具体列出要改哪几个文件。

接口定义就在这里，一共 13 个方法：

2. 四个核心结构体：同一张卡的四副面孔

初学者最容易晕的地方：同一张 GPU，在代码里有四种不同的表示。 搞清楚它们的区别，代码就通了一大半。

四者的分工
  • DeviceInfo = 房产证。静态属性：多大面积、几室几厅、在哪一层。不会变。
  • DeviceUsage = 入住登记表。动态状态：现在住了几个人、占了多少面积、还剩多少。调度时不断被修改。
  • ContainerDeviceRequest = 租房需求单。「我要 1 间、至少 3000 平、朝南」。
  • ContainerDevice = 签好的租约。「你住 A 栋 302，租 3000 平，用 30% 公共设施」。
四副面孔转换器互动

调整下面的参数，看同一张 GPU 在四个结构体里分别长什么样、数据从哪来、到哪去。

它从哪来？。从上一章讲的 Node 注解解析出来。 注意 NVIDIA 用的是 JSON 版本（因为要带 MIG placement）： 

func (dev *NvidiaGPUDevices) GetNodeDevices(n corev1.Node) ([]*device.DeviceInfo, error) {
	devEncoded, ok := n.Annotations[RegisterAnnos]              // hami.io/node-nvidia-register
	if !ok {

	}
	nodedevices, err := device.UnMarshalNodeDevices(devEncoded) // JSON 反序列化
	if err != nil {

		klog.InfoS("no nvidia gpu device found", "node", n.Name, ...)

	for idx := range nodedevices {

2.2 DeviceUsage：动态用量（入住登记表）

这是调度过程中被反复修改的那个结构体，也是整个打分算法的操作对象： 

type DeviceUsage struct {
	ID                  string
	Index               uint
	Used                int32     // ← 已经被几个容器用了（跟 Count 比）
	Count               int32     // ← 最多能被几个容器用
	Usedmem             int32     // ← 已用显存（跟 Totalmem 比）
	Totalmem            int32
	Totalcore           int32
	Usedcores           int32     // ← 已用算力（跟 Totalcore 比）
	Mode                string
	MigProfiles         []MigProfile
	MigAllocationsInUse []MigAllocation
	MigTemplate         []Geometry // Deprecated: unused by dynamic NVIDIA MIG.
	MigUsage            MigInUse   // Deprecated: unused by dynamic NVIDIA MIG.
	Numa                int
	Type                string
	Health              bool
	PodInfos            []*PodInfo
	CustomInfo          map[string]any
}
三条「余量」公式，记住它们

整个 Fit() 的十几个判断，本质上就是围绕这三条： 

剩余份数 = Count     - Used          // 份数用完 → CardTimeSlicingExhausted
剩余显存 = Totalmem  - Usedmem       // 显存不够 → CardInsufficientMemory
剩余算力 = Totalcore - Usedcores     // 算力不够 → CardInsufficientCore
踩坑：DeviceUsage 是会被就地修改的

打分时，调度器会假装把 Pod 放上去（调 AddResourceUsage 扣减余量）， 再看放完之后节点得多少分。所以每个节点打分前都必须先 DeepCopy()， 否则一个节点的试算会污染另一个节点的数据。
这就是为什么 DeviceUsage 有一个 50 行的手写 DeepCopy()。
第 05 章会看到这个 DeepCopy 在打分主循环里的确切位置。

2.3 ContainerDeviceRequest：需求（租房需求单）

type ContainerDeviceRequest struct {
	Nums             int32   // 要几张卡
	Type             string  // 要哪家的（"NVIDIA" / "MLU" / ...）
	Memreq           int32   // 要多少显存（MB，绝对值）
	MemPercentagereq int32   // 要多少显存（百分比）—— 101 是「未设置」哨兵值
	Coresreq         int32   // 要多少算力（0-100）
}
MemPercentagereq = 101 是什么鬼

Go 的 int32 零值是 0，但「显存要 0%」和「没设置显存百分比」是两回事。 于是代码用 101（一个不可能的百分比）当「未设置」的哨兵值。 在 Fit() 里你会看到 if k.MemPercentagereq != 101 && k.Memreq == 0 这种判断，就是在区分这两种情况。
这是典型的「用魔数当 Optional」，不够优雅但很常见 —— 读代码时看到 101 就知道是它。

它是从容器的 resources.limits 翻译过来的：

resources:
  limits:
    nvidia.com/gpu: 2          # → Nums = 2
    nvidia.com/gpumem: 3000    # → Memreq = 3000, MemPercentagereq = 101
    nvidia.com/gpucores: 30    # → Coresreq = 30

翻译逻辑在 GenerateResourceRequests() 里， 每家厂商的资源名不同，所以这是接口方法。NVIDIA 的实现有 88 行， 主要在处理各种边界情况（超范围、负数、百分比和绝对值同时给了怎么办）： 

func (dev *NvidiaGPUDevices) GenerateResourceRequests(ctr *corev1.Container) device.ContainerDeviceRequest {
	resourceName := corev1.ResourceName(dev.config.ResourceCountName)          // nvidia.com/gpu
	resourceMem := corev1.ResourceName(dev.config.ResourceMemoryName)          // nvidia.com/gpumem
	resourceMemPercentage := corev1.ResourceName(dev.config.ResourceMemoryPercentageName)
	resourceCores := corev1.ResourceName(dev.config.ResourceCoreName)          // nvidia.com/gpucores
	v, ok := ctr.Resources.Limits[resourceName]
	if !ok {
		v, ok = ctr.Resources.Requests[resourceName]      // limits 没有就看 requests
	}
	if ok {
		if n, ok := v.AsInt64(); ok {
			if n <= 0 || n > math.MaxInt32 {              // 卡数必须是正整数
				klog.ErrorS(nil, "nvidia device count request is out of range", ...)
				return device.ContainerDeviceRequest{}     // 返回零值 = 「这个容器不要 GPU」
			}
			memnum := 0
			// ... 解析 gpumem，注意 MemoryFactor 缩放 ...
			mempnum := int32(101)                          // ← 哨兵：未设置
			// ... 解析 gpumem-percentage ...

			if mempnum == 101 && memnum == 0 {             // 两个都没写 → 用默认值
				if dev.config.DefaultMemory != 0 {
					memnum = int(dev.config.DefaultMemory)
				} else {
					mempnum = 100                          // 默认整卡显存
				}
			}
			corenum := dev.config.DefaultCores
			// ... 解析 gpucores ...
			return device.ContainerDeviceRequest{
				Nums:             int32(n),
				Type:             NvidiaGPUDevice,
				Memreq:           int32(memnum),
				MemPercentagereq: mempnum,
				Coresreq:         corenum,
			}
		}
	}
	return device.ContainerDeviceRequest{}                 // 零值 = 不要 GPU
}

2.4 ContainerDevice：分配结果（签好的租约）

type ContainerDevice struct {
	// TODO current Idx cannot use, because EncodeContainerDevices method not encode this filed.
	Idx       int         // ← 注意这个 TODO：Idx 没被编码进注解，所以设备插件收不到
	UUID      string
	Type      string
	Usedmem   int32
	Usedcores int32
	// Slots is the number of concurrent tasks this collapsed entry represents on the device.
	// Usage reconstruction adds it to DeviceUsage.Used; 0 (raw, uncollapsed entries) counts as 1.

注意那个 TODO

Idx 字段有个明确的 TODO：它没有被编码进注解 （上一章看到编码只写了 UUID、Type、Usedmem、Usedcores 四个字段）。 所以设备插件那边拿不到 Idx，只能靠 UUID 去反查。
这种带 TODO 的地方是找贡献切入口的好去处 —— 但改它要动注解格式，属于破坏性变更， 需要先在社区开 issue 讨论兼容方案。

3. 三层嵌套：从一张卡到一个 Pod

四个结构体之上，还有三层容器类型。它们只是 type X []Y 的别名，但层次必须搞清：

type ContainerDevices []ContainerDevice              // ① 一个容器用的所有卡
type ContainerDeviceRequests map[string]ContainerDeviceRequest

// type ContainerAllDevices map[string]ContainerDevices.
type PodSingleDevice []ContainerDevices             // ② 一个 Pod 的所有容器（同一种硬件）
type PodDeviceRequests []ContainerDeviceRequests
type PodDevices map[string]PodSingleDevice          // ③ 一个 Pod 的所有硬件类型
三层结构可视化互动

一个同时用了 NVIDIA GPU 和寒武纪 MLU 的 Pod，它的 PodDevices 长这样。点击展开每一层。

用一句话记住：

PodDevices["NVIDIA"]          → PodSingleDevice   // 这个 Pod 用的所有 NVIDIA 卡
PodDevices["NVIDIA"][0]       → ContainerDevices  // 第 0 个容器用的 NVIDIA 卡
PodDevices["NVIDIA"][0][1]    → ContainerDevice   // 第 0 个容器的第 1 张卡
索引 [0] 是「第几个容器」，包含 InitContainer

PodSingleDevice 的下标不是「第几张卡」，是容器序号。 而且顺序是：先所有 InitContainer，再所有普通 Container。 看 Resourcereqs() 就明白了： 

func Resourcereqs(pod *corev1.Pod) (counts PodDeviceRequests) {
	// Total containers = init containers + regular containers
	totalContainers := len(pod.Spec.InitContainers) + len(pod.Spec.Containers)
	counts = make(PodDeviceRequests, totalContainers)
	...
	cnt := int32(0)

	// Process init containers first (indices 0 to len(InitContainers)-1)
	for i := range pod.Spec.InitContainers {
		devices := GetDevices()
		counts[i] = make(ContainerDeviceRequests)
		...
		for idx, val := range devices {                                  // 遍历每家厂商
			request := val.GenerateResourceRequests(&pod.Spec.InitContainers[i])
			if request.Nums > 0 {
				cnt += request.Nums
				counts[i][idx] = request                                 // counts[容器序号][厂商]
			}
		}
	}

	// Process regular containers (indices len(InitContainers) to totalContainers-1)
	initContainerOffset := len(pod.Spec.InitContainers)
	for i := range pod.Spec.Containers {
		devices := GetDevices()
		counts[initContainerOffset+i] = make(ContainerDeviceRequests)
		...
		for idx, val := range devices {
			request := val.GenerateResourceRequests(&pod.Spec.Containers[i])
			if request.Nums > 0 {
				cnt += request.Nums
				counts[initContainerOffset+i][idx] = request             // 加偏移量
			}
		}
	}
	...
	return counts
}

5. 实战：读懂最简单的后端（kunlun，245 行）

NVIDIA 后端 1140 行太复杂，先拿百度昆仑（Kunlun XPU）练手 —— 它是所有后端里最简单的，因为它不支持切分，只能整卡分配。

整个 Fit() 的核心判断只有一行：

func FitXPU(device *device.DeviceUsage, request device.ContainerDeviceRequest) bool {
	return device.Used == 0 && device.Health          // 只要没被用过 + 健康，就能放
}

对比一下 NVIDIA 的 Fit()（第 05 章详讲）：

kunlunnvidia
能不能切分不能，整卡能，按显存 + 算力两个维度
判断条件数2 个14 个（健康、cordon、型号、NUMA、UUID、份数、互斥、算力范围、配额、显存、算力、独占、算力耗尽、自定义规则）
拓扑感知有（graghSelect）有（NVLink pair score）

kunlun 的 Fit() 全文（有删减）—— 建议对着源码通读一遍：

func (kl *KunlunDevices) Fit(devices []*device.DeviceUsage, request device.ContainerDeviceRequest, pod *corev1.Pod, nodeInfo *device.NodeInfo, allocated *device.PodDevices) (bool, map[string]device.ContainerDevices, string) {
	klog.InfoS("Allocating device for container request", "pod", klog.KObj(pod), "card request", request)
	tmpDevs := make(map[string]device.ContainerDevices)
	reason := make(map[string]int)

	// graghSelect decides topology from the position of a device in the slice,
	// so the uuid constraint has to be applied through fitFn rather than by
	// filtering the slice first.
	uuidMismatches := make(map[string]bool)
	fitFn := func(d *device.DeviceUsage, r device.ContainerDeviceRequest) bool {
		if !device.CheckUUID(pod.GetAnnotations(), d.ID, UseUUIDAnno, NoUseUUIDAnno, kl.CommonWord()) ||
			!device.CheckUUID(pod.GetAnnotations(), d.ID, KunlunUseUUID, KunlunNoUseUUID, kl.CommonWord()) {
			uuidMismatches[d.ID] = true
			klog.V(5).InfoS(common.CardUUIDMismatch, "pod", klog.KObj(pod), "device", d.ID)
			return false
		}
		return FitXPU(d, r)                                  // ← 唯一的资源判断
	}

	alloc := graghSelect(devices, request, fitFn)            // 拓扑感知的选卡
	if len(alloc) == 0 {
		uuidMismatch := len(uuidMismatches)
		if uuidMismatch > 0 {
			reason[common.CardUUIDMismatch] += uuidMismatch
		} else {
			reason[common.NumaNotFit]++
			klog.V(5).InfoS(common.NumaNotFit, "pod", klog.KObj(pod), ...)
		}
		return false, tmpDevs, common.GenReason(reason, len(devices))   // 失败要给原因
	}

	for _, dev := range alloc {
		for _, val := range devices {
			if val.Index == uint(dev) {
				tmpDevs[request.Type] = append(tmpDevs[request.Type], device.ContainerDevice{
					Idx:       int(val.Index),
					UUID:      val.ID,
					Type:      request.Type,
					Usedmem:   val.Totalmem,               // ← 整卡：用满
					Usedcores: val.Totalcore,              // ← 整卡：用满
				})
				break
			}
		}
	}
	return true, tmpDevs, ""
}

注意最后那段：整卡分配时 Usedmem = Totalmem、Usedcores = Totalcore， 也就是「你拿走整张卡」。而 NVIDIA 会按请求填部分值 —— 这就是「能不能共享」在代码上的全部区别。

6. 新增一个硬件后端要改什么

这是社区里很常见的需求，也是一个很好的贡献方向。清单如下：

  1. 新建 pkg/device/<厂商>/device.go 定义 XxxDevices 结构体，实现全部 13 个接口方法。 抄 pkg/device/kunlun/ 起步最快。
  2. 定义常量：资源名和注解 key XxxResourceCount = "vendor.com/xpu"、 RegisterAnnos = "hami.io/node-xxx-register" 等。
  3. 在 InitXxxDevice() 里登记注解 key 往 device.InRequestDevices / SupportDevices / util.HandshakeAnnos 三张表里各写一条。
  4. 注册到 在 deviceInitializers 数组里加一项。
  5. 加配置结构体 在 Config 里加 XxxConfig 字段，同时改 charts/hami/ 里的 values 模板。
  6. 写测试 + 加 example 参考 pkg/device/kunlun/device_test.go（747 行）， 并在 examples/<厂商>/ 放一个示例 YAML。

8. 本章自测

PodDevices["NVIDIA"][2][0] 指的是什么？
A第 2 张 NVIDIA 卡的第 0 个分片
B第 2 个容器（含 InitContainer 计数）使用的第 0 张 NVIDIA 卡
C第 2 个 NUMA 节点上的第 0 张卡
D第 2 个 Pod 的第 0 张卡
三层是：[厂商] → [容器序号] → [该容器的第几张卡]。 而且容器序号是先 InitContainer 后普通 Container连续编号的 （见 Resourcereqs，devices.go:656）。 如果 Pod 有 1 个 InitContainer，那么 [2] 对应的是第 2 个普通容器（下标 1）。
MemPercentagereq 的值是 101 时意味着什么？
A请求 101% 显存，超卖模式
B参数非法，会被拒绝
C哨兵值，表示「用户没设置显存百分比」
D表示该容器不需要 GPU
因为 int32 零值是 0，而「0%」是合法输入， 无法用 0 表示「未设置」。所以代码用 101 这个不可能的百分比当哨兵。 在 Fit() 里的判断 if k.MemPercentagereq != 101 && k.Memreq == 0 意思是「用户给了百分比但没给绝对值，那就按百分比算」。
「该容器不需要 GPU」是靠返回整个零值结构体（Nums == 0）表示的，不是靠 101。
为什么 DeviceUsage 需要一个 50 行的手写 DeepCopy()？
A打分时要在副本上「假装放置 Pod」试算，不能污染其他节点的真实数据
B为了序列化成注解
CGo 的赋值不能复制结构体
D为了通过 race detector
打分流程是：拷贝一份节点用量 → 在副本上调 AddResourceUsage 扣减余量 → 看扣完之后节点得多少分。多个节点是并发打分的（calcScoreWithOptions 里起了 goroutine）， 如果共用同一份数据就会互相污染。
手写而不用泛型/反射，是因为里面有 MigProfiles、PodInfos、CustomInfo 等 切片和 map 字段，浅拷贝会共享底层数组。
你要给一款新的国产 AI 芯片写 HAMi 支持。下面哪一步不需要做？
A实现 Devices 接口的全部 13 个方法
B在 InitDevicesWithConfig() 的 deviceInitializers 里注册
C往 InRequestDevices / SupportDevices 注册注解 key
D修改 pkg/scheduler/score.go 的打分逻辑来支持新硬件
这正是接口抽象的价值：调度器的打分主流程对硬件完全无感知。 score.go 只调 devPlugin.Fit() 和 devPlugin.ScoreNode()， 具体怎么筛卡、怎么打分由各后端自己决定。 加新硬件只需要 A、B、C 三步（外加配置结构体、Helm chart、测试和示例 YAML）。

9. 小结

  • Devices 接口 13 个方法 = 「国标插座」，13 家厂商各自实现，调度器只认接口。
  • 按生命周期分六组：启动注册 → 节点巡检 → 准入 → 调度打分 → 写决策 → 绑定。
  • 同一张卡四副面孔：DeviceInfo（房产证，静态）、DeviceUsage（登记表，动态、会被改）、 ContainerDeviceRequest（需求单）、ContainerDevice（租约）。
  • 三层嵌套：PodDevices[厂商][容器序号][第几张卡]，容器序号先 Init 后普通。
  • DevicesMap 全局注册表在 InitDevicesWithConfig() 一次性填满； 写测试记得先初始化，否则它是空的。
  • 加新硬件 = 实现接口 + 注册，不用改调度器一行代码。
