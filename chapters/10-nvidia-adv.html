2. MIG：一个「区间占位」问题

电影院的连座

一张 A100 的显存被划成 8 个 slice（可以想成一排 8 个座位）。
每种 MIG profile 占用连续的若干个座位：1g.5gb 占 1 个， 2g.10gb 占 2 个，3g.20gb 占 4 个（注意不是 3 个！）， 7g.40gb 占满 8 个。

而且不是随便哪几个连座都行。NVIDIA 规定了每种 profile 允许的起始位置 （Placements）。这就是一个典型的受约束的区间装箱问题。

2.1 「半区」概念：为什么要给 placement 打分

// migRegions splits the card into two halves. The midpoint rounds up because
// the table ends where the furthest allowed placement ends: an A100 allowlist
// without 3g or 7g reaches slot 6 only, yet the card is still eight slices
// wide with its halves at 4. If any placement other than the full-card one
// straddles the midpoint, the whole card is a single region and scoring
// degrades to first-fit rather than misplacing on an unknown table.
func migRegions(profiles []device.MigProfile, sliceCount int) []migRegion {
	whole := []migRegion{{start: 0, end: uint32(sliceCount)}}
	if sliceCount < 2 {
		return whole
	}
	mid := uint32((sliceCount + 1) / 2)
	for _, profile := range profiles {
		for _, p := range profile.Placements {
			if p.Size == 0 || p.Size >= uint32(sliceCount) {
				continue
			}
			if p.Start < mid && p.Start+p.Size > mid {
				return whole                      // 有 placement 跨中线 → 放弃分区，退化为 first-fit
			}
		}
	}
	return []migRegion{{start: 0, end: mid}, {start: mid, end: uint32(sliceCount)}}
}
分半区的意义：保留大块空间

如果不管三七二十一 first-fit，两个 1g 请求会落在 slot 0 和 slot 1， 剩下 slot 2-7 看起来还有 6 个空位，但 4g（占 4 个） 只能放在 slot 0 或 slot 4。而 slot 4-7 恰好还是空的，能放。
但如果两个 1g 落在 slot 0 和 slot 4，两个半区都被污染了， 4g 就再也放不下。
打分的目标就是「尽量把小块挤在同一半区，保留另一半完整」。 

func (l migLayout) score(occupied []device.MigPlacement, candidate device.MigPlacement) migPlacementScore {
	after := make([]device.MigPlacement, 0, len(occupied)+1)
	after = append(after, occupied...)
	after = append(after, candidate)
	score := migPlacementScore{start: candidate.Start}
	for i, region := range l.regions {
		if region.free(after) {
			score.emptyRegions++              // ① 放完之后还有几个半区是完全空的 —— 越多越好
		}
		if len(l.regions) < 2 || !region.contains(candidate) {
			continue
		}
		if (candidate.Size == region.size()) != (i == l.reserved) {
			score.zoneMismatch = 1            // ② 大块该去「保留区」，小块该去另一区
		}
		if i == 0 {
			score.edgeDistance = region.end - (candidate.Start + candidate.Size)
		} else {
			score.edgeDistance = candidate.Start - region.start
		}                                     // ③ 越靠半区边缘越好（往两边挤，中间留连续空间）
	}
	return score
}

2.2 贪心不够，需要回溯

// place assigns every requested profile without overlap. result[i] belongs to
// requested[i]. Requests are placed pickiest first, best-scored placement
// first; when that greedy path succeeds the result is exactly the greedy
// result. When it fails although fits allowed the request, the same ranked
// candidates are searched by backtracking, so the greedy choice filling the
// wrong half first does not by itself reject the request. Every level checks
// fits for the requests still unplaced, so a run of identical requests that
// can no longer fit is rejected once rather than in every order. The search
// tries at most migSearchBudget candidates in total and rejects the request
// once the budget is spent; on the supported placement tables the exhaustive
// search never comes near it.
func (l migLayout) place(occupied []device.MigPlacement, requested []device.MigProfile) ([]device.MigPlacement, bool) {
这段注释交代了四个设计决策
  • 「pickiest first」：先放选择最少的请求（大块 placement 少）， 这是约束满足问题的标准启发式（最受约束变量优先）。
  • 「greedy path succeeds → 结果就是贪心结果」： 保证常见情况下行为可预测，不会因为加了回溯就变得难以理解。
  • 「every level checks fits」：剪枝。 每一层先用 fits() 快速判断剩下的还能不能放下， 不能就整个分支砍掉，而不是一个个排列试。
  • 「migSearchBudget = 4096」：给搜索加了硬预算。 宁可拒绝一个理论上可行的请求，也不能让调度器卡死。 后面还加了一句「实际的 placement 表根本用不到这个上限」—— 说明作者做过量化评估。
回到第 05 章那个诡异的 i++
		if dev.Mode == "mig" {
			i++                    // 配合 for i--，效果是「原地不动，重新检查同一张卡」
		}
	}

现在能解释了：一张 MIG 卡上可以切出多个实例， 一个容器申请 2 张「卡」时，这 2 张可能都在同一张物理卡上 （比如两个 2g.10gb 实例）。
所以 Fit 遍历到 MIG 卡时不能只看一次就走 —— 要停在原地反复检查， 直到这张卡再也放不下为止。

2.3 MIG 的分配为什么在 AddResourceUsage 里

func (dev *NvidiaGPUDevices) AddResourceUsage(pod *corev1.Pod, n *device.DeviceUsage, ctr *device.ContainerDevice) error {
	if n.Mode == MigMode {
		occupied := occupiedMigPlacements(n.MigAllocationsInUse)
		profile, placement, ok := plannedMigAllocation(n.MigProfiles, occupied, ctr)
		if !ok {
			profile, placement, ok = selectMigCandidate(n.MigProfiles, occupied, ctr.Usedmem)
		}
		if !ok {
			return errors.New("MIG profile and placement allocation failed")
		}
		ctr.Usedmem = profile.MemoryMB          // 覆盖用户请求值！
		ctr.Usedcores = profile.Core            // 
		if ctr.CustomInfo == nil {
			ctr.CustomInfo = make(map[string]any)
		}
		ctr.CustomInfo[MigProfileCustomInfo] = profile.Name
		ctr.CustomInfo[MigPlacementCustomInfo] = placement
		n.MigAllocationsInUse = append(n.MigAllocationsInUse, device.MigAllocation{Profile: profile.Name, Placement: placement})
	}
	n.Used++
	n.Usedcores += ctr.Usedcores
	n.Usedmem += ctr.Usedmem
	return nil
}
MIG 模式下，用户的请求值会被向上取整到 profile 规格

用户申请 gpumem: 6000，但 A100 的 MIG profile 只有 5GB / 10GB / 20GB / 40GB 几档。HAMi 会选 2g.10gb， 然后把 ctr.Usedmem 改成 10240。
所以 Pod 注解里最终记的是 10240 而不是 6000。用户实际拿到的比申请的多，但配额也按 10240 扣。
这个「静默向上取整」如果不知道，排查配额问题时会很困惑。

3. NVLink 拓扑感知

链路类型决定分数

多卡训练时，GPU 之间要频繁交换梯度。它们之间的「路」有多宽，直接决定训练速度。

连接方式分数相当于
P2PLinkCrossCPU10在不同楼层，走楼梯
P2PLinkSameCPU20同楼层不同房间
P2PLinkHostBridge30同房间隔着走廊
P2PLinkMultiSwitch40相邻工位，中间隔两个人
P2PLinkSingleSwitch50相邻工位，隔一个人
P2PLinkSameBoard60面对面坐
SingleNVLINKLink100专线电话（NVLink 起步就碾压 PCIe）
TwoNVLINKLinks200两条专线
…每多一条 +100…H100/B200 最多 18 条 = 1800 分
func calculateGPUPairScore(gpu0 *Device, gpu1 *Device) (int, bool) {
	if gpu0 == nil || gpu1 == nil {
		return 0, false
	}
	if gpu0 == gpu1 {
		return 0, false
	}

	if len(gpu0.Links[gpu1.Index]) != len(gpu1.Links[gpu0.Index]) {
		klog.Warningf("asymmetric P2P link data for GPU pair (index=%d uuid=%s) <-> (index=%d uuid=%s): "+
			"%d link(s) from GPU %d to GPU %d, %d link(s) from GPU %d to GPU %d; "+
			"scoring pair as 0 (possible NVLink hardware or driver issue)",
			gpu0.Index, gpu0.UUID, gpu1.Index, gpu1.UUID,
			len(gpu0.Links[gpu1.Index]), gpu0.Index, gpu1.Index,
			len(gpu1.Links[gpu0.Index]), gpu1.Index, gpu0.Index)
		return 0, true                        // 双向链路数不一致 → 判 0 分并告警
	}

	score := 0

	for _, link := range gpu0.Links[gpu1.Index] {
		switch link.Type {
		case P2PLinkCrossCPU:
			score += 10
		case P2PLinkSameCPU:
			score += 20
		case P2PLinkHostBridge:
			score += 30
		case P2PLinkMultiSwitch:
			score += 40
		case P2PLinkSingleSwitch:
			score += 50
		case P2PLinkSameBoard:
			score += 60
		case SingleNVLINKLink:
			score += 100
		...
		}
	}
	...
}
「链路数不对称」的检测

A→B 报告 4 条 NVLink，B→A 只报告 2 条 —— 这在物理上不可能， 说明硬件故障或驱动状态异常。 代码不是无视它，而是判 0 分 + 打日志 + 上报 Node Warning Event （第 08 章的 AsymmetricGPUP2PLink）。
这里的处理方式是：数据自相矛盾时，宁可保守处理并大声告警， 也不要猜一个值继续跑。

3.1 拓扑策略怎么接进 Fit

回顾第 05 章 Fit() 里的 needTopology：

单卡请求要挑互联最差的那张 —— 这不是笔误

computeWorstSingleCard：只要 1 张卡时， 故意挑跟其他卡连接最差的那张。
为什么？因为这张卡的高速互联对单卡任务毫无价值， 但把它留着，后面来的多卡任务就能用上完整的 NVLink 组。
这是「资源碎片管理」的经典思路： 把「不需要某种特质」的任务，安排到「缺少那种特质」的资源上。
注意 needTopology 时 k.Nums-- 被跳过了 —— 因为要先收集所有可用候选，最后再从中挑最优组合， 而不是遇到一张收一张。

4. NUMA 回填（refit）：设备插件反向调用调度器

问题：kubelet 的 Topology Manager 会推翻调度器的决定

调度器在集群层面选了 GPU-3。 但 kubelet 上还有一个 Topology Manager， 它会为了 CPU/内存/GPU 的 NUMA 亲和性， 把可用设备集合缩小到某几个 NUMA 节点上的设备。

如果 GPU-3 不在那个集合里 —— 调度器选的卡，kubelet 不让用。
老办法是直接失败，Pod 重新调度，但下次调度器可能还是选 GPU-3， 死循环。这就是 issue #2080。

① 调度器选了 GPU-3集群视角
写进 hami.io/vgpu-devices-to-allocate
↓
② kubelet Topology Manager 限制节点视角
为了 NUMA 对齐，可用设备集合只剩 GPU-0、GPU-1 的副本
↓ 设备插件在 GetPreferredAllocation 里发现对不上
③ 设备插件 POST /refit反向调用
「调度器，我这边只能用 [GPU-0, GPU-1]，你重新挑一个」
↓
④ 调度器 RefitNumaAllocation重新决策
在受限集合里重跑一遍完整的 Fit → 改两条注解 → 更新内存账本
// NumaRefitRequest asks the scheduler to re-run its normal fit for one
// container of an already-bound Pod, restricted to the physical devices whose
// replicas kubelet's Topology Manager left in the allocation's available set.
// The device plugin sends it when the scheduler-annotated device has no
// replica in that set. See the NUMA alignment design discussion in issue
// Project-HAMi/HAMi#2080.
type NumaRefitRequest struct {
	// PodUID guards against reusing a stale Pod object of the same name.
	PodUID       string `json:"podUID"`
	PodNamespace string `json:"podNamespace"`
	PodName      string `json:"podName"`
	NodeName     string `json:"nodeName"`
	// ContainerIndex is the Pod container position the refit applies to,
	// counting init containers first, matching PodDevices ordering. Senders
	// must derive it from the Pod's current to-allocate annotation state,
	// not from kubelet request positions, which shift as annotation entries
	// are consumed during allocation.
	ContainerIndex int `json:"containerIndex"`
	// ContainerName optionally names the container at ContainerIndex so the
	// scheduler can cross-check the index against the Pod spec and refuse a
	// mismatched request.
	ContainerName string `json:"containerName,omitempty"`
	// DeviceType is the device vendor type the refit applies to. The scheduler
	// currently accepts "NVIDIA" only; other registered types are rejected
	// until their allocation-specific accounting is supported.
	DeviceType string `json:"deviceType"`
	// AllowedDeviceUUIDs lists the physical device IDs kubelet can still
	// satisfy the allocation from. The refit must select among these only.
	AllowedDeviceUUIDs []string `json:"allowedDeviceUUIDs"`
}
三个防御性设计，都写在注释里了
  1. PodUID 防陈旧对象：同名 Pod 可能是重建的新 Pod， 只靠名字会张冠李戴。
  2. ContainerIndex 必须从注解推导，不能用 kubelet 的请求序号： 因为注解条目在分配过程中会被逐个消费掉（第 08 章的「消费即擦除」）， 两边的序号会漂移。
  3. ContainerName 做交叉校验：多给一个冗余字段， 让调度器能验证 index 对不对。协议里加冗余字段做一致性检查， 比事后排查串台问题便宜得多。
// RefitNumaAllocation moves one container's device reservation onto a device
// from the caller-supplied allowed set, re-running the pod's normal
// policy-chain fit restricted to that set. The device plugin calls it (via
// the /refit route) when kubelet's Topology Manager restricted an allocation
// to replicas of devices the scheduler did not annotate; see issue #2080.
//
// The scheduler stays authoritative: the refit runs the same fit and
// capacity checks as scheduling, patches hami.io/vgpu-devices-to-allocate
// and hami.io/vgpu-devices-allocated together in one merge patch, and only
// then moves the in-memory reservation. Failures are reported in-band and
// leave both annotations and accounting untouched.
「调度器保持权威」是这个设计的核心原则

设备插件不能自己改分配，只能请求调度器改。 因为只有调度器持有完整的集群账本，能做容量校验。
而且改动是原子的：两条注解在同一个 merge patch 里改， 改成功之后才动内存账本；失败则两边都不动。
再加上 allocLock（第 07 章）保证不跟 Filter 交错 —— 这是一套完整的「跨进程事务」设计。 

// patchPodAnnotations patches only the given annotations, with the pod's
// resourceVersion as a precondition so a stale refit cannot overwrite a
// newer update to the same annotations (for example Allocate consuming a
// to-allocate entry). Conflicts fail the refit; there is no retry with
// cached values. Also a test seam.
...
// refitPatchTimeout bounds the annotation patch. It is deliberately no longer
// than the device plugin's own refit budget: a patch that has not landed by
// then cannot be used, and waiting longer would hold the allocation lock
// against every concurrent Filter call.
「冲突就失败，不重试」是刻意的

一般 patch 冲突都会重试。但这里明确不重试。因为冲突意味着「有人（比如 Allocate）已经动过这个注解了」， 基于旧快照重算出来的结果已经不对了，重试只会覆盖掉正确的状态。
同理，超时也刻意设得不超过设备插件那边的预算： 超过了对方也用不上，而 refit 期间是持着 allocLock 的， 拖着不放会阻塞所有并发的 Filter。
这两个决策都体现了「持锁期间要尽快做完或尽快放弃」的原则。

6. 本章自测

用户申请 nvidia.com/gpumem: 6000，调度到一张 MIG 模式的 A100 上。Pod 注解里最终记录的显存是多少？
A6000，跟申请的一样
B0，MIG 模式不记显存
C被向上取整到匹配的 MIG profile 规格，比如 2g.10gb 的 10240
D调度失败，因为 6000 不是合法的 MIG 规格
看 AddResourceUsage（device.go:779）： MIG 模式下选中 profile 后，直接覆写 ctr.Usedmem = profile.MemoryMB 和 ctr.Usedcores = profile.Core。
MIG 是固定规格的硬件切分，没有「6000MB」这种档位，只能向上取整。
副作用：配额也按取整后的值扣。 用户看到「我只申请了 6000，为什么扣了 10240 配额」时，答案就在这里。
A100 有 8 个 MIG slice。已经放了两个 1g，分别在 slot 0 和 slot 4。现在申请一个 3g.20gb（占 4 个 slice，允许起始位置 0 和 4）。结果是？
A放在 slot 0-3
B放不下 —— 两个半区都被污染了
C放在 slot 2-5
D先驱逐一个 1g 实例再放
3g 只能从 slot 0 或 slot 4 开始（占 4 个）， 但 slot 0 和 slot 4 各被一个 1g 占了 → 两个候选位置都冲突。
这正是 migRegions 半区打分要避免的情况： 如果两个 1g 都被挤到同一半区（比如 slot 0 和 slot 1）， 另一半 slot 4-7 完整保留，3g 就放得下。
上面的模拟器可以亲手复现这个场景 —— 对比「贪心评分」和「朴素 first-fit」的差别。
topology-aware 策略下，只申请 1 张卡时，HAMi 会挑哪张？
ANVLink 连接最好的那张
B索引最小的那张
C随机一张
D跟其他卡连接最差的那张
看 computeWorstSingleCard 和它上面那行注释： 「select the card with the worst connection to other cards」。
逻辑是：单卡任务用不上 NVLink，把互联好的卡留给后面的多卡任务。 这是资源碎片管理的经典思路 —— 让「不挑食」的任务去吃「不好的」资源。
多卡请求才用 computeBestCombination 挑互联最好的组合。
NUMA refit 的 patch 遇到 resourceVersion 冲突时，为什么不重试？
A冲突说明有人（如 Allocate）已经改过注解，基于旧快照算出的结果已经不对，重试会覆盖正确状态
B重试会导致死锁
CK8s 不支持对注解重试 patch
D为了减少 apiserver 压力
注释写得很清楚： 「a stale refit cannot overwrite a newer update to the same annotations (for example Allocate consuming a to-allocate entry). Conflicts fail the refit; there is no retry with cached values.」
refit 的整个决策是基于「读到注解那一刻」的快照做的。 如果注解变了，那个快照就失效了 —— 重试等于用过时的决策覆盖新状态。
正确做法是整个 refit 失败，让上层重新走一遍。 B 也有一点道理（refit 持着 allocLock），但不是主要原因。

7. 小结

  • MIG 是硬件隔离，hami-core 是用户态限制；前者规格固定、强隔离，后者灵活、可超卖。
  • MIG 分配是受约束的区间装箱：半区打分（保留大块）+ 最受约束优先 + 回溯 + 搜索预算封顶。
  • MIG 会把用户请求向上取整到 profile 规格并覆写 Usedmem，配额也按取整值扣。
  • NVLink pair score：PCIe 类 10-60 分，NVLink 起步 100 分，每多一条 +100。 双向链路数不一致时判 0 分并告警。
  • 拓扑策略下：多卡挑最优组合，单卡故意挑互联最差的那张（留好卡给多卡任务）。
  • NUMA refit 是设备插件反向调用调度器；调度器保持权威，两条注解原子改， 冲突即失败不重试，超时不超过对方预算。
