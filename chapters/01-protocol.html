第 01 章 · 第一阶段 打地基

注解协议：三个进程之间的公告栏

调度器、设备插件、监控三个进程从不直连。它们把所有要说的话， 编码成一行逗号冒号分号拼起来的字符串，塞进 Kubernetes 的注解里。 这一章看懂了，你就掌握了整个项目的骨架。

学完这章你应该能

  • 看到一条 hami.io/node-nvidia-register 注解，逐字段说出它的含义
  • 手写一条「两个容器、每个容器 2 张卡」的 vgpu-devices-to-allocate 注解
  • 解释为什么用 : 和 ; 两级分隔符，以及它带来的隐患
  • 说清楚 handshake 握手机制如何判断一个节点「掉线了」
  • 找到编解码函数的具体位置，并能跑通它们的单元测试

1. 为什么是字符串？

第一次看到 HAMi 用字符串拼接传数据，很多人会想：为什么不用 CRD？为什么不用 JSON？ 理解这个设计选择，比记住格式本身更重要。

明信片，而不是电话

调度器和设备插件跑在不同的机器上，而且都可能随时重启。 如果用「打电话」（gRPC 直连），一方重启另一方就断线，还得处理服务发现、重连、鉴权。

HAMi 选的是「寄明信片」：所有信息都写在 kube-apiserver 这个公告栏上。 谁重启了都不要紧，起来重新看一眼公告栏就知道当前状态。 代价是 —— 明信片背面地方小，所以要把信息压缩成最紧凑的字符串。

方案优点为什么 HAMi 没选
gRPC 直连类型安全、高效需要服务发现、重连、TLS；组件重启就丢状态
自定义 CRD结构化、可校验要装 CRD、要 RBAC、要 controller；对「每 30 秒更新一次」的高频写入太重
注解字符串零额外部署、天然持久化、kubectl 就能看—（选它）

2. 两类注解，两个方向

Node 注解 · 「我这台机器有什么」设备插件写 → 调度器读
hami.io/node-nvidia-register — 设备清单（每 30 秒刷新一次）
hami.io/node-handshake — 心跳握手，判断节点是否掉线
⇅kube-apiserver（公告栏）
Pod 注解 · 「这个 Pod 该用哪几张卡」调度器写 → 设备插件读
hami.io/vgpu-devices-to-allocate — 分配决策（用哪些卡、各多少显存算力）
hami.io/vgpu-node — 选中的节点
hami.io/bind-phase — 绑定阶段状态机

3. Node 注解：设备清单

先说清楚：节点注解有两种编码，别搞混

这是最容易踩的坑。HAMi 里节点设备清单有两套编码， 不同厂商用的不是同一套：

编码函数哪些后端在用
JSON MarshalNodeDevices
UnMarshalNodeDevices		 nvidia、amd、ascend、biren、kunlun（vdevice）、vastai
逗号串 EncodeNodeDevices
DecodeNodeDevices		 hygon（DCU）、iluvatar

所以 hami.io/node-nvidia-register 的值是 JSON，不是逗号串。 逗号串在 NVIDIA 这条路径上只出现在一行 klog.V(5) 调试日志里 （）， 不是注解本身。
剩下几家（cambricon、metax、mthreads、awsneuron、enflame） 用的是各自的私有格式，不走这两套。

3.1 NVIDIA：JSON 格式

在一个装了 HAMi 的 GPU 节点上执行 kubectl describe node，你会看到：

[{"id":"GPU-0","count":5,"devmem":8192,"devcore":100,"type":"NVIDIA-Tesla P4","mode":"hami-core","health":true},
 {"id":"GPU-1","index":1,"count":10,"devmem":32768,"devcore":100,"type":"NVIDIA-Tesla V100-PCIE-32GB","numa":1,"mode":"hami-core","health":true}]
JSON 字段Go 字段含义
idIDGPU 的 UUID，全局唯一标识
indexIndex卡序号（NVML 的 device index）
countCount切分份数：这张卡最多能被几个容器共享
devmemDevmem显存总量（MB）
devcoreDevcore算力总量，恒为 100（代表 100%）
typeType型号，用于 use-gputype 亲和性筛选
numaNumaNUMA 节点号，用于拓扑亲和
modeModehami-core / mig / mps
migProfilesMIGProfilesMIG 规格与允许的 placement（第 10 章）。逗号格式装不下的就是它
healthHealth健康状态
omitempty：零值字段会整个消失

注意上面例子里 GPU-0 没有 index 和 numa， 而 GPU-1 两个都有。因为 DeviceInfo 的每个字段都带了 omitempty（）， 值为 0 / 空串 / false 时 JSON 里根本不会出现这个 key。

实际影响：

  • index:0、numa:0 会消失 —— 反序列化时靠 Go 零值补回来，正好是 0，没问题。
  • health:false 也会消失！反序列化后同样是 false，碰巧也对。
  • 但这意味着你没法从注解里区分「这个字段没上报」和「上报的值是零值」。 排查问题时看到某个 key 不见了，先想到 omitempty，别以为是设备插件漏报了。
你手上的样本如果字段顺序/内容不一样

JSON 的 key 顺序由 Go 结构体字段声明顺序决定， 当前版本是 id, index, count, devmem, devcore, type, numa, mode, migProfiles, …, health。
如果你看到 "numa":0,"health":true,"index":0 这种带零值、顺序也不同的， 那是较早版本的 HAMi（结构体字段顺序或 omitempty 标签变过）。 字段含义是一样的。

3.2 hygon / iluvatar：逗号串格式

这套格式更紧凑，一张卡一段用 : 分隔，段内 7 或 9 个字段用 , 分隔： 

GPU-0,5,8192,100,NVIDIA-Tesla P4,0,true,0,hami-core:GPU-1,10,32768,100,NVIDIA-Tesla V100-PCIE-32GB,1,true,1,hami-core:
└─ID─┘ │ └─mem┘ │  └─────type─────┘ │ └──┘ │ └──mode──┘
      count    core                numa  health index                              ↑ 每段末尾都有 ":"
位置字段示例值含义
[0]IDGPU-0设备 UUID
[1]Count5切分份数
[2]Devmem8192显存总量（MB）
[3]Devcore100算力总量
[4]TypeNVIDIA-Tesla P4型号
[5]Numa0NUMA 节点号
[6]Healthtrue健康状态
[7]Index0卡序号（9 字段格式才有）
[8]Modehami-core工作模式（9 字段格式才有）
7 字段 vs 9 字段：向后兼容的痕迹

解析函数同时接受 7 个和 9 个字段。7 字段是老版本格式， 解析时会默认填 index=0, mode="hami-core"。 这是典型的滚动升级兼容设计：新调度器要能读懂老设备插件写的注解。 字段数是 8 或 10 会直接报错。

为什么 NVIDIA 从逗号串换成了 JSON

看 MigProfile 的结构：它带一个 Placements []MigPlacement 数组，每个元素是 {Start, Size}。 这种嵌套结构没法塞进「逗号分隔的扁平字段」。
动态 MIG 是 NVIDIA 后端才有的能力，所以只有它必须换 JSON； hygon / iluvatar 没有这个需求，就留在了老格式上。
代价是注解体积大了几倍 —— 这也是为什么 MarshalNodeDevices 刻意排除了 CustomInfo （各厂商能往里塞任意数据，不该膨胀注解）。

3.4 对应源码

先看 NVIDIA 走的 JSON 路径 —— 编码端只挑「调度契约需要的」字段：

// MarshalNodeDevices marshals scheduler-visible device information. Arbitrary
// customInfo is deliberately excluded; MIG placement capabilities are part of
// the scheduling contract and must be preserved.
func MarshalNodeDevices(dlist []*DeviceInfo) string {
	devAnnos := []*DeviceInfo{}
	for _, val := range dlist {
		devAnnos = append(devAnnos, &DeviceInfo{
			ID:          val.ID,
			Count:       val.Count,
			Devmem:      val.Devmem,
			Devcore:     val.Devcore,
			Type:        val.Type,
			Numa:        val.Numa,
			Health:      val.Health,
			Index:       val.Index,
			Mode:        val.Mode,
			MIGProfiles: val.MIGProfiles,   // ← 逗号格式装不下的部分
		})
	}
	data, err := json.Marshal(devAnnos)
	if err != nil {
		return ""
	}
	return string(data)
}

func UnMarshalNodeDevices(str string) ([]*DeviceInfo, error) {
	var dlist []*DeviceInfo
	err := json.Unmarshal([]byte(str), &dlist)
	return dlist, err
}

注意它重新构造了一个只含白名单字段的对象再序列化， 而不是直接 marshal 原对象 —— CustomInfo、DeviceVendor、 DevicePairScore 都被挡在外面。这是一条明确的 API 边界。

再看逗号串路径。解析端对每个字段都做了严格校验 —— 防止畸形注解让调度器 panic：

func DecodeNodeDevices(str string) ([]*DeviceInfo, error) {
	if !strings.Contains(str, OneContainerMultiDeviceSplitSymbol) {
		return nil, fmt.Errorf("node annotation missing device separator")
	}
	tmp := strings.Split(str, OneContainerMultiDeviceSplitSymbol)   // 按 ":" 拆成一张张卡
	var retval []*DeviceInfo
	for _, val := range tmp {
		if val == "" {
			continue                                                 // 末尾的空段（字符串以 ":" 结尾）
		}
		if !strings.Contains(val, ",") {
			return nil, fmt.Errorf("malformed node annotation segment: %q", val)
		}
		items := strings.Split(val, ",")
		if len(items) == 7 || len(items) == 9 {                      // 只接受这两种长度
			count, err := strconv.ParseInt(items[1], 10, 32)
			if err != nil {
				return nil, fmt.Errorf("invalid count field: %w", err)
			}
			devmem, err := strconv.ParseInt(items[2], 10, 32)
			if err != nil {
				return nil, fmt.Errorf("invalid memory field: %w", err)
			}
			devcore, err := strconv.ParseInt(items[3], 10, 32)
			if err != nil {
				return nil, fmt.Errorf("invalid core field: %w", err)
			}
			health, err := strconv.ParseBool(items[6])
			if err != nil {
				return nil, fmt.Errorf("invalid health field: %w", err)
			}
			numa, err := strconv.Atoi(items[5])
			if err != nil {
				return nil, fmt.Errorf("invalid numa field: %w", err)
			}
			mode := "hami-core"                                      // 7 字段格式的默认值
			index := 0
			if len(items) == 9 {                                     // 9 字段才有 index / mode
				index, err = strconv.Atoi(items[7])
				if err != nil {
					return nil, fmt.Errorf("invalid index field: %w", err)
				}
				if index < 0 {
					return nil, fmt.Errorf("index field must not be negative: %d", index)
				}
				mode = items[8]
			}
			i := DeviceInfo{
				ID: items[0], Count: int32(count), Devmem: int32(devmem),
				Devcore: int32(devcore), Type: items[4], Numa: numa,
				Health: health, Mode: mode, Index: uint(index),
			}
			retval = append(retval, &i)
		} else {
			return nil, fmt.Errorf("unexpected field count %d in node annotation", len(items))
		}
	}
	return retval, nil
}

编码方向是它的镜像，简单得多：

func EncodeNodeDevices(dlist []*DeviceInfo) string {
	builder := strings.Builder{}
	for _, val := range dlist {
		builder.WriteString(val.ID)
		builder.WriteString(",")
		builder.WriteString(strconv.FormatInt(int64(val.Count), 10))
		builder.WriteString(",")
		builder.WriteString(strconv.Itoa(int(val.Devmem)))
		builder.WriteString(",")
		builder.WriteString(strconv.Itoa(int(val.Devcore)))
		builder.WriteString(",")
		builder.WriteString(val.Type)
		builder.WriteString(",")
		builder.WriteString(strconv.Itoa(val.Numa))
		builder.WriteString(",")
		builder.WriteString(strconv.FormatBool(val.Health))
		builder.WriteString(",")
		builder.WriteString(strconv.Itoa(int(val.Index)))
		builder.WriteString(",")
		builder.WriteString(val.Mode)
		builder.WriteString(OneContainerMultiDeviceSplitSymbol)      // 每段末尾都加 ":"
	}
	tmp := builder.String()
	klog.V(5).Infof("Encoded node Devices: %s", tmp)
	return tmp
}
踩坑：逗号格式下，型号名里不能有逗号

Type 字段是裸拼进去的，没有转义。如果某个设备型号名里带逗号， 解析时字段数就会变成 10，直接报 unexpected field count。

注意空格是没问题的。NVIDIA-Tesla P4 这种带空格的型号名 在两种格式下都能正常工作，只有逗号会炸。
而 JSON 格式完全没有这个问题，encoding/json 会自动转义。 这算是换成 JSON 附带的一个好处。
如果你想找第一个 PR 的切入口，「给逗号格式的 Type 字段加转义」是个候选 —— 但它只影响 hygon / iluvatar 两家，而且改编码格式是破坏性变更，得先开 issue 讨论兼容方案。

3.5 调度器这一侧怎么读

每个后端的 GetNodeDevices() 负责读自己那条注解。 NVIDIA 的实现同时读了两条注解 —— 设备清单和 NVLink 拓扑分数： 

func (dev *NvidiaGPUDevices) GetNodeDevices(n corev1.Node) ([]*device.DeviceInfo, error) {
	devEncoded, ok := n.Annotations[RegisterAnnos]              // hami.io/node-nvidia-register
	if !ok {
		return []*device.DeviceInfo{}, errors.New("annos not found " + RegisterAnnos)
	}
	nodedevices, err := device.UnMarshalNodeDevices(devEncoded) // JSON 反序列化
	if err != nil {
		klog.ErrorS(err, "failed to decode node devices", "node", n.Name, "device annotation", devEncoded)
		return []*device.DeviceInfo{}, err
	}
	if len(nodedevices) == 0 {
		klog.InfoS("no nvidia gpu device found", "node", n.Name, "device annotation", devEncoded)
		return []*device.DeviceInfo{}, errors.New("no gpu found on node")
	}
	for idx := range nodedevices {
		nodedevices[idx].DeviceVendor = dev.CommonWord()        // 打上厂商标签（注解里没有这个字段）
	}
	pairScores, ok := n.Annotations[RegisterGPUPairScore]       // hami.io/node-nvidia-score
	if !ok {
		klog.V(5).InfoS("no topology score found", "node", n.Name)
	} else {
		// ... 解析 NVLink 拓扑分数，按 UUID 挂到对应的卡上（第 10 章）
	}
	devDecoded := device.EncodeNodeDevices(nodedevices)
	klog.V(5).InfoS("nodes device information", "node", n.Name, "nodedevices", devDecoded)
	return nodedevices, nil
}
最后那两行就是「逗号串」在 NVIDIA 路径上的唯一用途

devDecoded := device.EncodeNodeDevices(nodedevices)。把刚解析出来的对象再编码成逗号串，只为了打一行 V(5) 日志， 因为逗号串比 JSON 短得多，日志里更好读。
它不会被写回任何注解。
如果你在调度器日志里看到逗号格式的设备清单，别误以为注解就长那样。
顺带一提：这行代码无论日志级别开没开都会执行 （参数在调用前就求值了）。在大节点上这是个可以微优化的点。

4. Pod 注解：调度决策

4.1 两级分隔符

Pod 侧的格式更简洁，每个设备只有 4 个字段，但多了一级「容器」的嵌套：

hami.io/vgpu-devices-to-allocate: {容器1的设备};{容器2的设备};

每个容器的设备 = {设备1}:{设备2}:...:
每个设备       = {UUID},{Type},{Usedmem},{Usedcores}

分隔符：
  ,  分隔一个设备的 4 个字段
  :  分隔同一个容器内的多张卡      OneContainerMultiDeviceSplitSymbol
  ;  分隔一个 Pod 内的多个容器      OnePodMultiContainerSplitSymbol

一个真实例子 —— Pod 有两个容器，第一个用 2 张卡，第二个用 1 张卡：

GPU-aaa,NVIDIA,3000,30:GPU-bbb,NVIDIA,3000,30:;GPU-ccc,NVIDIA,8000,50:;
└────────── 容器 1（两张卡）──────────┘ └──── 容器 2 ────┘
                                     ↑                  ↑
                                     容器分隔 ;          结尾也有 ;
为什么每段末尾都有多余的分隔符

编码时是无条件在每个元素后追加分隔符（而不是「元素之间插入」）， 所以字符串总是以 : 或 ; 结尾。 解析时靠 if val == "" { continue } 跳过末尾产生的空段。 写代码时这样最省事，但也意味着空字符串和「一个空容器」在编码后长得一样。

4.3 对应源码：三层嵌套的编码

编码是三个函数一层套一层，正好对应「设备 → 容器 → Pod」三级结构：

func EncodeContainerDevices(cd ContainerDevices) string {        // ① 一个容器的所有卡
	var builder strings.Builder
	for _, val := range cd {
		fmt.Fprintf(&builder, "%s,%s,%d,%d%s", val.UUID, val.Type, val.Usedmem, val.Usedcores, OneContainerMultiDeviceSplitSymbol)
	}
	tmp := builder.String()
	klog.Infof("Encoded container Devices: %s", tmp)
	return tmp
}
func EncodePodSingleDevice(pd PodSingleDevice) string {           // ② 一个 Pod 的所有容器
	res := ""
	for _, ctrdevs := range pd {
		res = res + EncodeContainerDevices(ctrdevs)               //   拼上这个容器的卡
		res = res + OnePodMultiContainerSplitSymbol               //   再补一个 ";"
	}
	klog.Infof("Encoded pod single devices %s", res)
	return res
}

func EncodePodDevices(checklist map[string]string, pd PodDevices) map[string]string {  // ③ 多设备类型
	res := map[string]string{}
	for devType, cd := range pd {
		klog.Infoln("devtype=", devType)
		res[checklist[devType]] = EncodePodSingleDevice(cd)       //   每种硬件一条独立注解
	}
	klog.Infof("Encoded pod Devices %s\n", res)
	return res
}
checklist 是什么？注解 key 的注册表

不同厂商的注解 key 不遵循统一命名规则（历史原因）。 NVIDIA 是 hami.io/vgpu-devices-to-allocate， 寒武纪是 hami.io/cambricon-mlu-devices-to-allocate， 海光是 hami.io/dcu-devices-to-allocate。

所以有一张全局注册表 device.InRequestDevices， 每个后端在初始化时把自己的 key 登记进去： 

func InitNvidiaDevice(nvconfig NvidiaConfig) *NvidiaGPUDevices {
	klog.InfoS("initializing nvidia device", "resourceName", nvconfig.ResourceCountName, ...)
	_, ok := device.InRequestDevices[NvidiaGPUDevice]
	if !ok {
		device.InRequestDevices[NvidiaGPUDevice] = "hami.io/vgpu-devices-to-allocate"  // 待分配
		device.SupportDevices[NvidiaGPUDevice]   = "hami.io/vgpu-devices-allocated"    // 已分配
		util.HandshakeAnnos[NvidiaGPUDevice]     = HandshakeAnnos                      // 握手 key
	}
	...
}
注册表NVIDIA 的值用途
InRequestDeviceshami.io/vgpu-devices-to-allocate调度器写入决策，设备插件消费后会清空
SupportDeviceshami.io/vgpu-devices-allocated决策的永久留档，供监控和用量统计读取
HandshakeAnnoshami.io/node-handshake节点心跳（Node 注解，不是 Pod）

注意 PatchAnnotations 里两条注解写的是同一个字符串。一条会被消费掉，一条留着做记录： 

func (dev *NvidiaGPUDevices) PatchAnnotations(pod *corev1.Pod, annoinput *map[string]string, pd device.PodDevices) map[string]string {
	devlist, ok := pd[NvidiaGPUDevice]
	if ok && len(devlist) > 0 {
		deviceStr := device.EncodePodSingleDevice(devlist)
		(*annoinput)[device.InRequestDevices[NvidiaGPUDevice]] = deviceStr   // 待分配
		(*annoinput)[device.SupportDevices[NvidiaGPUDevice]]   = deviceStr   // 已分配（留档）
		if allocationData, hasAllocations := EncodeMigAllocations(devlist); hasAllocations {
			(*annoinput)[MigAllocationsAnnotation] = allocationData
		}
		...
	}
	return *annoinput
}

5. Handshake：怎么判断一个节点掉线了

设备插件每 30 秒刷新一次注解。但如果节点宕机、网络断了，注解就停在那里不动了 —— 调度器怎么知道这份设备清单已经过期？

点名答到

调度器（老师）在注解上写 Requesting_{当前时间}（「点名了，报数」）。
设备插件（学生）看到后，把它改成 Reported {当前时间}（「到！」）。
如果老师发现自己写的 Requesting 超过一定时间还没被改成 Reported， 就认为这个学生不在了。 

func CheckHealth(devType string, resourceCountName string, node *corev1.Node) (bool, bool) {
	handshake := node.Annotations[util.HandshakeAnnos[devType]]
	if strings.Contains(handshake, "Requesting") {
		// 状态一：我上次点了名，看看学生答到了没
		_, timestampStr, found := strings.Cut(handshake, "_")
		if !found {
			return true, false
		}
		formertime, err := time.ParseInLocation(time.DateTime, timestampStr, time.Local)
		if err != nil {
			return true, false
		}
		if time.Now().Before(formertime.Add(time.Second * 60)) {
			return true, false                       // 还没到 60 秒，再等等
		}

		// 超时了，但再兜一层底：如果 kubelet 还在上报 Allocatable，说明节点其实活着
		qty := node.Status.Allocatable[corev1.ResourceName(resourceCountName)]
		if qty.Value() > 0 {
			klog.V(5).InfoS("Handshake expired but Allocatable still present, skipping NodeCleanUp", ...)
			return true, false
		}
		return false, false                          // 判定掉线 → 触发 NodeCleanUp

	} else {
		// 状态二：注解是 "Reported ..." 或者空的 → 发起一次新的点名
		_, ok := util.HandshakeAnnos[devType]
		if ok {
			tmppat := make(map[string]string)
			tmppat[util.HandshakeAnnos[devType]] = "Requesting_" + time.Now().Format(time.DateTime)
			n, err := util.GetNode(node.Name)
			if err != nil {
				klog.ErrorS(err, "Failed to get node", "nodeName", node.Name)
				return true, false
			}
			if err := util.PatchNodeAnnotations(n, tmppat); err != nil {
				klog.ErrorS(err, "Failed to patch node annotations", "nodeName", node.Name)
			}
		}
		return true, true                            // 第二个返回值 = needUpdate
	}
}

返回的两个 bool 含义容易搞混，记住这张表：

返回值名字调用方（调度器 register 循环）拿它干什么
(true, true)健康 + 需更新正常路径：刷新缓存里这个节点的设备清单
(true, false)健康 + 不用更新点名还在等回复，跳过本轮
(false, false)不健康调 NodeCleanUp()，从调度器缓存里摘掉这个节点
踩坑：这里有两个不同的超时

代码里是 60 秒（time.Second * 60）， 但项目文档 docs/develop/protocol.md 里写的是 5 分钟。 文档没跟上代码。顺手改文档，就是一个能被合入的 PR。

8. 本章自测

你 kubectl describe node 看一台 NVIDIA 节点， hami.io/node-nvidia-register 的值会是什么样子？
A逗号分隔的 9 字段串，卡间用 :
BYAML 列表
CJSON 数组，形如 [{"id":"GPU-0","count":5,"devmem":8192,…}]
Dbase64 编码的二进制
NVIDIA 后端读注解用的是 UnMarshalNodeDevices（json.Unmarshal）， 设备插件写注解用的是 MarshalNodeDevices（json.Marshal）。
A 描述的是 DecodeNodeDevices 那套逗号串，只有 hygon 和 iluvatar 在用。 NVIDIA 代码里确实出现过 EncodeNodeDevices，但那是 GetNodeDevices 末尾打 V(5) 日志用的，不写回注解。
某台节点的注解里，一张卡的 JSON 对象没有 numa 这个 key。说明什么？
A设备插件版本太老，不支持 NUMA
B这张卡不在任何 NUMA 节点上
C注解被截断了
D它的 NUMA 号就是 0，被 omitempty 省掉了
DeviceInfo 每个字段都带 omitempty， 零值（0 / "" / false）不会出现在 JSON 里。 反序列化时 Go 零值正好把它补回 0，结果是对的。
代价是没法区分「没上报」和「上报的值是零值」。 同理 health:false 也会消失，这个更容易让人误判。
一个 Pod 有 3 个容器，只有第 1 个和第 3 个用 GPU。它的 vgpu-devices-to-allocate 会是什么形状？
A只有两段：{ctr1};{ctr3};
B报错，HAMi 不支持部分容器用 GPU
C三段，中间那段写 none
D三段，中间那段是空的：{ctr1};;{ctr3};
EncodePodSingleDevice 遍历的是 PodSingleDevice 这个切片， 每个容器占一个位置，不用 GPU 的容器对应一个空的 ContainerDevices， 编码出来就是相邻的两个 ;。
这一点很关键 —— 设备插件在 Allocate() 里是按容器顺序逐个弹出的， 位置必须严格对齐，否则第 3 个容器会拿到第 1 个容器的卡。第 08 章会看到这个逻辑。
调度器发现某节点的 handshake 注解是 Requesting_2026-09-02 10:00:00，现在是 10:05:00。它会怎么做？
A先看 Node.Status.Allocatable 里还有没有 GPU 资源，有就继续认为健康
B立刻判定节点掉线，清理缓存
C重新写一次 Requesting_ 再等一轮
D什么都不做，等设备插件自己上报
超过 60 秒确实算超时，但代码多兜了一层底： 去查 node.Status.Allocatable[nvidia.com/gpu]。 如果 kubelet 仍在正常上报这个资源，说明设备插件其实活着（可能只是注解 patch 失败了）， 这时贸然清理会导致整个节点上的 GPU 被误摘。 只有 Allocatable 也归零，才真正返回 (false, false) 触发清理。
「多个信号交叉验证后才做破坏性操作」是分布式系统里的常见做法。
为什么 HAMi 需要 InRequestDevices 和 SupportDevices 两张注解 key 注册表？
A一张给 NVIDIA，一张给其他厂商
B一张存明文，一张存加密后的
C一张的内容会被设备插件消费掉，另一张作为永久留档供监控读取
D历史遗留，其实是重复的
两条注解写入时内容完全一样，但生命周期不同： to-allocate 是给设备插件的「工单」，处理完就清掉，防止 Pod 重启时重复分配； allocated 保留下来，vGPUmonitor 和用量统计都靠读它来知道这个 Pod 占了哪些卡。 见 PatchAnnotations（device.go:513）里连着写的那两行。

9. 小结

  • 三个进程都只跟 apiserver 打交道，靠注解传话，所以任何组件重启都不丢状态。
  • Node 注解有两套编码：nvidia / amd / ascend / biren / kunlun-vdevice / vastai 用 JSON， hygon / iluvatar 用逗号串。EncodeNodeDevices 在 NVIDIA 路径上只用于调试日志。
  • JSON 的每个字段都带 omitempty，零值 key 会整个消失。
  • Pod 注解是 4 字段，: 分设备、; 分容器；编码时无条件追加分隔符，所以总以分隔符结尾。
  • 不用 GPU 的容器也占一个空位，设备插件按序号取容器，位置错一位就全错。
  • Handshake 超时后还要查 Allocatable 才判定掉线，避免误摘整个节点。
  • 各厂商注解 key 不统一，靠 InRequestDevices / SupportDevices 两张全局注册表映射。
