这是整个 HAMi 的心脏。两层打分（卡级 + 节点级）决定顺序， Fit 的 14 道关卡决定每张卡能不能用。 这一章有三个互动模拟器，跑一遍比读十遍代码管用。

2. 第一层：卡级打分 ComputeScore

每张卡都会算一个分数，代表「如果把这个 Pod 放上去，这张卡会有多满」。 公式很简单，三个维度加权平均再乘 10： 

func (ds *DeviceListsScore) ComputeScore(requests device.ContainerDeviceRequests, weights util.DeviceScoringWeights) {
	if ds.Device == nil || ds.Device.Count == 0 || ds.Device.Totalcore == 0 || ds.Device.Totalmem == 0 {
		ds.Score = 0
		return
	}
	request, core, mem := int32(0), int32(0), int32(0)
	// Here we are required to use the same type device
	for _, container := range requests {

		if container.Type != ds.Device.Type {
			continue                                    // 只累加同类型设备的请求
		}

		request += 1
		core += container.Coresreq
		if container.MemPercentagereq != 0 && container.MemPercentagereq != 101 {
			mem += int32((int64(ds.Device.Totalmem) * int64(container.MemPercentagereq)) / 100)
			continue                                    // 百分比 → 折算成绝对值
		}
		mem += container.Memreq
	}
	klog.V(2).Infof("device %s user %d, userCore %d, userMem %d,", ds.Device.ID, ds.Device.Used, ds.Device.Usedcores, ds.Device.Usedmem)

	usedScore := float32(request+ds.Device.Used) / float32(ds.Device.Count)        // 份数占用率
	coreScore := float32(core+ds.Device.Usedcores) / float32(ds.Device.Totalcore)  // 算力占用率
	memScore  := float32(mem+ds.Device.Usedmem) / float32(ds.Device.Totalmem)      // 显存占用率
	ds.Score = float32(util.Weight) * (float32(weights.Slot)*usedScore + float32(weights.Core)*coreScore + float32(weights.Memory)*memScore)
	klog.V(2).Infof("device %s computer score is %f", ds.Device.ID, ds.Score)
}
拆开看这个公式
Score = 10 × ( w_slot × (已用份数+本次请求数)/总份数
             + w_core × (已用算力+本次请求算力)/总算力
             + w_mem  × (已用显存+本次请求显存)/总显存 )

util.Weight = 10（pkg/util/types.go:104）
默认权重 w_slot = w_core = w_mem = 1（DefaultDeviceScoringWeights）
用户可以用 hami.io/device-scoring-weights 注解改

关键点：分数算的是「放上去之后」的占用率，不是「现在」的。 所以它能区分「放上去刚好塞满」和「放上去还剩一大半」。

3. 排序：binpack 和 spread 就差一个大于号

算完分数后，fitInDevices 会对整个设备列表排序， 然后 Fit() 从后往前遍历。所以排序规则直接决定了「优先挑哪张卡」。 

func (l DeviceUsageList) Less(i, j int) bool {
	// Comma-separated policy: chain binpack/spread/numa as sort keys in the
	// order the caller wrote them. mutex/topology-aware are filters applied
	// in each device backend's Fit(), not sort keys, so they don't appear here.
	// Bare "numa" also routes here: it's a chain token, not a legacy value.
	if strings.Contains(l.Policy, ",") || l.Policy == util.GPUSchedulerPolicyNuma.String() {
		return l.lessByChain(i, j)                      // 逗号分隔的复合策略
	}

	// Single policy value: unchanged behavior.
	si, sj := l.DeviceLists[i].Score, l.DeviceLists[j].Score
	ni, nj := l.DeviceLists[i].Device.Numa, l.DeviceLists[j].Device.Numa
	binpack := l.Policy == util.GPUSchedulerPolicyBinpack.String()

	// mutex: busy GPUs first, idle GPUs at tail so Fit picks idle ones.
	if l.Policy == util.GPUSchedulerPolicyMutex.String() {
		ui, uj := l.DeviceLists[i].Device.Used, l.DeviceLists[j].Device.Used
		if ui != uj {
			return ui > uj                              // 忙的排前面 → 空闲的在末尾被优先选中
		}
		return ni < nj
	}

	// numa-bind: keep NUMA groups contiguous for Fit's same-NUMA accumulation.
	if l.NumaBind {
		if binpack {
			if ni == nj {
				return si < sj
			}
			return ni > nj                              // NUMA 是主键，保证同 NUMA 的卡连续
		}
		// default policy is spread
		if ni == nj {
			return si > sj
		}
		return ni < nj
	}

	// score primary, NUMA tiebreaker (#1806).
	if binpack {
		if si != sj {
			return si < sj                              // binpack：分数低的排前，高的在末尾
		}
		return ni < nj
	}
	// default policy is spread
	if si != sj {
		return si > sj                                  // spread：分数高的排前，低的在末尾
	}
	return ni < nj
}
「从后往前遍历」是理解排序的钥匙
for i := len(devices) - 1; i >= 0; i-- {      // ← 倒着走！
	dev := devices[i]
	...
}

所以 「排在末尾的卡最先被检查」。这就解释了所有排序规则：

策略排序（升序）末尾是谁 = 优先选谁
binpack分数 低 → 高分数最高 = 最满的卡，把碎片塞满
spread分数 高 → 低分数最低 = 最空的卡，负载摊开
mutex已用份数 多 → 少已用份数最少 = 全空闲的卡，实现独占
numa-bindNUMA 号为主键保证同 NUMA 的卡在列表里连续，Fit 才能累积同 NUMA 的卡
复合策略：numa,binpack 这样写

新版本支持用逗号串联排序键，走 lessByChain()（）。 mutex 和 topology-aware 不是排序键， 它们是在 Fit() 里通过 util.PolicyContains 生效的过滤器， 所以 gpuSortKeyChain() 会把它们丢掉。这个区分很容易搞混。

4. 第二层：节点级打分

节点分数 = 基础分 + 后端加分。基础分逻辑跟卡级几乎一样，只是把全节点的卡汇总：

func (ns *NodeScore) ComputeDefaultScore(devices DeviceUsageList) {
	used, usedCore, usedMem := int32(0), int32(0), int32(0)
	for _, device := range devices.DeviceLists {
		used += device.Device.Used
		usedCore += device.Device.Usedcores
		usedMem += device.Device.Usedmem
	}
	klog.V(2).Infof("node %s used %d, usedCore %d, usedMem %d,", ns.NodeID, used, usedCore, usedMem)

	total, totalCore, totalMem := int32(0), int32(0), int32(0)
	for _, deviceLists := range devices.DeviceLists {
		total += deviceLists.Device.Count
		totalCore += deviceLists.Device.Totalcore
		totalMem += deviceLists.Device.Totalmem
	}
	if total == 0 || totalCore == 0 || totalMem == 0 {
		ns.Score = 0
		return
	}
	useScore := float32(used) / float32(total)
	coreScore := float32(usedCore) / float32(totalCore)
	memScore := float32(usedMem) / float32(totalMem)
	ns.Score = float32(util.Weight) * (useScore + coreScore + memScore)
	klog.V(2).Infof("node %s computer default score is %f", ns.NodeID, ns.Score)
}
节点基础分不支持自定义权重

对比一下：卡级 ComputeScore 有 weights.Slot/Core/Memory， 但节点级 ComputeDefaultScore 是硬编码的等权重。
这算是一个不一致的地方。如果你想找一个「小而明确」的贡献点， 「让 hami.io/device-scoring-weights 也作用于节点打分」是个不错的候选 —— 但记得先开 issue 问社区这是不是有意为之。

然后是后端加分。这里用了一个空方法的标记接口：

// policyNeutralScorer is an optional interface a device backend may implement to
// declare that its ScoreNode result is policy-independent and follows a "higher
// score is a better node" convention. Backends that implement it must not
// inspect the scheduler policy inside ScoreNode; instead OverrideScore weights
// the returned score and adapts it to the active scheduling policy (for example,
// inverting it under the Spread policy). This keeps policy handling in one place
// so new policies do not require backend-specific changes.
type policyNeutralScorer interface {
	PolicyNeutralScore()
}

func (ns *NodeScore) OverrideScore(previous []*device.DeviceUsage, policy string) {
	devScore := float32(0)
	for idx, val := range ns.Devices {
		dev, ok := device.GetDevices()[idx]
		if !ok || dev == nil {
			klog.V(4).Infof("Skip scoring for device type %s: not registered", idx)
			continue
		}

		score := dev.ScoreNode(ns.Node, val, previous, policy)

		// Backends implementing policyNeutralScorer return policy-independent
		// "higher is better" scores. For the Spread policy (which selects the
		// lowest score), we invert the score to preserve the ranking.
		// We also apply a weight of 10000 to ensure device scores dominate
		// the base node score.
		if _, ok := dev.(policyNeutralScorer); ok {
			weight := float32(10000)
			if policy == util.NodeSchedulerPolicySpread.String() {
				weight = -10000                        // spread 下取反
			}
			score = weight * score
		}

		devScore += score
	}
	ns.Score += devScore
	klog.V(2).Infof("node %s default score is %f, computer override score is %f", ns.NodeID, ns.Score-devScore, ns.Score)
}
policyNeutralScorer。标记接口的用法

问题：不同后端的 ScoreNode 返回的分数，方向不一致。 有的是「越高越好」，而调度器在 spread 策略下要选最低分的节点。 如果每个后端自己判断策略，逻辑就散落各处了。

解法：定义一个空方法的标记接口。后端实现它，就表示「我返回的是策略无关的、越高越好的分数」， 剩下的策略适配（spread 时取反）由 OverrideScore 统一处理。
权重 10000 保证后端分数压倒基础分 —— 比如 NVLink 拓扑最优的组合， 无论基础分怎样都应该胜出。

			profile, placement, ok = selectMigCandidate(n.MigProfiles, occupied, ctr.Usedmem)
		}
		if !ok {
			return errors.New("MIG profile and placement allocation failed")
		}
		ctr.Usedmem = profile.MemoryMB          // ← 注意：会覆盖用户请求值！
		ctr.Usedcores = profile.Core
		...
		n.MigAllocationsInUse = append(n.MigAllocationsInUse, device.MigAllocation{Profile: profile.Name, Placement: placement})
	}
	n.Used++                                     // 三行记账
	n.Usedcores += ctr.Usedcores
	n.Usedmem += ctr.Usedmem
	return nil
}

7. InitContainer 的峰值用量：一个精妙的双机制

第 03 章讲配额时提过：InitContainer 是串行的， 所以它们的资源应该取最大值而不是累加。 但调度时还有个额外要求：要保证每个 InitContainer 单独看都能放下。

话剧的舞台调度

三个 InitContainer 像三幕戏，轮流上台，同一时刻只有一幕在演。
要求 1：每一幕单独都要放得下舞台（各自 Fit 检查）。
要求 2：最终占用要按「最费空间的那一幕」算，而不是三幕加起来。
例外：Sidecar 是一直待在台上的道具，它跟每一幕都同时存在，所以要累加。 

func allocateInitContainers(appNodeCopy *NodeUsage, nodeID string, resourceReqs device.PodDeviceRequests, task *corev1.Pod, nodeInfo *device.NodeInfo, allocTypes map[string]struct{}, sidecarIdx map[int]struct{}, numInitContainers int, peakUsage map[string]peakUsageSnapshot, weights util.DeviceScoringWeights) (device.PodDevices, bool, string) {
	initAllocs := make(device.PodDevices)

	for i, req := range resourceReqs {
		if i >= numInitContainers {
			break
		}
		if len(req) == 0 {
			for typ := range allocTypes {
				initAllocs[typ] = append(initAllocs[typ], device.ContainerDevices{})   // 占位
			}
			continue
		}
		if _, isSidecar := sidecarIdx[i]; isSidecar {
			// Sidecar：一直活着 → 直接在共享副本上扣，累积效果
			fit, reason := fitInDevices(appNodeCopy, req, task, nodeInfo, &initAllocs, weights)
			if !fit {
				klog.V(4).InfoS("Sidecar container does not fit", ...)
				return nil, false, reason
			}
			updatePeakUsage(peakUsage, appNodeCopy)
		} else {
			// 普通 Init：在一次性副本上试算 → 用完丢弃，不影响下一个
			nodeCopy := appNodeCopy.DeepCopy()                                        // 关键
			fit, reason := fitInDevices(nodeCopy, req, task, nodeInfo, &initAllocs, weights)
			if !fit {
				klog.V(4).InfoS("Init container does not fit", ...)
				return nil, false, reason
			}
			updatePeakUsage(peakUsage, nodeCopy)                                      // 但记录峰值
		}
		...
	}
	return initAllocs, true, ""
}
两套机制配合
机制作用
DeepCopy 一次性副本让每个普通 InitContainer 都从「Sidecar 已占用」的基线开始试算，
互不影响。因为它们不同时存在
peakUsage 快照记录整个过程中每张卡出现过的最高用量，
最后用 applyPeakUsage 写回真实节点

最后一步 applyPeakUsage（） 取 max(普通容器分配后的用量, init 阶段的峰值)， 跟第 03 章配额检查的公式完全对应。

			switch {
			case result.err != nil:
				failedNodesMutex.Lock()
				failedNodes[nodeID] = result.reason
				failedNodesMutex.Unlock()
				errCh <- result.err

			case result.score == nil:                     // 不 fit，但不是错误
				failedNodesMutex.Lock()
				failedNodes[nodeID] = result.reason
				for reasonType := range common.ParseReason(result.reason) {
					failureReason[reasonType] = append(failureReason[reasonType], nodeID)
				}
				failedNodesMutex.Unlock()

			default:
				fitNodesMutex.Lock()
				res.NodeList = append(res.NodeList, result.score)
				fitNodesMutex.Unlock()
			}
		}(nodeID, node)
	}
	wg.Wait()
	close(errCh)
并发安全的前提：每个节点数据独立

这些 goroutine 敢并发跑，是因为 scoreNode 一进去就 appNodeCopy := node.DeepCopy()（）， 每个节点操作自己的副本。
如果哪天有人在 scoreNode 里加了对全局状态的写入，这里就会炸。 项目专门有 -race 的 CI 就是防这个。

10. 本章自测

在 binpack 策略下，DeviceUsageList.Less() 返回 score[i] < score[j]（升序），而 Fit() 从后往前遍历。最先被检查的是哪张卡？
A最空闲的卡（分数最低）
B最满的卡（分数最高）
CNUMA 号最小的卡
D索引最小的卡
升序排列 → 分数最高的在末尾 → 从后往前遍历 → 最先检查分数最高的。 分数代表「放上去之后有多满」，binpack 的目标就是优先把已经用了一部分的卡填满， 留出完整的空卡给需要整卡的任务。
这两个设计（排序方向 + 倒序遍历）必须一起看才能理解，单看任何一个都会得出相反的结论。
一个 Pod 有 2 个普通 InitContainer（各要 8000MB）和 1 个普通容器（要 3000MB）。调度器最终会在卡上记多少显存？
A19000（全部累加）
B3000（只算普通容器）
C8000（init 峰值和普通容器取最大）
D11000（一个 init + 普通容器）
两个普通 InitContainer 串行执行，各自在 DeepCopy 的一次性副本上试算， peakUsage 记录到的峰值是 8000（不是 16000，因为它们不同时存在）。 普通容器占 3000。最后 applyPeakUsage 取 max(3000, 8000) = 8000。
注意：两个 InitContainer 各自都必须单独能放下 8000， 这是「每个 init 都跑一次 fitInDevices」保证的。 如果其中一个要 40000MB 而卡只有 32768，整个节点会被判 unfit。
Pod 设了 nvidia.com/numa-bind: true 要 2 张卡。节点上排序后的卡是 [numa0-A, numa0-B, numa1-C, numa1-D]（倒序遍历，即先 D 后 A）。会选中哪两张？
AD 和 C（都在 numa1）
BD 和 A（分数最优的两张）
CA 和 B（numa0 优先）
D失败，因为跨 NUMA
倒序遍历先看 D（numa1），prevnuma 从 -1 变成 1，攒下 D； 再看 C（numa1），NUMA 没变，继续攒 → 凑够 2 张，立刻返回。
如果需要 3 张，走到 B（numa0）时 numa && prevnuma != dev.Numa 成立， 把攒的 D、C 全部丢弃（tmpDevs = make(...)）， 从 numa0 重新开始攒 B、A —— 但只有 2 张，最终失败并报 NumaNotFit。
这个算法能工作的前提是排序保证同 NUMA 的卡连续。
为什么 policyNeutralScorer 被设计成一个空方法的「标记接口」？
AGo 语言要求接口至少有一个方法
B为了让后端能返回多个分数
C为了性能，避免反射
D让后端声明「我的分数是策略无关的」，把策略适配逻辑集中到 OverrideScore 一处
看代码里那段注释：实现这个接口的后端不许在 ScoreNode 里检查调度策略， 只管返回「越高越好」的分数；OverrideScore 统一负责在 spread 策略下取反。
好处：加新策略时只改一个地方，不用挨个改当前 16 个后端实现。 这是「把变化点收敛到单点」的经典做法，
用户看到 event 2 nodes CardInsufficientMemory(node-1,node-3)。他应该怎么办？
A重启 HAMi 调度器
B降低 nvidia.com/gpumem 的值，或者等其他 Pod 释放，或者加机器
C把 schedulerName 改回 default-scheduler
D给 Pod 加 nvidia.com/use-gputype 注解
这条消息来自 Fit 的第 ⑩ 关： dev.Totalmem - dev.Usedmem < memreq， 即两个节点上每一张卡的剩余显存都不够。
排查顺序：先 kubectl describe node 看 hami.io/node-nvidia-register 确认卡的总显存； 再看那个节点上已经跑了哪些 GPU Pod。
D 反而会让候选卡更少，更难调度上去。

11. 小结

  • 两层打分：卡级 ComputeScore（决定选哪张卡）+ 节点级 ComputeDefaultScore + OverrideScore（决定选哪个节点）。
  • 分数含义是「放上去之后有多满」，binpack 选最满、spread 选最空、mutex 选全空。
  • 排序方向 + 倒序遍历必须一起看，单看一个会得出相反结论。
  • Fit 的 14 道关卡里，最常触发的是 ⑥ 份数用完、⑩ 显存不足、⑪ 算力不足。
  • NUMA 绑定靠「排序保证连续 + 换组就清空重来」实现。
  • InitContainer 用 DeepCopy 一次性副本（互不影响）+ peakUsage 快照（记峰值）双机制。
  • 并发打分安全的前提是 scoreNode 一进去就 DeepCopy，改这块代码要格外小心。
