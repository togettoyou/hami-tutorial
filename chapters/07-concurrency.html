第 07 章 · 第三阶段 硬骨头

并发与一致性：缓存、事件、选主

HAMi 的调度决策完全建立在一份本地缓存之上。 缓存错一点，就会超卖或者资源泄漏。这一章讲这份缓存怎么维护、 有哪些并发陷阱 —— 也是最容易做出高价值贡献的地方。

学完这章你应该能

  • 说出 HAMi 里所有的锁、各自保护什么、粒度多大
  • 画出 Pod informer 三个回调的完整决策树（包括 terminating 的特殊处理）
  • 解释 synced 标志为什么必须在 register 的最后一行才置 true
  • 说清楚 leader 选举失败时会发生什么，以及为什么 follower 不能 register
  • 找出至少三处「如果改错就会导致超卖/泄漏」的代码位置

1. 全景：三个并发实体

① Informer 事件循环client-go 的 goroutine
Pod add/update/delete、Node add/delete、ResourceQuota add/update/delete
随时可能触发，改 podManager 和 quotaManager
⇅ 共享 podManager / overviewstatus
② register 巡检循环独立 goroutine，15 秒一轮
扫所有节点 → 握手 → 解析设备清单 → 重建 overviewstatus 全量快照
⇅
③ HTTP 请求处理每个请求一个 goroutine
/filter（读缓存 + 写记账）、/bind（抢锁）、/refit（改已有分配）
内部还会为每个节点再起 goroutine 并发打分

2. HAMi 的所有锁

锁类型保护什么
Scheduler.lock
 sync.RWMutex overviewstatus（节点用量总览快照）。register 写、InspectAllNodesUsage 读。
读多写少，所以用读写锁
Scheduler.allocLock
 sync.Mutex 预留账本的三条修改路径：Filter、RefitNumaAllocation、onUpdatePod 的 init 用量释放。
保证不会看到「改了一半」的账

nodeLocks（每节点一把）

hami.io/mutex.lock Node 注解（分布式） 跨进程、跨调度器副本的互斥（第 06 章）

3. Pod 事件回调：账本的生命线

podManager 是「谁占了哪张卡多少显存」的唯一真相来源。 它只被三个 informer 回调和 Filter 修改。任何一个分支写错， 直接导致超卖或泄漏。

Pod 事件决策树互动

选一个 Pod 状态，看 informer 回调怎么处理它。

3.1 onAddPod：四道判断

func (s *Scheduler) onAddPod(obj any) {
	pod, ok := obj.(*corev1.Pod)
	if !ok {
		klog.ErrorS(fmt.Errorf("invalid pod object"), "Failed to process pod addition")
		return
	}
	klog.V(5).InfoS("Pod added", "pod", pod.Name, "namespace", pod.Namespace)
	nodeID, ok := pod.Annotations[util.AssignedNodeAnnotations]
	if !ok {
		return                                       // ① 没被 HAMi 调度过 → 不关我事
	}
	if util.IsPodInTerminatedState(pod) {
		if pi, ok := s.podManager.TakeAndDeletePod(pod); ok {
			s.quotaManager.RmUsage(pod, pi.Devices)  // ② 已终止 → 释放资源
		}
		return
	}
	if util.IsPodTerminating(pod) {
		// A terminating pod still holds its devices. When it is already
		// cached, refresh the object; when it is not (the informer's initial
		// sync after a scheduler restart replays it as an add), fall through
		// so its usage is accounted instead of silently dropped.
		if _, cached := s.podManager.GetPod(pod); cached {
			klog.V(5).InfoS("Pod is terminating but holding locks, preserving cache", "pod", pod.Name)
			s.podManager.UpdatePod(pod)              // ③ 正在删但还占着卡 → 保留记账
			return
		}
	}

	rawDevices, err := device.DecodePodDevices(device.SupportDevices, pod.Annotations)
	if err != nil {
		klog.ErrorS(err, "failed to decode pod devices", "pod", klog.KObj(pod))
		return
	}

	effectiveDevices := device.CollapseInitContainerUsage(pod, rawDevices)

	if s.podManager.AddPod(pod, nodeID, effectiveDevices) {   // ④ 正常路径：记账
		s.quotaManager.AddUsage(pod, effectiveDevices)
	}
}
第 ③ 条那段注释，讲的是一个真实 bug

「正在删除的 Pod 仍然占着卡」。这是对的， Pod 有 DeletionTimestamp 之后容器还在跑，GPU 还在用，资源不能立刻释放。

但注释说的第二种情况更微妙：调度器重启后， informer 会把集群里所有已存在的 Pod 当作 add 事件重放一遍。 如果这时有一个正在删除的 Pod，而缓存里当然没有它（刚重启，缓存是空的）， 早期版本会直接 return，导致这个 Pod 占的显存永远统计不到 → 超卖。
修复方式就是这个 if cached 判断： 没缓存过就不 return，继续往下走正常记账路径。
「组件重启后 informer 重放全量事件」是 K8s controller 开发的经典陷阱， 每个回调都要问自己「这个事件如果是重放的，我处理对了吗」。

3.2 onUpdatePod：多了一个「用量收缩」

func (s *Scheduler) onUpdatePod(oldObj, newObj any) {
	newPod, ok := newObj.(*corev1.Pod)
	if !ok {
		return
	}
	klog.V(5).InfoS("Pod updated", "pod", klog.KObj(newPod))

	if _, ok := newPod.Annotations[util.AssignedNodeAnnotations]; !ok {
		return
	}
	if util.IsPodInTerminatedState(newPod) {
		if pi, ok := s.podManager.TakeAndDeletePod(newPod); ok {
			s.quotaManager.RmUsage(newPod, pi.Devices)
		}
		return
	}
	if util.IsPodTerminating(newPod) {
		// Same as onAddPod: a resync update for a terminating pod that is
		// missing from the cache must be accounted, not dropped.
		if _, cached := s.podManager.GetPod(newPod); !cached {
			s.onAddPod(newPod)                       // 复用 add 的逻辑
			return
		}
		s.podManager.UpdatePod(newPod)
		return
	}

	// RefitNumaAllocation reads the release flag, devices, and quota as one
	// accounting snapshot. Keep the normal update and the one-time init-usage
	// transition in the same critical section so a refit cannot commit from a
	// stale pre-release snapshot after this handler records steady-state usage.
	s.allocLock.Lock()                               // 跟 Filter 用同一把锁
	defer s.allocLock.Unlock()

	pi, exists := s.podManager.GetPod(newPod)
	if !exists {
		s.onAddPod(newPod)
		return
	}

	s.podManager.UpdatePod(newPod)

	if !pi.InitContainerResourceReleased && util.AllNonSidecarInitContainersSucceeded(newPod) {
		rawDevices, err := device.DecodePodDevices(device.SupportDevices, newPod.Annotations)
		if err != nil {
			klog.ErrorS(err, "failed to decode pod devices during shrink", "pod", klog.KObj(newPod))
			return
		}

		steadyStateDevices := device.SteadyStateDeviceUsage(newPod, rawDevices)   // 收缩

		oldDevices, ok := s.podManager.UpdatePodDevice(newPod, steadyStateDevices)
		if ok {
			s.quotaManager.ReplaceUsage(newPod, oldDevices, steadyStateDevices)
			klog.InfoS("Non-sidecar init containers completed, shrunk usage to steady state",
				"pod", klog.KObj(newPod),
				"oldUsage", oldDevices,
				"newUsage", steadyStateDevices,
			)
		}
	}
}
「用量收缩」是什么

回忆第 03、05 章：调度时按 max(init 峰值, sidecar + 普通容器) 预留资源。 如果某个 InitContainer 要 8000MB 而普通容器只要 3000MB， 调度时预留的是 8000MB。

但 InitContainer 跑完就退出了，那 5000MB 就白占着。 所以这里检测到「所有非 sidecar InitContainer 都成功了」， 就把账本收缩到稳态用量。把多占的 5000MB 还回去， 让别的 Pod 能用上。
InitContainerResourceReleased 是幂等标志，保证只收缩一次。

注意 allocLock 的位置

锁是在前面几个 return 分支之后才加的 —— terminated / terminating 的处理不需要这把锁。
而注释解释了为什么「普通 update」和「一次性的收缩」必须在同一个临界区： 如果分成两段，NUMA refit（第 10 章）可能在中间插进来， 基于「收缩前」的快照做决策，然后提交一个过时的分配 → 账本错乱。

4. register 巡检循环

func (s *Scheduler) RegisterFromNodeAnnotations() {
	klog.InfoS("Entering RegisterFromNodeAnnotations")
	defer klog.InfoS("Exiting RegisterFromNodeAnnotations")

	labelSelector := labels.Set(config.NodeLabelSelector).AsSelector()
	klog.InfoS("Using label selector for list nodes", "selector", labelSelector.String())

	ticker := time.NewTicker(time.Second * 15)          // 15 秒一轮
	defer ticker.Stop()
	printedLog := map[string]bool{}
	for {
		select {
		case <-s.nodeNotify:                            // 节点增删 → 立即触发
			klog.V(5).InfoS("Received node notification")
		case <-s.leaderNotify:                          // 刚当选 leader → 立即触发
			klog.V(5).InfoS("Received leaderElection notification. We are just elected to leader")
		case <-ticker.C:                                // 定时触发
			klog.V(5).InfoS("Ticker triggered")
		case <-s.stopCh:
			klog.InfoS("Received stop signal, exiting RegisterFromNodeAnnotations")
			return
		}
		if atomic.LoadUint32(&s.started) == 0 {
			klog.V(5).InfoS("Scheduler not started yet, skipping ...")
			continue                                    // informer 还没起来，跳过
		}
		s.register(labelSelector, printedLog)
	}
}
三个触发源合并成一个 select：事件驱动 + 定时兜底

事件驱动（nodeNotify、leaderNotify）保证响应快； 15 秒定时器保证即使漏了事件也能自愈。
这是写 controller 的标准模式：永远不要只依赖事件， 因为事件可能丢失、乱序、重复。定时全量对账是最后一道保险。

4.1 synced 标志的严格时序

func (s *Scheduler) register(labelSelector labels.Selector, printedLog map[string]bool) {
	// Lock here to avoid setting s.synced to false, when we lost leadership, while doing register.
	// 1. lost leadership before register: synced will set to false in callbacks, and register will be skipped because IsLeader() returns false
	// 2. lost leadership during or after register: synced will set to true after finishing register, and callback will set it to false again after lock is acquired by callback
	s.lock.Lock()
	defer s.lock.Unlock()

	// Only do registration when we are leader.
	isLeader := s.leaderManager.IsLeader()
	if isLeader {
		s.updateSchedulerLabel()
	} else {
		klog.V(5).InfoS("Scheduler is not leader yet, skipping ...")
		return                                       // follower 不做注册
	}
	...
	_, overallnodeMap, _, err := s.getNodesUsage(&nodeNames, nil)
	if err != nil {
		klog.ErrorS(err, "Failed to get node usage", "nodeNames", nodeNames)
		return                                       // 失败就不置 synced
	}
	s.overviewstatus = *overallnodeMap

	// Set synced to true only after getNodeUsage() succeeds
	s.synced.Store(true)                             // 最后一行才置 true
}
为什么 synced 必须是最后一行

HTTP 层的 WaitForCacheSync（第 04 章）就等这个标志。 如果提前置 true，filter 请求会在缓存只填了一半的时候进来， 看到「有些节点没有 GPU」，把 Pod 误判为不可调度。
而且注意：中途任何一个 return 都不会置 true。这是刻意的，宁可继续阻塞请求，也不能用残缺的数据做决策。
这个模式叫「就绪标志放在初始化的最后一步」， 跟 Go 里 sync.Once、双检锁的道理是一样的。

5. 选主：为什么 follower 什么都不做

	if config.LeaderElect {
		leaseInformerFactory := informers.NewSharedInformerFactoryWithOptions(s.kubeClient, defaultResync, informers.WithNamespace(config.LeaderElectResourceNamespace))
		s.leaseLister = leaseInformerFactory.Coordination().V1().Leases().Lister()

		leaseEventHandlerRegistration, err := leaseInformerFactory.Coordination().V1().Leases().Informer().AddEventHandler(s.leaderManager)
		if err != nil {
			return fmt.Errorf("failed to register lease event handler: %w", err)
		}
		leaseInformerFactory.Start(s.stopCh)
		leaseInformerFactory.WaitForCacheSync(s.stopCh)
		cache.WaitForCacheSync(s.stopCh, leaseEventHandlerRegistration.HasSynced)
	}
为什么需要选主

HAMi 调度器可以部署多副本做 HA。但 register() 会 往 Node 注解写 handshake（第 01 章的「点名」）。 如果多个副本同时点名，就会互相覆盖，导致 handshake 状态机错乱， 节点被误判为掉线。

所以：只有 leader 做 register（写注解），follower 只保持待命。
注意 /filter 和 /bind 不受选主限制。因为 kube-scheduler 通过 Service 访问扩展器， 请求可能落到任何一个副本上。这就是为什么节点锁必须是集群级的分布式锁， 而不能只靠进程内 mutex。

Leader 状态用 coordination.k8s.io/Lease 实现，判断逻辑：

func (m *leaderManager) isHolderOf(lease *coordinationv1.Lease) bool {
	...
}

func (m *leaderManager) isLeaseValid(now time.Time) bool {
	if m.observedLease == nil || m.observedLease.Spec.LeaseDurationSeconds == nil {
		return false
	}
	return m.observedTime.Add(time.Second * time.Duration(*m.observedLease.Spec.LeaseDurationSeconds)).After(now)
}
注意这里的 observedTime 是本地观察时间

判断租约是否有效用的是「我什么时候看到这个 Lease 的」+ 租约时长， 而不是 Lease 对象里的 renewTime。
这是刻意的：跨节点的系统时钟可能有偏差， 用本地单调时间更安全。（第 01 章的 handshake 也有同样的时钟问题， 但那里用的是墙上时间，是一个相对薄弱的点。）

6. 节点删除：一次五连清理

func (s *Scheduler) onDelNode(obj any) {
	// Ensure downstream consumers are notified regardless of decoding success
	defer s.doNodeNotify()                           // ① 不管成不成功都通知 register 循环

	var nodeName string
	switch t := obj.(type) {
	case *corev1.Node:
		nodeName = t.Name
		klog.V(4).InfoS("Node deleted, cleaning up nodelock", "node", nodeName)
	case cache.DeletedFinalStateUnknown:             // ← tombstone！
		if n, ok := t.Obj.(*corev1.Node); ok {
			nodeName = n.Name
			klog.V(4).InfoS("Node tombstone deleted, cleaning up nodelock", "node", nodeName)
		} else {
			klog.V(5).InfoS("Received tombstone for non-node object on delete")
			return
		}
	default:
		klog.V(5).InfoS("Received unknown object type on node delete")
		return
	}

	nodelockutil.CleanupNodeLock(nodeName)           // ② 清进程内的每节点 mutex（防内存泄漏）
	s.rmNode(nodeName)                               // ③ 清 nodeManager 里的设备清单
	s.cleanupNodeUsage(nodeName)                     // ④ 清 overviewstatus（否则指标一直报废弃节点）
	// Clear per-device health bookkeeping for the deleted node.
	// Devices that track per-node state (e.g. NvidiaGPUDevices) implement
	// NodeDeleted to prune their internal maps; others are a no-op.
	for _, devInstance := range device.GetDevices() {
		if nd, ok := devInstance.(*nvidia.NvidiaGPUDevices); ok {
			nd.NodeDeleted(nodeName)                 // ⑤ 清各后端自己的每节点缓存
		}
	}
}
cache.DeletedFinalStateUnknown（墓碑）—— 必须处理

当 informer 和 apiserver 的连接断开又重连时，中间发生的删除事件拿不到原始对象， client-go 会包一个 DeletedFinalStateUnknown「墓碑」给你。
不处理这个 case，节点删除时缓存就清不干净。调度器会一直认为那台机器还在，把 Pod 调度过去然后永远 Pending。
每个 DeleteFunc 都必须有这个 switch。这是审查 controller 代码时的必查项。

第 ⑤ 步有个类型断言，这是个可以改进的点

if nd, ok := devInstance.(*nvidia.NvidiaGPUDevices); ok。这里硬编码了 NVIDIA 类型。注释说「其他后端是 no-op」， 但如果将来有别的后端也需要清理每节点状态，就得改这里。
更好的做法是定义一个可选接口（就像第 05 章的 policyNeutralScorer）： 

type nodeDeletedNotifier interface{ NodeDeleted(nodeName string) }

if nd, ok := devInstance.(nodeDeletedNotifier); ok {
	nd.NodeDeleted(nodeName)
}

这是一个范围小、价值明确、不改行为的重构 —— 非常适合做第一个 PR。

7. 三类最容易踩的并发坑

坑症状在 HAMi 里的防御
超卖 分配的显存总和超过物理容量，容器启动后 CUDA OOM 节点锁 + Filter 的 TakeAndDeletePod + informer 回调的 terminating 处理
资源泄漏 集群明明空着却调度不上去；overviewstatus 里有幽灵占用 cleanupStalePodAllocation、onDelPod、onDelNode 五连清理、15 秒全量对账
数据竞争 -race 报警；偶发的 map 并发读写 panic scoreNode 一进去就 DeepCopy；所有共享 map 都有锁；专门的 race 测试

9. 本章自测

调度器重启后，informer 把一个「正在删除中」的 GPU Pod 当作 add 事件重放。如果 onAddPod 直接 return，会发生什么？
A没影响，Pod 马上就要删了
B这个 Pod 占的显存统计不到，其他 Pod 会被分配到同一份显存 → 超卖 → CUDA OOM
C调度器会 panic
DPod 会被重新调度
Pod 有了 DeletionTimestamp 之后，容器还在运行， GPU 显存还被真实占用着。如果账本里没有它， getNodesUsage 算出来的「已用」就偏小， 新 Pod 会被分配到同一份显存上，两个进程抢同一块显存 → CUDA OOM。
所以代码里那个 if _, cached := s.podManager.GetPod(pod); cached 判断很关键： 缓存里有就只刷新，没有就落到正常记账路径。
为什么 s.synced.Store(true) 一定要放在 register() 的最后一行？
A提前置 true 会让 filter 请求用残缺的缓存做决策，把有 GPU 的节点误判为无 GPU
BGo 的编译器要求
C为了让日志顺序好看
D为了释放锁
HTTP 层的 WaitForCacheSync 就等这个标志。 register() 中间有多个 return（不是 leader、列节点失败、算用量失败）， 任何一条提前返回都不该让缓存被认为「就绪」。
宁可继续阻塞请求（kube-scheduler 会重试），也不能用残缺数据把 Pod 误判为不可调度。
这是「就绪标志放最后」的通用模式。
调度器部署了 3 个副本。哪些操作只有 leader 能做？
A全部操作，follower 完全空转
B只有 /bind，/filter 所有副本都能处理
C只有 register()（写 Node 的 handshake 注解），/filter 和 /bind 任何副本都可能处理
D只有 webhook
kube-scheduler 通过 Service 访问扩展器，请求会被负载均衡到任意副本， 所以 /filter 和 /bind 无法限制在 leader。
只有 register() 受限，因为它要写 Node 的 handshake 注解 —— 多个副本同时写会互相覆盖，让「点名答到」状态机错乱。
正因为 filter/bind 可能在不同副本上执行，节点锁才必须是集群级的分布式锁 （Node 注解 + resourceVersion CAS），进程内 mutex 是不够的。
onDelNode 里的 case cache.DeletedFinalStateUnknown 分支不写会怎样？
A编译不过
B没影响，正常删除总会走 *corev1.Node 分支
C只是日志少一行
Dinformer 断线重连期间发生的节点删除会漏掉，缓存永远清不干净，调度器把 Pod 调到不存在的节点上
当 informer 与 apiserver 的 watch 连接断开又重连时， 断开期间的删除事件拿不到原始对象，client-go 会包一个墓碑 （DeletedFinalStateUnknown）投递过来。
不处理它，nodeName 就是空字符串，五连清理全部失效： 节点锁泄漏、设备清单残留、overviewstatus 里有幽灵节点。
这是 K8s controller 代码审查的必查项， HAMi 的 onDelPod 也有同样的 switch。

10. 小结

  • 三个并发实体：informer 事件循环、15 秒 register 巡检、HTTP 请求处理，共享 podManager 和 overviewstatus。
  • 锁的分工：lock 保护 overviewstatus，allocLock 保护预留账本的三条修改路径， nodeLocks 保护单节点注解读改写，注解锁做跨进程互斥。
  • terminating 的 Pod 仍占卡，informer 重放时必须记账，否则超卖。
  • InitContainer 跑完要收缩用量，把多预留的显存还回去，用幂等标志保证只做一次。
  • synced 放在初始化最后一行；任何中途 return 都不置 true。
  • 只有 leader 做 register，filter/bind 任何副本都可能执行 → 所以必须有分布式锁。
  • 每个 DeleteFunc 都要处理 墓碑（DeletedFinalStateUnknown）。
  • 事件驱动 + 定时全量对账兜底，是 controller 的标准写法。

调度器这一侧到此结束。下一章切换到节点上的设备插件。它怎么把「一张物理卡」上报成「10 张虚拟卡」， 又怎么把 Pod 注解翻译成容器里的环境变量。
