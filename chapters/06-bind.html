第 06 章 · 第二阶段 一个 Pod 的旅程

Bind：把决策落地，以及失败回滚

Filter 已经选好了节点和卡。Bind 要做的是抢锁 → 打标 → 真正绑定， 并且保证任何一步失败都能干净地退回去。 这一章的重点不是「成功路径」，而是那些容易被忽略的失败路径。

学完这章你应该能

  • 说清楚为什么 Filter 已经算过一遍了，Bind 还要再上一把节点锁
  • 画出 Bind 的 6 个步骤和每一步失败时的回滚动作
  • 解释 fail() 闭包为什么返回 (result, nil) 而不是 (nil, err)
  • 说出 bind-phase 注解的三个状态和各自的意义
  • 理解 PodGroup（协同调度）场景下的锁重试机制

1. Bind 在整条链路的位置

Filter 返回唯一节点第 04 章
Pod 注解已写入：vgpu-node、vgpu-devices-to-allocate、vgpu-time
↓kube-scheduler 只剩一个候选，直接调 /bind
Scheduler.Bind()本章
① 从缓存取 Pod → ② 取 Node → ③ 抢所有厂商的节点锁 → ④ 打 bind-phase: allocating → ⑤ 调 K8s Bind API → ⑥ 发 event
↓Pod.spec.nodeName 被写入
kubelet 拉起 Pod第 08 章
调设备插件 Allocate()，读注解 → 注入环境变量 → 释放节点锁
注意：节点锁不是在 Bind 里释放的

Bind 成功后，锁继续持有，一直到设备插件的 Allocate() 执行完 才释放（第 08 章会看到 PodAllocationSuccess）。
为什么？因为真正的资源占用发生在 Allocate 那一刻。 如果 Bind 完就放锁，另一个 Pod 可能在 kubelet 还没来得及调 Allocate 时就抢进来了。
所以锁有 5 分钟超时兜底（NodeLockTimeout），防止设备插件挂了导致死锁。

2. 为什么 Filter 算过了还要锁

网上选座 vs 检票入场

Filter 像网上选座：系统告诉你「3 排 5 座是空的」，并帮你标记了。 但从选座到你真的坐下，中间有时间差。

问题在于 HAMi 的「已占用」是靠本地缓存算出来的（第 04 章）， 而缓存的更新依赖 informer 事件 —— 那是异步的，有延迟。
并发场景：Pod A 和 Pod B 几乎同时被调度到 node-1 的同一张卡。 A 的 Filter 写完注解，但 informer 事件还没回来更新缓存； 这时 B 的 Filter 跑起来，看到的还是「这张卡是空的」→ 超卖。
节点锁就是堵这个窗口的。

3. Bind 全流程

Step 1-2：从缓存取 Pod 和 Node

func (s *Scheduler) Bind(args extenderv1.ExtenderBindingArgs) (*extenderv1.ExtenderBindingResult, error) {
	klog.InfoS("Attempting to bind pod to node", "pod", args.PodName, "namespace", args.PodNamespace, "node", args.Node)
	var res *extenderv1.ExtenderBindingResult

	binding := &corev1.Binding{                                    // K8s 的 Binding 对象
		ObjectMeta: metav1.ObjectMeta{Name: args.PodName, UID: args.PodUID},
		Target:     corev1.ObjectReference{Kind: "Node", Name: args.Node},
	}

	current, err := s.podLister.Pods(args.PodNamespace).Get(args.PodName)
	if err != nil {
		klog.ErrorS(err, "Failed to get pod from cache", "pod", args.PodName, "namespace", args.PodNamespace)
		s.cleanupStalePodAllocation(&corev1.Pod{                   // 回滚：撤销 Filter 的记账
			ObjectMeta: metav1.ObjectMeta{
				UID:       args.PodUID,
				Name:      args.PodName,
				Namespace: args.PodNamespace,
			},
		})
		return &extenderv1.ExtenderBindingResult{Error: err.Error()}, err
	}

	klog.InfoS("Trying to get the target node for pod", "pod", args.PodName, "namespace", args.PodNamespace, "node", args.Node)

	node, err := s.nodeLister.Get(args.Node)
	if err != nil {
		klog.ErrorS(err, "Failed to get node from cache", "node", args.Node)
		s.recordScheduleBindingResultEvent(current, EventReasonBindingFailed, []string{}, fmt.Errorf("failed to get node %s", args.Node))
		s.cleanupStalePodAllocation(current)                       // 回滚
		res = &extenderv1.ExtenderBindingResult{Error: err.Error()}
		return res, nil
	}
cleanupStalePodAllocation。撤销 Filter 留下的账
func (s *Scheduler) cleanupStalePodAllocation(pod *corev1.Pod) {
	if pi, ok := s.podManager.TakeAndDeletePod(pod); ok && len(pi.Devices) > 0 {
		s.quotaManager.RmUsage(pod, pi.Devices)
	}
}

记得第 04 章 Filter 的 Step 6 吗？它在选中节点后就 AddPod + AddUsage 了。 如果 Bind 阶段发现 Pod 已经不存在（被用户删了），那笔账必须撤掉，否则 资源会被一个不存在的 Pod 永久占着。这类 bug 叫「资源泄漏」， 表现是「明明没跑什么任务，却调度不上去了」。

Step 3：fail 闭包：统一的回滚出口

	tmppatch := map[string]string{
		util.DeviceBindPhase:     "allocating",
		util.BindTimeAnnotations: strconv.FormatInt(time.Now().Unix(), 10),
	}

	fail := func(e error) (*extenderv1.ExtenderBindingResult, error) {
		klog.InfoS("Release node locks", "node", args.Node)
		s.releaseAllDevices(node, current)                        // 释放所有已抢到的锁
		s.recordScheduleBindingResultEvent(current, EventReasonBindingFailed, []string{}, e)
		errStr := ""
		if e != nil {
			errStr = e.Error()
		}
		return &extenderv1.ExtenderBindingResult{Error: errStr}, nil   // ← 注意：err 位是 nil
	}
return result, nil 而不是 return nil, err。这是有意的

Go 的惯例是出错就返回 error。但这里故意把错误装进结果结构体，第二个返回值给 nil。

原因在 HTTP 层（）： 如果 Bind() 返回非 nil 的 error，路由会再包一层覆盖掉结果； 而 K8s extender 协议期望的是「HTTP 200 + body 里的 Error 字段」， 这样 kube-scheduler 才能正确识别为「绑定失败，请重新调度」而不是「扩展器故障」。
返回 (nil, err) 会让 kube-scheduler 的重试行为变得不可预期。
读代码时看到「反直觉的返回值」，先去看调用方怎么处理的，往往能找到原因。

抢锁要抢所有厂商的，而且失败要按逆序回滚：

func (s *Scheduler) lockAllDevices(node *corev1.Node, pod *corev1.Pod) error {
	devs := device.GetDevices()
	keys := make([]string, 0, len(devs))
	for k := range devs {
		keys = append(keys, k)
	}
	sort.Strings(keys)                                     // 固定顺序！

	acquired := make([]device.Devices, 0, len(keys))
	for _, k := range keys {
		val := devs[k]
		if err := val.LockNode(node, pod); err != nil {
			for _, locked := range slices.Backward(acquired) {           // 逆序释放
				if relErr := locked.ReleaseNodeLock(node, pod); relErr != nil {
					klog.ErrorS(relErr, "Failed to release node lock during rollback", "node", node.Name, "pod", klog.KObj(pod))
				}
			}
			return err
		}
		acquired = append(acquired, val)
	}
	return nil
}
sort.Strings(keys)。一行代码防死锁

Go 的 map 遍历顺序是随机的。如果不排序，两个并发的 Bind 可能是： 

Pod A 的 Bind：先锁 NVIDIA → 再锁 MLU
Pod B 的 Bind：先锁 MLU    → 再锁 NVIDIA

时刻 1：A 拿到 NVIDIA，B 拿到 MLU
时刻 2：A 等 MLU（B 持有），B 等 NVIDIA（A 持有）
        ↓
     经典的 ABBA 死锁

固定加锁顺序是解决 ABBA 死锁的标准方法， 这行 sort.Strings 就是干这个的。
（HAMi 的多厂商锁实际都指向同一个注解 key hami.io/mutex.lock， 所以这里更多是防御性写法。）

4. 节点锁：用注解实现的分布式锁

HAMi 没用 Lease、没用 etcd 的事务，就用了一条 Node 注解： 

const (
	NodeLockKey = "hami.io/mutex.lock"
	NodeLockSep = ","
)

注解的值格式是「时间戳,命名空间,Pod 名」：

func GenerateNodeLockKeyByPod(pod *corev1.Pod) string {
	if pod == nil {
		return time.Now().Format(time.RFC3339)
	}
	return fmt.Sprintf("%s%s%s", time.Now().Format(time.RFC3339), NodeLockSep, GeneratePodNamespaceName(pod, NodeLockSep))
}

func GeneratePodNamespaceName(pod *corev1.Pod, sep string) string {
	if pod == nil {
		return ""
	}
	return fmt.Sprintf("%s%s%s", pod.Namespace, sep, pod.Name)
}

4.1 LockNode 的四个分支

func LockNode(nodeName string, lockname string, pods *corev1.Pod) error {
	if pods == nil {
		return fmt.Errorf("cannot lock node: pod is nil")
	}
	...
	// Acquire per-node lock instead of global lock
	nodeLock := nodeLocks.getLock(nodeName)      // ← 先拿进程内的 mutex
	nodeLock.Lock()
	defer nodeLock.Unlock()

	ctx := context.Background()
	node, err := client.GetClient().CoreV1().Nodes().Get(ctx, nodeName, metav1.GetOptions{})
	if err != nil {
		return err
	}
	if _, ok := node.Annotations[NodeLockKey]; !ok {
		return setNodeLockLocked(nodeName, lockname, pods)    // 【分支 1】没锁 → 直接上锁
	}
	lockTime, ns, previousPodName, err := ParseNodeLock(node.Annotations[NodeLockKey])
	if err != nil {
		return err
	}

	var skipOwnerCheck = false
	if time.Since(lockTime) > NodeLockTimeout {
		klog.InfoS("Node lock expired", "node", nodeName, "lockTime", lockTime, "timeout", NodeLockTimeout)
		skipOwnerCheck = true                                 // 【分支 2】锁过期 → 强行抢
	} else if ns == pods.Namespace && previousPodName == pods.Name {
		// The lock is already held by this exact pod. lockAllDevices calls
		// LockNode once per device vendor a pod requests resources from, so
		// a pod requesting resources from two or more vendors (e.g. both
		// nvidia.com/gpu and cambricon.com/vmlu) would otherwise contend
		// with its own still-valid lock on the second call and never
		// become schedulable. Treat this as already acquired.
		klog.V(4).InfoS("Node lock already held by this pod, treating as acquired", "node", nodeName, "podName", pods.Name)
		return nil                                            // 【分支 3】就是我自己 → 可重入
	} else if ns != "" && previousPodName != "" {
		// Check dangling nodeLock
		if _, err := client.GetClient().CoreV1().Pods(ns).Get(ctx, previousPodName, metav1.GetOptions{}); err != nil {
			if !apierrors.IsNotFound(err) {
				klog.ErrorS(err, "Failed to get pod of NodeLock", "podName", previousPodName, "namespace", ns)
				return err
			}
			klog.InfoS("Previous pod of NodeLock not found, releasing lock", ...)
			skipOwnerCheck = true                             // 【分支 4】持锁者已消失 → 抢
		}
	}

	if skipOwnerCheck {
		err = releaseNodeLockLocked(nodeName, lockname, pods, true)
		if err != nil {
			klog.ErrorS(err, "Failed to release node lock", "node", nodeName)
			return err
		}
		return setNodeLockLocked(nodeName, lockname, pods)
	}

	return fmt.Errorf("node %s has been locked within %v: %w", nodeName, NodeLockTimeout, ErrNodeLockContention)
}
分支 3 的注释解释了一个真实 bug

一个 Pod 同时要 NVIDIA GPU 和寒武纪 MLU 时，lockAllDevices 会调 LockNode 两次（每个厂商一次）。 第二次调用时锁已经被自己持有了 —— 如果没有分支 3， 它会跟自己竞争，永远调度不上去。
这就是可重入锁的必要性。注释里把这个场景写得很清楚， 说明这是踩过坑之后补上的。

4.2 两层锁：进程内 mutex + 集群级注解

// nodeLockManager manages locks on a per-node basis to allow concurrent
// operations on different nodes while maintaining mutual exclusion for
// operations on the same node.
type nodeLockManager struct {
	mu    sync.Mutex
	locks map[string]*sync.Mutex     // 每个节点一把进程内 mutex
}
...
// getLock returns the mutex for a specific node, creating it if necessary.
// This method is thread-safe.
func (m *nodeLockManager) getLock(nodeName string) *sync.Mutex {
	m.mu.Lock()
	defer m.mu.Unlock()

	if _, ok := m.locks[nodeName]; !ok {
		m.locks[nodeName] = &sync.Mutex{}
	}
	return m.locks[nodeName]
}

注解锁的写入用了 resourceVersion 乐观锁 + 重试：

func setNodeLockLocked(nodeName string, lockname string, pods *corev1.Pod) error {
	ctx := context.Background()
	node, err := client.GetClient().CoreV1().Nodes().Get(ctx, nodeName, metav1.GetOptions{})
	if err != nil {
		return err
	}
	if _, ok := node.Annotations[NodeLockKey]; ok {
		return fmt.Errorf("node %s is locked: %w", nodeName, ErrNodeLockContention)
	}
	lockOwner := NodeLockSep + GeneratePodNamespaceName(pods, NodeLockSep)
	err = retry.OnError(DefaultStrategy, func(err error) bool {
		return !IsNodeLockContention(err)                  // 竞争不重试，其他错误才重试
	}, func() error {
		node, err = client.GetClient().CoreV1().Nodes().Get(ctx, nodeName, metav1.GetOptions{})
		if err != nil {
			klog.ErrorS(err, "Failed to get node when retry to patch", "node", nodeName)
			return err
		}
		lockStr, ok := node.Annotations[NodeLockKey]
		if ok && strings.Contains(lockStr, NodeLockSep) && strings.HasSuffix(lockStr, lockOwner) {
			return nil                                     // 已经是我的锁了，幂等返回
		}
		if ok {
			return fmt.Errorf("node %s is locked: %w", nodeName, ErrNodeLockContention)
		}
		patchData := fmt.Sprintf(`{"metadata":{"annotations":{"%s":"%s"},"resourceVersion":"%s"}}`, NodeLockKey, GenerateNodeLockKeyByPod(pods), node.ResourceVersion)
		_, err = client.GetClient().CoreV1().Nodes().Patch(ctx, nodeName, types.MergePatchType, []byte(patchData), metav1.PatchOptions{})
		...
	})
	...
}
resourceVersion 在 patch 里的作用

把读到的 resourceVersion 一起写进 patch，apiserver 会检查 「这个对象自你读取之后有没有被别人改过」。改过就返回 409 Conflict， retry.OnError 重新读一遍再试。
这就是 Compare-And-Swap，只不过用 HTTP 实现的。
重试策略在 ： 5 次，100ms 起步，指数退避 2 倍，带 0.5 抖动。

5. PodGroup 场景：为什么需要重试等待

协同调度（Gang Scheduling）场景下，一批 Pod 必须要么全部调度成功，要么全部失败。 比如一个 8 卡的分布式训练任务，拆成 8 个 Pod。

问题：同一个 PodGroup 的成员会互相抢锁

如果 8 个 Pod 都要调度到同一个节点，它们会依次去抢同一把节点锁。 第 1 个抢到，第 2~8 个直接失败返回 —— 然后整个 PodGroup 调度失败， 下一轮又是同样的结果，永远起不来。 

func (s *Scheduler) acquireNodeLocks(node *corev1.Node, pod *corev1.Pod) error {
	if !util.IsPodGroupMember(pod) || config.NodeLockRetryTimeout <= 0 {
		return s.lockAllDevices(node, pod)                    // 普通 Pod：抢不到就失败
	}

	deadline := time.Now().Add(config.NodeLockRetryTimeout)

	for {
		err := s.lockAllDevices(node, pod)
		if err == nil {
			return nil
		}
		if !nodelockutil.IsNodeLockContention(err) {
			return err                                        // 不是竞争导致的错误 → 立即失败
		}
		if time.Now().After(deadline) {
			return fmt.Errorf("timed out after %v waiting for node %s to be unlocked: %w",
				config.NodeLockRetryTimeout, node.Name, nodelockutil.ErrNodeLockContention)
		}
		select {
		case <-s.stopCh:
			return fmt.Errorf("scheduler shutting down while waiting for node lock: %w", nodelockutil.ErrNodeLockContention)
		case <-time.After(100 * time.Millisecond):            // 等 100ms 再试
		}
	}
}
这里有个必须注意的配置耦合

NodeLockRetryTimeout 默认 28 秒 （见 ）。 那条 flag 的帮助文本明确说了： 「Align the Extender's httpTimeout in KubeSchedulerConfiguration with this value.」
如果 kube-scheduler 那边的 httpTimeout 小于 28 秒， 它会在 HAMi 还在等锁时就超时断开，然后重新发起调度，前面的等待白费。
部署时这是个真实的坑。Helm chart 里两个值应该是配套的。

6. bind-phase 状态机

值谁写的含义
allocating调度器 Bind已抢到锁，正在绑定；设备插件用它来找「该给谁分配」
success设备插件 Allocate环境变量已注入，锁已释放
failed设备插件 Allocate分配失败，锁已释放，Pod 需要重新调度
allocating 是设备插件的「寻人启事」

第 08 章会看到，设备插件的 Allocate() 收到 kubelet 请求时， 并不知道这是给哪个 Pod 的（gRPC 请求里只有设备 ID，没有 Pod 信息）。 它是靠 getPendingPod(nodename) 去找「本节点上 bind-phase=allocating 且时间最早的那个 Pod」。
这是整个协议里最脆弱的一环：如果两个 Pod 同时处于 allocating 状态， 就可能张冠李戴。节点锁的存在正是为了保证同一时刻只有一个 Pod 处于 allocating。

9. 本章自测

Filter 阶段已经算过资源了，为什么 Bind 还要抢节点锁？
A为了防止节点被其他管理员 drain
BK8s Bind API 要求必须持有锁
CFilter 的用量来自本地缓存，而缓存靠异步的 informer 事件更新，有延迟窗口会导致并发超卖
D为了给 vGPUmonitor 发信号
Pod A 的 Filter 写完注解后，informer 事件要过一会儿才会更新 podManager 缓存。这个窗口期内，Pod B 的 Filter 看到的还是旧账本， 会把同一张卡的同一份显存再分一次。
节点锁把「从 Bind 开始到设备插件 Allocate 完成」这一整段变成临界区， 保证同一时刻只有一个 Pod 在这个节点上落地。
lockAllDevices 里那行 sort.Strings(keys) 是干什么的？
A固定加锁顺序，防止多个 Bind 之间形成 ABBA 死锁
B让日志输出更整齐
C保证 NVIDIA 优先被处理
D提升 map 遍历性能
Go 的 map 遍历顺序是随机的。如果 Pod A 按「NVIDIA→MLU」的顺序加锁， Pod B 按「MLU→NVIDIA」，就可能各持一把、互相等待，形成经典的 ABBA 死锁。 所有并发路径按同一个固定顺序获取多把锁，是解决这类死锁的标准方法。
注意后面的回滚是 slices.Backward(acquired)。逆序释放， 这也是配套的规范做法。

A为了性能优化
B一个 Pod 同时申请多家厂商资源时，lockAllDevices 会调 LockNode 多次，不可重入的话它会跟自己竞争，永远调度不上去

代码里那段长注释写得很明白：一个同时要 nvidia.com/gpu 和 cambricon.com/vmlu 的 Pod，会触发两次 LockNode。 第二次时锁已经被自己持有 —— 如果判定为竞争失败，这个 Pod 永远无法完成绑定。
所以这里实现了可重入锁。从注释的详细程度看，这是修复某个真实 issue 时补上的。
Bind 成功之后，节点锁什么时候释放？
ABind 函数返回前立即释放
BPod 变成 Running 时
C永远不释放，只靠 5 分钟超时
D设备插件的 Allocate() 执行完之后（成功或失败都释放），5 分钟超时是兜底
真正的资源占用发生在设备插件注入环境变量的那一刻。 Bind 只是写了 spec.nodeName，kubelet 还要过一会儿才会调 Allocate()。 这中间如果放锁，另一个 Pod 可能抢先占用。
第 08 章会看到设备插件里的 PodAllocationSuccess / PodAllocationFailed， 它们负责释放锁。NodeLockTimeout（默认 5 分钟）是防止设备插件挂掉导致永久死锁的兜底。

10. 小结

  • Bind 的价值不在「绑定」这个动作本身，而在 抢锁 和 失败回滚。
  • 锁的生命周期是 Bind 开始 → 设备插件 Allocate 结束，跨越了两个进程，靠 5 分钟超时兜底。
  • 多厂商加锁必须 固定顺序（sort）+ 逆序回滚，防 ABBA 死锁。
  • 节点锁是两层：进程内每节点一把 mutex + 集群级注解 CAS（resourceVersion 乐观锁）。
  • 锁可重入（同一 Pod 多次加锁）、可抢占（超时 或 持锁 Pod 已消失）。
  • PodGroup 成员会重试等锁，超时时间必须和 kube-scheduler 的 httpTimeout 对齐。
  • fail() 返回 (result, nil) 是为了让 kube-scheduler 正确识别「绑定失败」而非「扩展器故障」。
