Filter：调度器扩展器主流程

kube-scheduler 把一批候选节点丢过来问「哪些能用」。 HAMi 的回答方式很特别：它不返回「一批能用的节点」，而是直接返回「一个最优节点」， 并且顺手把「用哪几张卡」写进了 Pod 注解。这一章拆解这个过程。

学完这章你应该能

  • 画出 /filter 从 HTTP 进来到返回的完整调用链
  • 解释「为什么 HAMi 的 Filter 只返回一个节点」以及这个设计的代价
  • 说清楚 NodeInfo（静态）怎么 + Pod 缓存 = NodeUsage（动态）
  • 解释 overviewstatus 缓存、informer 事件、allocLock 三者的关系
  • 找到「分配失败原因」是怎么变成 Pod event 给用户看的

2. HTTP 层：三件小事，但都不能省

func PredicateRoute(s *scheduler.Scheduler) httprouter.Handle {
	klog.Infoln("Initializing Predicate Route")
	return func(w http.ResponseWriter, r *http.Request, _ httprouter.Params) {
		klog.V(5).Infoln("Entering Predicate Route handler")
		if !checkBody(w, r) {
			return
		}

		var buf bytes.Buffer
		// Limit the body size to prevent deep nesting/resource exhaustion attacks
		limitedReader := io.LimitReader(r.Body, maxRequestSize)     // ① 限制 body 大小
		body := io.TeeReader(limitedReader, &buf)

		var extenderArgs extenderv1.ExtenderArgs
		var extenderFilterResult *extenderv1.ExtenderFilterResult

		if err := json.NewDecoder(body).Decode(&extenderArgs); err != nil {
			klog.ErrorS(err, "Failed to decode extender arguments")
			extenderFilterResult = &extenderv1.ExtenderFilterResult{
				Error: err.Error(),
			}
		} else if extenderArgs.Pod == nil {                          // ② Pod 不能为空
			err := fmt.Errorf("extender args missing pod")
			klog.ErrorS(err, "Rejecting filter request with no pod")
			extenderFilterResult = &extenderv1.ExtenderFilterResult{
				Error: err.Error(),
			}
		} else {
			synced := s.WaitForCacheSync(r.Context())                // ③ 等缓存同步（关键！）
			if !synced {
				// Poll may return false when context is cancelled
				err := fmt.Errorf("context cancelled")
				klog.ErrorS(err, "Cache not synced, cannot proceed with filtering")
				extenderFilterResult = &extenderv1.ExtenderFilterResult{
					Error: err.Error(),
				}
			} else {
				extenderFilterResult, err = s.Filter(extenderArgs)   // 进主流程
				...
			}
		}
		...
	}
}
WaitForCacheSync 为什么是关键

调度器刚启动时，overviewstatus 缓存是空的（还没跑完第一轮节点注册）。 如果这时来了 filter 请求，它会看到「所有节点都没有 GPU」，然后 把所有节点都判成不合格，Pod 就被误判为不可调度。
所以必须先阻塞等缓存就绪。synced 是在 register() 的最后一行 才置为 true 的（见 ）， 保证「置 true 时缓存一定是完整的」。

Step 1：这个 Pod 关我事吗？

func (s *Scheduler) Filter(args extenderv1.ExtenderArgs) (*extenderv1.ExtenderFilterResult, error) {
	klog.InfoS("Starting schedule filter process", "pod", args.Pod.Name, "uuid", args.Pod.UID, "namespace", args.Pod.Namespace)
	resourceReqs := device.Resourcereqs(args.Pod)          // 翻译成 PodDeviceRequests

	hasHAMiResource := false
	for _, reqMap := range resourceReqs {
		if len(reqMap) > 0 {
			hasHAMiResource = true
			break
		}
	}

	if !hasHAMiResource {
		klog.V(1).InfoS("Pod does not request any resources", "pod", args.Pod.Name)
		// Simulation callers such as the cluster autoscaler send Nodes
		// instead of NodeNames; echo both back so a pod without HAMi
		// resources keeps every candidate node on either protocol shape.
		return &extenderv1.ExtenderFilterResult{
			Nodes:       args.Nodes,        // ← 原样退回，两种协议形态都回
			NodeNames:   args.NodeNames,
			FailedNodes: nil,
			Error:       "",
		}, nil
	}
注意「两种协议形态」

K8s 的 extender 协议有两种传节点的方式：NodeNames（只传名字，轻量）和 Nodes（传完整 Node 对象）。取决于 KubeSchedulerConfiguration 里的 nodeCacheCapable 设置。
Cluster Autoscaler 做扩容模拟时用的是 Nodes， 因为那些节点还不存在于集群中，只有名字没用。 所以 HAMi 必须两种都支持 —— 下一步就分叉了。

为什么要先删自己

Filter 可能对同一个 Pod 被调用多次（调度失败重试、抢占后重调度）。 如果不先把上一次的记账撤销，这个 Pod 会「自己占自己的资源」， 导致第二次怎么算都放不下。
TakeAndDeletePod 是「取出并删除」的原子操作 —— 见 。

Step 4：算出每个节点的当前用量：本章的技术核心

这是整个 Filter 里最有意思的一段。它要回答： 「节点 A 上那张 GPU，现在还剩多少显存？」

注意：HAMi 不去问 GPU 本身（那太慢，而且会有时序问题）。 它是算出来的： 

节点当前用量 = 节点静态设备清单（DeviceInfo，Used 全为 0）
              + Σ 所有已调度到该节点的 Pod 的分配记录

第一步，从静态清单铺出一张空白账本，所有用量字段都是 0：

func buildNodeUsage(node *device.NodeInfo, task *corev1.Pod) *NodeUsage {
	userGPUPolicy := util.GetGPUSchedulerPolicyByPod(device.GPUSchedulerPolicy, task)
	nodeUsage := &NodeUsage{
		Node:     node.Node,
		NodeInfo: node,
		Devices: policy.DeviceUsageList{
			Policy:      userGPUPolicy,                        // 这个 Pod 想要的选卡策略
			NumaBind:    numaBindingRequested(task),
			DeviceLists: make([]*policy.DeviceListsScore, 0),
		},
	}
	for _, vendorDevices := range node.Devices {
		for _, d := range vendorDevices {
			nodeUsage.Devices.DeviceLists = append(nodeUsage.Devices.DeviceLists, &policy.DeviceListsScore{
				Score: 0,
				Device: &device.DeviceUsage{
					ID:          d.ID,
					Index:       d.Index,
					Used:        0,                            // ← 全部从 0 开始
					Count:       d.Count,
					Usedmem:     0,                            // ←
					Totalmem:    d.Devmem,
					Totalcore:   d.Devcore,
					Usedcores:   0,                            // ←
					MigProfiles: d.MIGProfiles,
					Mode:        d.Mode,
					Type:        d.Type,
					Numa:        d.Numa,
					Health:      d.Health,
					PodInfos:    make([]*device.PodInfo, 0),
					CustomInfo:  maps.Clone(d.CustomInfo),
				},
			})
		}
	}
	return nodeUsage
}

第二步，遍历本地 Pod 缓存，把每个 Pod 占的资源加回去：

func (s *Scheduler) getNodesUsage(nodes *[]string, task *corev1.Pod) (*map[string]*NodeUsage, *map[string]*NodeUsage, map[string]string, error) {
	overallnodeMap := make(map[string]*NodeUsage)
	cachenodeMap := make(map[string]*NodeUsage)
	failedNodes := make(map[string]string)
	allNodes, err := s.ListNodes()
	if err != nil {
		return &overallnodeMap, &overallnodeMap, failedNodes, err
	}

	for _, node := range allNodes {
		overallnodeMap[node.ID] = buildNodeUsage(node, task)      // ① 空白账本
	}

	podsInfo := s.podManager.ListPodsInfo()                       // ② 所有已调度 Pod
	for _, p := range podsInfo {
		...
		node, ok := overallnodeMap[p.NodeID]
		if !ok {
			klog.V(5).InfoS("pod allocated unknown node resources", ...)
			continue
		}
		for _, podsingleds := range p.Devices {                    // 遍历厂商
			for _, ctrdevs := range podsingleds {                 // 遍历容器
				for _, udevice := range ctrdevs {                 // 遍历卡
					matched := false
					for _, d := range node.Devices.DeviceLists {
						deviceID := udevice.UUID
						if d.Device.ID == deviceID {              // 按 UUID 对上号
							matched = true
							// Raw entries carry no slot count; clamp to at least one.
							slots := max(udevice.Slots, 1)
							d.Device.Used      += slots           // 记账
							d.Device.Usedmem   += udevice.Usedmem
							d.Device.Usedcores += udevice.Usedcores
							d.Device.PodInfos  = append(d.Device.PodInfos, p)
							...
						}
					}
					if !matched {
						klog.ErrorS(nil, "pod allocated unknown or stale device resources", ...)
					}
				}
			}
		}
	}
	...
}
用量重建可视化互动

增删「已调度的 Pod」，看节点上两张卡的用量怎么被一步步累加出来。

这个设计的三个后果，都很重要
  1. 本地缓存必须准确。如果 podManager 漏掉一个 Pod， 那个 Pod 占的显存就「凭空消失」了 → 超卖。 所以 informer 的 add/update/delete 回调（） 必须严丝合缝，第 07 章专门讲。
  2. UUID 对不上会静默丢失。看那个 if !matched 分支 —— 只打了一条 error 日志。如果 GPU 被换了导致 UUID 变了， 旧 Pod 的占用就统计不到。
  3. 缓存是全量重建的，不是增量。每次 Filter 都把所有节点、所有 Pod 重算一遍。 节点多的时候这是热点 —— 项目里有专门的 benchmark （）在盯这块。

取的是最后一个，不是第一个

sort.Sort 是升序，然后取 [len-1]，也就是排序后最大的那个。 但「最大」是什么意思取决于 Less() 怎么定义： 

func (l NodeScoreList) Less(i, j int) bool {
	if l.Policy == util.NodeSchedulerPolicySpread.String() {
		return l.NodeList[i].Score > l.NodeList[j].Score      // spread：分数低的排后面
	}
	// default policy is Binpack
	return l.NodeList[i].Score < l.NodeList[j].Score          // binpack：分数高的排后面
}

分数代表「这个节点有多满」。所以： binpack 要挑最满的（分数最高）→ 升序排完取末尾； spread 要挑最空的（分数最低）→ 反过来排，末尾就是最空的。 一个 Less 反转，两种策略都搞定。

「先本地后远程 + 失败回滚」的顺序很讲究

为什么不先写 apiserver 再记本地？因为写 apiserver 是慢操作， 期间可能有另一个 Filter 请求进来（虽然有 allocLock，但 informer 事件是异步的）。 先在本地占坑，能保证账本的连续性。
写失败时严格逆序回滚：先撤配额，再撤 Pod 记录。 这个「本地先行 + 失败补偿」的模式在 Bind 里还会看到一次（第 06 章）。

为什么只返回一个节点：HAMi 最重要的架构决策

标准的 extender 语义是「Filter 返回一批可行节点，然后 Prioritize 打分排序」。 HAMi 把这两步合并进 Filter 一步做完，只返回冠军。

为什么必须这样？

因为 HAMi 要分配的不只是「节点」，还有「节点上的哪几张卡」。 判断「这个节点能不能放下」的过程本身就是在选卡（Fit()）。 如果 Filter 只返回一批节点，那么 Prioritize 阶段还得再算一遍选卡； 更糟的是 kube-scheduler 最终选了哪个节点，扩展器要等到 Bind 才知道， 那时才写注解就太晚了（有并发窗口）。
所以 HAMi 干脆在 Filter 里就把节点和卡一起定了，直接写进注解。

这个决策的代价
  • kube-scheduler 的 Prioritize / Score 插件对 GPU Pod 基本失效， 因为只剩一个候选，怎么打分都是它。你在 KubeSchedulerConfiguration 里配的 NodeResourcesBalancedAllocation 之类对 GPU Pod 不起作用。
  • 抢占（Preemption）行为会变怪，因为可行节点集合被人为缩小到 1。
  • Filter 变成了有副作用的操作（写注解、改缓存）， 而 K8s 假设 Filter 是幂等只读的。这就是为什么 Step 3 必须先 TakeAndDeletePod 自我清理。

4. 失败原因怎么传给用户

Pod 一直 Pending 时，用户 kubectl describe pod 看到的那行原因，是从这里来的： 

func genSuccessMsg(totalNodes int, target string, nodes []*policy.NodeScore) string {
	successMsg := "find fit node(%s), %d nodes not fit, %d nodes fit(%s)"
	var scores []string
	for _, no := range nodes {
		scores = append(scores, fmt.Sprintf("%s:%.2f", no.NodeID, no.Score))
	}
	score := strings.Join(scores, ",")
	return fmt.Sprintf(successMsg, target, totalNodes-len(nodes), len(nodes), score)

失败时的聚合更有意思，它把「同一种原因」的节点归到一起：

func (s *Scheduler) recordFilteringFailures(task *corev1.Pod, failureReason map[string][]string) {
	for reasonType, failureNodes := range failureReason {
		sort.Strings(failureNodes)
		reason := fmt.Errorf("%d nodes %s(%s)", len(failureNodes), reasonType, strings.Join(failureNodes, ","))
		s.recordScheduleFilterResultEvent(task, EventReasonFilteringFailed, "", reason)
	}
}

6. 本章自测

HAMi 的 Filter 为什么只返回一个节点，而不是一批可行节点？
A为了减少 HTTP 响应体大小
BK8s extender 协议规定只能返回一个
C判断「能否放下」的过程本身就是在选卡，选完必须立刻写注解锁定，否则有并发窗口
D因为 HAMi 不支持多节点集群
HAMi 要分配的粒度是「节点 + 具体哪几张卡」。 Fit() 在判断可行性的同时就产出了分配方案， 如果返回一批节点让 kube-scheduler 自己挑，那扩展器要到 Bind 才知道结果， 中间的窗口期里其他 Pod 可能已经占走了那些卡。
代价是：kube-scheduler 的打分插件对 GPU Pod 基本失效， 而且 Filter 变成有副作用的操作（违反 K8s 的幂等假设）。
节点上某张 GPU 的 Usedmem 是怎么得到的？
A设备插件通过 NVML 读实际显存占用，写进 Node 注解
B从 0 开始，遍历本地缓存里所有已调度到该节点的 Pod，把它们的分配值累加
C调用 kubelet 的 metrics 接口
D从 vGPUmonitor 的 Prometheus 指标读
见 buildNodeUsage（scheduler.go:683，全部置 0） + getNodesUsage（scheduler.go:773，遍历 podManager 累加）。
用的是「调度器承诺分配了多少」，不是「实际用了多少」。这是资源调度的标准做法（跟 CPU/内存的 Requests 一个道理）。 A 描述的是静态能力清单（总量），不是用量。D 那个数据只用于监控展示，不参与调度。
为什么 Filter 一开始要先调 TakeAndDeletePod(args.Pod)？
AFilter 可能对同一 Pod 调用多次，不先撤销旧记账会「自己占自己的资源」
B为了释放内存
C为了触发 informer 的删除事件
D为了让 Pod 重新排队
调度失败重试、抢占后重调度都会让同一个 Pod 再次进 Filter。 第一次已经在 Step 6 里 AddPod 记过账了， 第二次 getNodesUsage 会把这笔账算进「节点已用量」， 于是 Pod 需要的资源被自己占着，怎么算都不够。
这是「Filter 有副作用」这个设计带来的必要补偿。
sort.Sort(nodeScores) 之后取 NodeList[len-1]，在 spread 策略下选中的是？
A分数最高的节点（最满的）
B第一个可行的节点
C随机一个
D分数最低的节点（最空的）
看 NodeScoreList.Less()（node_policy.go:48）： spread 策略下 Less(i,j) 返回 Score[i] > Score[j]， 也就是降序排列，末尾自然是分数最低的。
分数含义是「这个节点有多满」（ComputeDefaultScore 算的是已用/总量的比例）。 spread 要把负载摊开，所以挑最空的。 两种相反的策略靠同一个 Less 反转实现。

7. 小结

  • Filter 的 7 步：判断是否相关 → 模拟分支 → 清旧账 → 重建用量 → 并发打分 → 写注解记账 → 返回唯一节点。
  • HTTP 层必须 WaitForCacheSync，否则冷启动时会把所有节点误判为无 GPU。
  • 节点用量是算出来的：静态清单（全 0）+ Σ 本地缓存里所有已调度 Pod 的分配值。
  • 只返回一个节点是 HAMi 最重要的架构决策 —— 因为选卡和判可行性是同一件事。 代价是 kube-scheduler 的打分插件失效、Filter 有副作用。
  • 写注解先本地后远程，失败逆序回滚。
  • 失败原因经 GenReason/ParseReason 聚合后写成 Pod event，格式必须严格对齐。
