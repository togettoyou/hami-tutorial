2. 注解速查

2.1 Node 注解

Key谁写值 / 含义
hami.io/node-nvidia-register设备插件 JSON（MarshalNodeDevices）：
[{"id","index","count","devmem","devcore","type","numa","mode","migProfiles","health"}]
每个字段都带 omitempty，零值 key 会整个消失
同格式：amd / ascend / biren / kunlun-vdevice / vastai
hami.io/node-hygon-register
hami.io/node-iluvatar-register		设备插件 逗号串（DecodeNodeDevices）：
{UUID},{Count},{Devmem},{Devcore},{Type},{Numa},{Health}[,{Index},{Mode}]，卡间用 :
接受 7 或 9 字段；Type 里不能有逗号（无转义）
hami.io/node-handshake双方 Requesting_{ts}（调度器点名）/ Reported {ts}（插件答到）。60 秒超时
hami.io/node-nvidia-score设备插件 卡间 NVLink pair score，JSON。需 ENABLE_TOPOLOGY_SCORE=true
hami.io/mutex.lock调度器 节点锁：{RFC3339时间},{namespace},{podName}。默认 5 分钟超时
hami.io/device-cordon运维手动 逗号分隔的 UUID，把这些卡排除出新分配（已跑的不受影响）

2.2 Pod 注解（调度器写）

Key值 / 含义
hami.io/vgpu-devices-to-allocate 「工单」：{UUID},{Type},{Usedmem},{Usedcores}:…;…
: 分设备，; 分容器。设备插件消费后擦除
hami.io/vgpu-devices-allocated同上内容，永久留档，调度器账本和监控读它
hami.io/vgpu-node选中的节点名
hami.io/vgpu-time分配时间戳（Unix 秒）
hami.io/bind-phaseallocating → success / failed
hami.io/bind-timeBind 开始时间

2.3 Pod 注解（用户写，调整行为）

Key可选值
hami.io/node-scheduler-policybinpack（默认，挑最满）/ spread（挑最空）
hami.io/gpu-scheduler-policy binpack / spread / topology-aware / mutex / numa
可逗号串联做排序键链，如 numa,binpack。
mutex 和 topology-aware 是过滤器不是排序键
hami.io/device-scoring-weights如 slot=1,core=2,memory=3。只作用于卡级打分
hami.io/numa-alignmentNUMA 对齐模式，非法值在 webhook 就被拒
nvidia.com/use-gputype / nouse-gputype按型号白/黑名单
nvidia.com/use-gpuuuid / nouse-gpuuuid按 UUID 白/黑名单
nvidia.com/numa-bindtrue = 多卡必须同 NUMA
nvidia.com/vgpu-modehami-core / mig

4. 调度失败原因

格式：{数量}/{总卡数} {原因}，多个用 , 连接。 生成/解析在 。

原因含义 / 用户该怎么办
CardNotHealth卡不健康。查设备插件日志 / nvidia-smi
CardCordoned被 hami.io/device-cordon 排除了
CardTypeMismatch型号不匹配 use-gputype
CardUuidMismatchUUID 不匹配 use-gpuuuid

CardTimeSlicingExhausted切分份数用完（Used >= Count）。调大节点的 deviceSplitCount
CardInsufficientMemory最常见。剩余显存不够。降低 gpumem 或等释放
CardInsufficientCore剩余算力不够，或 gpucores 超出 0-100
CardComputeUnitsExhausted算力已被预定完，不能再放 gpucores: 0 的任务
ExclusiveDeviceAllocateConflict要独占（gpucores:100 或 mutex 策略）但卡上有人
ResourceQuotaNotFit超命名空间 ResourceQuota
CardMigTopologyInfeasibleMIG 模式下找不到可用 placement
CardNotFoundCustomFilterRule后端自定义规则拒绝
NodeInsufficientDevice节点上该类型的卡总数就不够
AllocatedCardsInsufficientRequest凑到了一部分卡但不够数
ModeNotFit请求的 mode 和卡的 mode 不匹配

8. 关键设计决策一览

决策为什么章节
用注解字符串通信，不用 CRD/gRPC零额外部署、天然持久化、组件重启不丢状态01
Filter 只返回一个节点选卡和判可行性是同一件事，选完必须立刻写注解锁定04
用量是算出来的（静态清单 + Σ Pod）不查 GPU 实际占用，用「承诺分配量」，跟 CPU Requests 同理04
排序升序 + 倒序遍历一个 Less 反转就实现 binpack/spread 两种相反策略05
节点锁跨越 Bind→Allocate 两个进程真正的资源占用在 Allocate 那一刻，提前放锁会超卖06/08
多厂商加锁 sort 固定顺序防 ABBA 死锁06
两条注解（to-allocate / allocated）一条是工单（消费即销毁），一条是账本（永久保留）01/08
空容器也在注解里占位设备插件按容器序号换算，跳过就全部错位01/08
显存百分比用 101 当哨兵0 在 HAMi-core 里意味着「不限制」，绝不能传下去02/09
InitContainer 用 DeepCopy + peakUsage串行执行取峰值；每个单独都要放得下05
synced 放 register 最后一行宁可阻塞请求，也不用残缺缓存做决策07
只有 leader 做 register多副本同时写 handshake 会互相覆盖；filter/bind 不受限，所以锁必须是分布式的07
单卡请求挑互联最差的卡把高 NVLink 的卡留给多卡任务，减少碎片10
refit 冲突不重试冲突说明快照失效，重试等于用过时决策覆盖新状态10

9. 术语表

术语含义
vGPU一张物理卡切出来的一份虚拟卡（显存 + 算力配额）
ExtenderK8s 调度器扩展器。kube-scheduler 通过 HTTP 调用外部服务参与调度
hami-core用户态 CUDA 劫持库（libvgpu.so），软性限制
MIGMulti-Instance GPU，NVIDIA 的硬件级切分，强隔离
MPSMulti-Process Service，NVIDIA 的进程共享方案
sliceMIG 里的显存/算力最小单元。A100 有 8 个
placementMIG 实例在 slice 序列上的落位 {Start, Size}
GI / CIGPU Instance / Compute Instance，MIG 的两层实例
binpack装箱策略：优先填满已用的资源，留出完整空闲
spread摊开策略：优先用最空闲的资源，均衡负载
mutex互斥策略：只分配完全空闲的卡（独占）
Count / 切分份数一张卡最多被几个容器共享，默认 10
handshake调度器和设备插件之间的「点名答到」保活机制
refitNUMA 回填：kubelet 拒绝调度器选的卡时，请求重新选
PodGroup协同调度（Gang Scheduling）里的一批 Pod，要么全成功要么全失败
墓碑 / tombstonecache.DeletedFinalStateUnknown，informer 断连期间删除事件的包装
