第 03 章 · 第二阶段 一个 Pod 的旅程

Webhook：Pod 进门的第一道关

Pod 刚被 kubectl apply 提交，还没写进 etcd，就被 HAMi 拦下来了。 这一关做三件事：改调度器名字、补默认值、把非法请求挡在门外。

学完这章你应该能

  • 说清楚为什么必须有 webhook —— 不加它 HAMi 根本不会被调用
  • 按顺序背出 Handle() 的 8 个处理步骤
  • 列出 4 种会被 Denied 的情况，并解释每种的理由
  • 解释「只写 gpumem 不写 gpu」时 HAMi 帮你补了什么
  • 跑通 Test_MutateAdmission 并读懂它的用例

1. 为什么必须有这一关

Kubernetes 的调度器扩展器（Extender）机制有个前提： kube-scheduler 必须被配置成会去调用你的 HTTP 接口。 这个配置是按 schedulerName 生效的。

改门牌号

默认所有 Pod 的 schedulerName 都是 default-scheduler， 走的是原生调度流程，根本不会经过 HAMi。

HAMi 的 webhook 就像一个站在门口的人： 看到有人要 GPU，就悄悄把他手上的门牌号从「1 号楼」改成「2 号楼」（hami-scheduler）， 这样他才会被送到 HAMi 这栋楼里来处理。

如果没有这一步，用户就必须在每个 YAML 里手写 schedulerName: hami-scheduler。对用户来说是心智负担，也没法给存量应用无侵入接入。

2. 挂载点：一个 HTTP 路由

webhook 跟 filter / bind 挂在同一个 HTTP server 上，就是一条路由：

	// start http server
	router := httprouter.New()
	router.POST("/filter", routes.PredicateRoute(sher))
	router.POST("/bind", routes.Bind(sher))
	router.POST("/refit", routes.NumaRefit(sher))
	router.POST("/webhook", routes.WebHookRoute())      // ← 就是这一条
	router.GET("/healthz", routes.HealthzRoute())
	router.GET("/readyz", routes.ReadyzRoute(sher))
	klog.Info("listen on ", config.HTTPBind)

路由处理器本身极薄，把活全交给 controller-runtime 的 admission 框架： 

func WebHookRoute() httprouter.Handle {
	h, err := scheduler.NewWebHook()
	if err != nil {
		klog.ErrorS(err, "Failed to create new webhook")
	}
	return func(w http.ResponseWriter, r *http.Request, _ httprouter.Params) {
		klog.V(5).Infof("Handling webhook request on %s", r.URL.Path)
		h.ServeHTTP(w, r)          // 委托给 admission.Webhook
	}
}
func NewWebHook() (*admission.Webhook, error) {
	logf.SetLogger(klog.NewKlogr())
	schema := runtime.NewScheme()
	if err := clientgoscheme.AddToScheme(schema); err != nil {
		return nil, err
	}
	decoder := admission.NewDecoder(schema)
	wh := &admission.Webhook{Handler: &webhook{decoder: decoder}}   // 我们的 Handler
	return wh, nil
}
集群侧还需要一个 MutatingWebhookConfiguration

光有 HTTP 端点不够，还得告诉 apiserver「创建 Pod 时来调我」。 这个配置在 Helm chart 里：charts/hami/templates/scheduler/webhook.yaml。
它有一个关键设置 failurePolicy：如果设成 Fail， webhook 挂掉会导致整个集群创建不了 Pod；设成 Ignore 则 HAMi 挂了之后 GPU Pod 会走默认调度器（然后 Fit 不到，一直 Pending）。
生产环境这是个经典坑，值得看一眼 chart 里到底怎么配的。

3. Handle() 全流程：8 个步骤

这个函数只有 88 行，但它是整条链路上唯一能修改 Pod 的地方， 每一行都有明确目的。我们逐段拆。

Webhook 决策模拟器互动

Step 1-2：解码 + 空容器检查

func (h *webhook) Handle(_ context.Context, req admission.Request) admission.Response {
	pod := &corev1.Pod{}
	err := h.decoder.Decode(req, pod)
	if err != nil {
		klog.Errorf("Failed to decode request: %v", err)
		return admission.Errored(http.StatusBadRequest, err)
	}
	if len(pod.Spec.Containers) == 0 {
		klog.Warningf(template+" - Denying admission as pod has no containers", pod.Namespace, pod.Name, pod.UID)
		return admission.Denied("pod has no containers")          // ① 拒绝
	}

这个三重条件在说什么

翻译成人话：「如果用户已经明确指定了一个不是我的调度器，我就不插手。」

  • 条件 1：schedulerName 不为空（用户确实指定了）
  • 条件 2：不是 default-scheduler，或者虽然是默认但配置说了不允许覆盖 （ForceOverwriteDefaultScheduler 默认是 true， 见 ）
  • 条件 3：也不是 HAMi 自己（避免重复处理）

Step 4：校验 numa-alignment 注解

		klog.Warningf(template+" - Denying admission: %v", pod.Namespace, pod.Name, pod.UID, err)
		return admission.Denied(err.Error())                      // ② 拒绝
	}
注意这段注释体现的设计哲学

「让拼写错误立刻暴露给用户，而不是几分钟后埋在设备插件的日志里。」
在准入阶段就拒绝非法输入，比让它一路走下去在深处失败要好得多。用户 kubectl apply 的那一刻就能看到错误信息。 这是贯穿整个 webhook 的思路。

Step 5：核心：遍历所有容器调 MutateAdmission

	hasResource := false

	for idx := range pod.Spec.InitContainers {
		c := &pod.Spec.InitContainers[idx]
		for _, val := range device.GetDevices() {              // 遍历 12 家厂商

			if err != nil {

				return admission.Errored(http.StatusInternalServerError, err)
			}
			hasResource = hasResource || found                 // 任一家认领了就算用了 GPU
		}
	}

	// 2. Process Regular Containers (Keep your existing loop here)
	for idx := range pod.Spec.Containers {
		c := &pod.Spec.Containers[idx]
		for _, val := range device.GetDevices() {
			found, err := val.MutateAdmission(c, pod)
			if err != nil {
				klog.Errorf("validating pod failed:%s", err.Error())
				return admission.Errored(http.StatusInternalServerError, err)
			}
			hasResource = hasResource || found
		}
	}
踩坑：&pod.Spec.Containers[idx] 而不是 range 的值

注意循环写法是 for idx := range 然后取 &pod.Spec.Containers[idx]， 不是 for _, c := range pod.Spec.Containers。 因为 MutateAdmission 要真正修改容器（加环境变量、补 limits）， 必须拿到切片元素的指针。如果用 range 的值拷贝，改了个寂寞。
这是 Go 里非常经典的坑，读到别的项目也要留意。

Step 6-7：三种拒绝 + 改 schedulerName

	}

		//return admission.Allowed("no resource found")

		if pod.Spec.NodeName != "" {
			klog.Infof(template+" - Pod already has node assigned", ...)
			return admission.Denied("pod has node assigned")      // ⑤ 拒绝：已指定 nodeName

为什么「特权容器 + GPU」要拒绝

特权容器可以绕过 HAMi-core 的劫持：它能直接访问 /dev/nvidia*， 自己加载真正的 libcuda.so，显存和算力限制形同虚设。 允许它进来就等于允许一个租户偷偷占满整张卡，影响其他租户。所以直接拒。
注意判断是 hasPrivileged && hasResource。不用 GPU 的特权容器是允许的（比如各种 agent DaemonSet）。

为什么指定了 nodeName 要拒绝

直接写 spec.nodeName 会完全跳过调度器，kubelet 直接开跑。 那 HAMi 就没机会写「用哪张卡」的注解，设备插件在 Allocate() 里 读不到注解就会失败。所以必须在准入时挡住。
这也是 DecodeContainerDevices 里那句错误信息的来历： "pod annotation format error, missing fields, do not use nodeName in task spec"。

4. MutateAdmission 到底改了什么

以 NVIDIA 为例，这个方法做五件事：

func (dev *NvidiaGPUDevices) MutateAdmission(ctr *corev1.Container, p *corev1.Pod) (bool, error) {
	/*gpu related */
	if err := dev.validateMemoryPercentage(ctr); err != nil {      // ① 校验显存百分比范围
		return false, err
	}
	if err := dev.validateCores(ctr); err != nil {                 // ② 校验算力范围
		return false, err
	}
	priority, ok := ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourcePriority)]
	if ok {
		ctr.Env = append(ctr.Env, corev1.EnvVar{                   // ③ 优先级 → 环境变量
			Name:  util.TaskPriority,                              //    CUDA_TASK_PRIORITY
			Value: fmt.Sprint(priority.Value()),
		})
	}

	if dev.config.GPUCorePolicy != "" &&
		dev.config.GPUCorePolicy != DefaultCorePolicy {
		ctr.Env = append(ctr.Env, corev1.EnvVar{                   // ④ 算力策略 → 环境变量
			Name:  util.CoreLimitSwitch,                           //    GPU_CORE_UTILIZATION_POLICY
			Value: string(dev.config.GPUCorePolicy),
		})
	}

	hasResource := dev.mutateContainerResource(ctr)                // ⑤ 补默认卡数
	if dev.defaultExclusiveCoreIfNeeded(ctr) {                     // ⑥ 补独占算力
		hasResource = true
	}

	if hasResource {
		// Set runtime class name if it is not set by user and the runtime class name is configured
		if p.Spec.RuntimeClassName == nil && dev.config.RuntimeClassName != "" {
			p.Spec.RuntimeClassName = &dev.config.RuntimeClassName // ⑦ 补 RuntimeClass
		}
	}

	if !hasResource && dev.config.OverwriteEnv {
		ctr.Env = append(ctr.Env, corev1.EnvVar{                   // ⑧ 不用 GPU 的容器：屏蔽所有卡
			Name:  "NVIDIA_VISIBLE_DEVICES",
			Value: "none",
		})
	}
	return hasResource, nil
}

4.1 「只写显存不写卡数」的自动补全

用户经常这么写 YAML：

resources:
  limits:
    nvidia.com/gpumem: 3000     # 只说要 3000MB 显存
                                # 但没说要几张卡！

HAMi 帮他补上：

func (dev *NvidiaGPUDevices) mutateContainerResource(ctr *corev1.Container) bool {
	_, resourceNameOK := ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourceCountName)]
	if resourceNameOK {
		return true                                    // 已经写了 nvidia.com/gpu，不用管
	}

	_, resourceCoresOK := ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourceCoreName)]
	_, resourceMemOK := ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourceMemoryName)]
	_, resourceMemPercentageOK := ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourceMemoryPercentageName)]

	if resourceCoresOK || resourceMemOK || resourceMemPercentageOK {
		if dev.config.DefaultGPUNum > 0 {              // 写了显存/算力但没写卡数
			ctr.Resources.Limits[corev1.ResourceName(dev.config.ResourceCountName)] =
				*resource.NewQuantity(int64(dev.config.DefaultGPUNum), resource.BinarySI)   // 补 1 张
			return true
		}
	}
	return false                                       // 完全没提 GPU，不是我的活
}

4.2 「不写算力 = 独占整卡」的隐式规则

这条规则很容易踩坑，值得单独看：

func (dev *NvidiaGPUDevices) defaultExclusiveCoreIfNeeded(ctr *corev1.Container) bool {
	if ctr == nil {
		return false
	}

	countName := corev1.ResourceName(dev.config.ResourceCountName)
	if countName == "" || !resourcePresent(ctr, countName) {
		return false                                   // 没申请卡数 → 不管
	}

	coreName := corev1.ResourceName(dev.config.ResourceCoreName)
	if coreName == "" || resourcePresent(ctr, coreName) {
		return false                                   // 已经明写了算力 → 尊重用户
	}

	exclusive := false
	if pct, ok := resourceValue(ctr, corev1.ResourceName(dev.config.ResourceMemoryPercentageName)); ok {
		exclusive = pct == 100                         // 显存要 100% → 那算力也给满
	} else if dev.config.ResourceMemoryName == "" {
		exclusive = true
	} else if _, ok := resourceValue(ctr, corev1.ResourceName(dev.config.ResourceMemoryName)); !ok {
		exclusive = true                               // 显存也没写 → 就是要整卡
	}

	if !exclusive {
		return false
	}

	if ctr.Resources.Limits == nil {
		ctr.Resources.Limits = corev1.ResourceList{}
	}
	ctr.Resources.Limits[coreName] = *resource.NewQuantity(100, resource.DecimalSI)  // 算力 = 100
	return true
}
这条规则的实际影响
用户写的HAMi 补成效果
gpu: 1gpu:1, gpucores:100独占整卡，跟原生 K8s 行为一致
gpu: 1, gpumem: 3000不补共享卡，算力用默认值（DefaultCores，通常 0 = 不限）
gpumem: 3000gpu:1, gpumem:3000共享卡
gpu:1, gpumem-percentage:100+ gpucores:100独占整卡

关键：只写 nvidia.com/gpu: 1 是独占，不是共享。 这个设计保证了「存量应用直接接入 HAMi，行为不变」， 但也让不少人第一次用时困惑「为什么我的卡没被共享」。

5. 配额检查：一个容易忽略的复杂点

最后一步 fitResourceQuota() 里有一段不太显眼但容易算错的逻辑： 怎么算一个 Pod 真正的资源峰值。 

func fitResourceQuota(pod *corev1.Pod) bool {
	for deviceName, dev := range device.GetDevices() {
		resourceNames := dev.GetResourceNames()
		if len(resourceNames.ResourceMemoryName) == 0 && len(resourceNames.ResourceCoreName) == 0 {
			continue                                   // 这家厂商不支持显存/算力配额，跳过
		}

		// Ask the backend what the pod is requesting rather than reading the
		// container spec here. It applies its own memory factor, defaults and
		// template rounding, which is what the scheduler later records as used,
		// so this keeps admission and the scheduler on the same numbers.
		var appMemoryReq, appCoresReq int64
		for i := range pod.Spec.Containers {
			req := dev.GenerateResourceRequests(&pod.Spec.Containers[i])
			if req.Nums == 0 {
				continue
			}
			appMemoryReq += int64(req.Memreq) * int64(req.Nums)     // 普通容器：累加
			appCoresReq  += int64(req.Coresreq) * int64(req.Nums)
		}

		var initPeakMemoryReq, initPeakCoresReq int64
		var sidecarMemoryReq, sidecarCoresReq int64
		for i := range pod.Spec.InitContainers {
			c := &pod.Spec.InitContainers[i]
			req := dev.GenerateResourceRequests(c)
			if req.Nums == 0 {
				continue
			}
			mem := int64(req.Memreq) * int64(req.Nums)
			cores := int64(req.Coresreq) * int64(req.Nums)
			if util.IsSidecarContainer(c) {                         // Sidecar：跟普通容器同时活着
				sidecarMemoryReq += mem
				sidecarCoresReq += cores
				initPeakMemoryReq = max(initPeakMemoryReq, sidecarMemoryReq)
				initPeakCoresReq = max(initPeakCoresReq, sidecarCoresReq)
				continue
			}
			initPeakMemoryReq = max(initPeakMemoryReq, sidecarMemoryReq+mem)  // 普通 Init：串行，取峰值
			initPeakCoresReq = max(initPeakCoresReq, sidecarCoresReq+cores)
		}

		memoryReq := max(initPeakMemoryReq, sidecarMemoryReq+appMemoryReq)   // 全局峰值
		coresReq  := max(initPeakCoresReq,  sidecarCoresReq+appCoresReq)
		if memoryReq == 0 && coresReq == 0 {
			continue
		}
		...
		if !device.GetLocalCache().FitQuota(pod.Namespace, memoryReq, resourceNames.MemoryFactor, coresReq, deviceName) {
			klog.Infof(template+" - Denying admission", pod.Namespace, pod.Name, pod.UID)
			return false
		}
	}
	return true
}
三类容器，三种资源占用模型
容器类型何时活着资源怎么算
普通 ContainerPod 整个生命周期累加（它们同时运行）
普通 InitContainer串行，一个跑完下一个取最大值（同一时刻只有一个在跑）
Sidecar InitContainer
restartPolicy: Always		启动后一直活到 Pod 结束累加，而且要加到后面每一项上

最终公式 max(init 阶段峰值, sidecar + 所有普通容器) 就是这么来的。
这段逻辑在第 05 章打分时会再出现一次（allocateInitContainers）， 因为调度时也要按同样的模型试算。

7. 本章自测

如果把 HAMi 的 MutatingWebhookConfiguration 删掉，会发生什么？
A没影响，调度器照常工作
B集群里所有 Pod 都创建不了
CGPU Pod 的 schedulerName 保持 default-scheduler，永远不会走到 HAMi
DGPU Pod 会被随机调度到任意节点
调度器扩展器是按 schedulerName 绑定的。 没有 webhook 改门牌号，Pod 就走原生 default-scheduler，HAMi 的 /filter 根本不会被调用， 也就不会有分配注解。这时 Pod 会被原生调度器按 nvidia.com/gpu 整卡分配 （如果集群里还有官方 device plugin），或者一直 Pending。
用户可以自己在 YAML 里手写 schedulerName: hami-scheduler 绕过 —— 这也是排查问题时的验证手段。
下面这个容器，webhook 处理后的 limits 是什么？
limits: nvidia.com/gpu: 1
A不变，还是只有 nvidia.com/gpu: 1
B补上 nvidia.com/gpucores: 100，变成独占整卡
C补上 nvidia.com/gpumem: 默认值
D被拒绝，因为没指定显存
defaultExclusiveCoreIfNeeded() 的逻辑： 申请了卡数 + 没写算力 + 没写显存 → 判定为「用户想要整卡」，补 gpucores: 100。
这保证了存量应用无缝接入：原来独占一张卡，接入 HAMi 后还是独占。 想共享必须显式写 gpumem 或 gpucores。
一个 Pod 有：1 个普通 InitContainer 要 4000MB，1 个 Sidecar InitContainer 要 1000MB，2 个普通容器各要 3000MB。配额检查算出的显存需求是多少？
A4000（取最大）
B11000（全部累加）
C6000（只算普通容器）
D7000
按公式 max(initPeak, sidecar + app) 算：
  • sidecarMemoryReq = 1000
  • initPeak = max(1000, 1000+4000) = 5000（Init 阶段：sidecar 已启动 + 普通 init 在跑）
  • app = 3000 + 3000 = 6000
  • 结果 = max(5000, 1000 + 6000) = 7000
关键在于 Sidecar（restartPolicy: Always 的 InitContainer）在整个 Pod 生命周期都活着， 所以要加到每一项上；而普通 InitContainer 跑完就退出，只在 Init 阶段占资源。
为什么 webhook 循环写成 for idx := range pod.Spec.Containers 再取 &pod.Spec.Containers[idx]？
A必须拿到切片元素的指针，才能真正修改容器（加 env、补 limits）
B性能更好，避免结构体拷贝
C为了兼容旧版本 Go
D习惯写法，没有实际区别
MutateAdmission 会往 ctr.Env 追加环境变量、 往 ctr.Resources.Limits 写默认值。如果用 for _, c := range， c 是值拷贝，改它对原 Pod 毫无影响， 最后 json.Marshal(pod) 出来的还是原样，patch 是空的。
B 也算是个副作用（corev1.Container 结构体很大），但不是主要原因。

8. 小结

  • Webhook 的头号任务是把 schedulerName 改成 hami-scheduler， 否则 HAMi 根本不会被调用。
  • 它是整条链路上唯一能修改 Pod 的地方，之后只能加注解不能改 spec。
  • 五种拒绝：无容器、numa-alignment 非法、打分权重非法、特权容器 + GPU、已指定 nodeName、超配额。
  • 自动补全两条隐式规则：写了显存补卡数、只写卡数补 gpucores=100（独占）。
  • 配额峰值公式 max(initPeak, sidecar + app)， 三类容器三种占用模型 —— 第 05 章打分时会再遇到一次。
  • 循环用索引取指针，因为要真正修改容器。

Pod 的 schedulerName 已经被改成 hami-scheduler， kube-scheduler 开始调用 HAMi 的 /filter 接口。 下一章我们走进调度器主流程：从 HTTP 请求进来，到选出一个节点写进注解，中间发生了什么。
