第 09 章 · 第三阶段 硬骨头

HAMi-core：容器里的 CUDA 劫持

前面八章都在讲「怎么记账」。这一章讲怎么真正执法。一个 C 语言写的动态库，在容器内部把 CUDA API 全部换成自己的版本， 显存超了就报 OOM，算力多了就限速。

学完这章你应该能

  • 解释 LD_PRELOAD / ld.so.preload 劫持的原理和边界
  • 说清楚显存限额是怎么被检查的，以及为什么需要跨进程共享内存
  • 解释算力限制的令牌桶模型：谁发令牌、谁花令牌、怎么调速
  • 说出至少三种「劫持会失效」的场景
  • 知道排查容器内 GPU 问题该看哪些日志和文件
关于这一章的定位

libvgpu/ 是 C 代码，构建和调试方式跟 Go 部分完全不同， 而且改动它需要真实 GPU 才能验证。
第一遍读，理解原理和边界就够了。知道「什么情况下限制会失效」，比背下每个函数更有价值。 真要动手改这块时再回来精读。

1. 劫持原理：插到调用队伍的最前面

动态链接器的「插队」机制

Linux 程序调用 cuMemAlloc() 时， 动态链接器（ld.so）负责找到这个符号在哪个 .so 里。 它按固定顺序搜索已加载的库。

/etc/ld.so.preload 里列出的库会被插到队伍最前面。 所以只要 libvgpu.so 也导出一个叫 cuMemAlloc 的函数， 它就会先被找到。应用以为自己在调 CUDA，其实调的是 HAMi。

应用代码PyTorch / TensorFlow
torch.cuda.empty_cache() → cudaMalloc() → cuMemAlloc_v2()
↓动态链接器解析符号
libvgpu.so 的 cuMemAlloc_v2劫持点
检查额度 → 超了返回 CUDA_ERROR_OUT_OF_MEMORY；没超则记账后放行
↓CUDA_OVERRIDE_CALL 转发
真正的 libcuda.soNVIDIA 驱动
执行真实的显存分配

2. 劫持是怎么实现的

2.1 拿到「真身」函数指针

劫持函数检查完额度后，得调用真正的 CUDA 函数。 但它不能直接调 cuMemAlloc（那会调到自己，无限递归）。 解法是用 dlsym(RTLD_NEXT, ...) 在「队伍后面」找真身： 

    table = dlopen(cuda_filename, RTLD_NOW | RTLD_NODELETE);   // 显式打开真正的 libcuda.so
    if (!table) {
        LOG_WARN("can't find library %s", cuda_filename);
    }

    for (i = 0; i < CUDA_ENTRY_END; i++) {
        LOG_DEBUG("LOADING %s %d",cuda_library_entry[i].name,i);
        cuda_library_entry[i].fn_ptr = real_dlsym(table, cuda_library_entry[i].name);
        if (!cuda_library_entry[i].fn_ptr) {
            cuda_library_entry[i].fn_ptr=real_dlsym(RTLD_NEXT,cuda_library_entry[i].name);
            //                                      ^^^^^^^^^ 「在我之后加载的库里找」
            if (!cuda_library_entry[i].fn_ptr){
                LOG_INFO("can't find function %s in %s", cuda_library_entry[i].name,cuda_filename);
                snprintf(tmpfunc, sizeof(tmpfunc), "%s", cuda_library_entry[i].name);
                while (prior_function(tmpfunc)) {         // 再退回去找老版本后缀
                    cuda_library_entry[i].fn_ptr=real_dlsym(RTLD_NEXT,tmpfunc);
                    if (cuda_library_entry[i].fn_ptr) {
                        LOG_INFO("found prior function %s",tmpfunc);
                        break;

三级降级查找：先在显式 dlopen 的 libcuda.so 里找 → 再用 RTLD_NEXT 找 → 还找不到就退回去找老版本后缀。 这种层层兜底说明现实中确实遇到过各种奇怪的运行环境。

之后所有转发都通过一个宏：

CUDA_OVERRIDE_CALL(cuda_library_entry, cuMemAlloc_v2, dptr, bytesize);
//                 ^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^
//                 真身函数表           要调哪个        参数原样透传

2.2 处理 CUDA 的版本后缀地狱

void *find_symbols_in_table(const char *symbol) {
    char symbol_v[500];
    void *pfn;
    /* Skip CUDA graph functions: let them fall through to real driver */
    if (strncmp(symbol, "cuGraph", 7) == 0) {
        return NULL;                          // CUDA Graph 不劫持，直接放行
    }
    snprintf(symbol_v, sizeof(symbol_v), "%s_v3", symbol);
    if ((pfn = __dlsym_hook_section(NULL, symbol_v)) != NULL)
        return pfn;                           // 优先找 _v3
    symbol_v[strlen(symbol_v)-1]='2';
    if ((pfn = __dlsym_hook_section(NULL, symbol_v)) != NULL)
        return pfn;                           // 再找 _v2
    return __dlsym_hook_section(NULL, symbol); // 最后找无后缀版本
}
CUDA API 的版本后缀是劫持最大的坑

NVIDIA 改 API 时不改名字，而是加后缀： cuMemAlloc → cuMemAlloc_v2。 应用链接的可能是任意一个版本。漏掉一个后缀，那条路径的限制就完全失效。应用可以随便分配显存，HAMi 一无所知。

注意 cuGraph* 被显式跳过了 —— CUDA Graph 里的显存分配绕过了 HAMi 的限制，这是一个已知的功能缺口。

为什么必须劫持 cuGetProcAddress

CUDA 12 之后，运行时不再直接链接符号，而是调 cuGetProcAddress("cuMemAlloc", &fn, ...) 动态查询函数地址。
这条路径完全绕过动态链接器。ld.so.preload 拦不住它。
所以 HAMi 必须连查询函数本身也劫持掉， 在返回地址时偷偷换成自己的实现。
这就是为什么劫持类工具需要持续跟进 CUDA 版本 —— 每个大版本都可能引入新的绕过路径。

3. 显存限制

3.1 限额从哪来

void do_init_device_memory_limits(uint64_t* arr, int len) {
    size_t fallback_limit = get_limit_from_env(CUDA_DEVICE_MEMORY_LIMIT);   // 全局兜底
    int i;
    for (i = 0; i < len; ++i) {
        char env_name[CUDA_DEVICE_MEMORY_LIMIT_KEY_LENGTH];
        snprintf(env_name, sizeof(env_name), "%s_%d", CUDA_DEVICE_MEMORY_LIMIT, i);
        size_t cur_limit = get_limit_from_env(env_name);      // CUDA_DEVICE_MEMORY_LIMIT_0
        if (cur_limit > 0) {
            arr[i] = cur_limit;                               // 每卡独立限额
        } else if (fallback_limit > 0) {
            arr[i] = fallback_limit;                          // 退回全局限额
        } else {
            arr[i] = 0;                                       // 0 = 不限制
        }
    }
}

环境变量的值支持带单位后缀：

size_t get_limit_from_env(const char* env_name) {
    char* env_limit = getenv(env_name);
    if (env_limit == NULL) {
        return 0;
    }
    size_t len = strlen(env_limit);
    if (len == 0) {
        return 0;
    }
    size_t scalar = 1;
    char* digit_end = env_limit + len;
    if (env_limit[len - 1] == 'G' || env_limit[len - 1] == 'g') {
        digit_end -= 1;  scalar = 1024 * 1024 * 1024;
    } else if (env_limit[len - 1] == 'M' || env_limit[len - 1] == 'm') {
        digit_end -= 1;  scalar = 1024 * 1024;          // ← 设备插件用的是 "3000m"
    } else if (env_limit[len - 1] == 'K' || env_limit[len - 1] == 'k') {
        digit_end -= 1;  scalar = 1024;
    }
    size_t res = strtoul(env_limit, &digit_end, 0);
    size_t scaled_res = res * scalar;
    ...
}
0 意味着「不限制」，不是「不给显存」

这解释了第 02 章 GenerateResourceRequests 里那条注释： 「0 would inject CUDA_DEVICE_MEMORY_LIMIT=0m, which hami-core reads as "no limit"」。
所以调度器那边用 101 当「未设置」的哨兵， 绝不能把 0 传下来 —— 那等于给容器开了无限显存。
这是一个跨越 Go 和 C 两侧的隐式契约，只看一边永远想不通为什么要用 101。

3.2 OOM 检查

int oom_check(const int dev, size_t addon) {
    CUdevice d;
    if (dev==-1)
        cuCtxGetDevice(&d);
    else
        d=dev;
    uint64_t limit = get_current_device_memory_limit(d);
    size_t _usage = get_gpu_memory_usage(d);          // 跨进程共享内存里读

    if (limit == 0) {
        return 0;                                     // 0 = 不限制，直接放行
    }

    size_t new_allocated = _usage + addon;
    LOG_INFO("_usage=%lu limit=%lu new_allocated=%lu",_usage,limit,new_allocated);
    if (new_allocated > limit) {
        LOG_ERROR("Device %d OOM %lu / %lu", d, new_allocated, limit);

        lock_shrreg();
        int cleared = clear_proc_slot_nolock(1);      // 先清理死进程的残留记账
        unlock_shrreg();
        if (cleared > 0)
            return oom_check(dev,addon);              // 清出空间了就重试一次
        return 1;                                     // 真的 OOM
    }
    return 0;
}
clear_proc_slot_nolock。死进程的显存回收

同一个容器里可能有多个进程共用限额。 如果某个进程崩了（没走正常的 free 路径）， 它在共享内存里的记账还留着，会虚占额度。
所以 OOM 之前先扫一遍：哪些 PID 已经不存在了，把它们的账清掉， 清出空间就重试。这是一个很实用的自愈设计。

3.4 跨进程共享记账

合租房里的共用水表

一个容器可能跑好几个进程（PyTorch DataLoader 的 worker、多卡训练的多个 rank）。 限额是给整个容器的，不是给单个进程的。
所以记账不能放在进程内存里，得放在所有进程都能读写的地方。一个 mmap 的共享内存文件，路径由环境变量 CUDA_DEVICE_MEMORY_SHARED_CACHE 指定（第 08 章注入的）。

4. 算力限制：一个令牌桶

游乐场的门票

每次启动 CUDA kernel 就像进游乐场，要交票（票数 = grid 大小）。
票桶里的票有限，没票了就排队等。
另有一个发票员（watcher 线程）定期往桶里放票 —— 放多放少取决于「当前实际利用率 vs 目标利用率」。

效果：长期平均利用率被控制在目标值附近， 但不是硬性瞬时限制（瞬时可能冲高）。

4.1 花票：rate_limiter

void rate_limiter(int grids, int blocks) {
  CUdevice current_device;
  CUresult res = cuCtxGetDevice(&current_device);
  int device_id = (res == CUDA_SUCCESS) ? (int)current_device : 0;

  int64_t before_cuda_cores = 0;
  int64_t after_cuda_cores = 0;
  int64_t kernel_size = grids;                        // 票价 = grid 数量

  /* Fast exit using cached values — no shared memory access needed */
  if (cached_sm_limit[device_id] >= 100 || cached_sm_limit[device_id] == 0) {
      return;                                         // 100% 或 0 = 不限制，快速返回
  }
  if (cached_util_switch == 0) {
      return;                                         // 开关关闭
  }

  while (get_recent_kernel()<0) {
    sleep(1);
  }
  set_recent_kernel(2);

  do {
CHECK:
      before_cuda_cores = g_cur_cuda_cores[device_id];
      if (before_cuda_cores < 0) {
        nanosleep(&g_cycle, NULL);                    // 没票了 → 睡一小会儿再看
        goto CHECK;
      }
      after_cuda_cores = before_cuda_cores - kernel_size;
  } while (!CAS(&g_cur_cuda_cores[device_id], before_cuda_cores, after_cuda_cores));
                                                      // CAS 保证多线程安全
}
这就是「HAMi 会让训练变慢」的原因

nanosleep 是真的在阻塞调用方线程。 当算力配额用完时，你的 kernel launch 会卡在这里。
所以 gpucores 设得太低会显著拖慢任务。 那个 fast exit（>= 100 || == 0 直接返回）非常重要。不限制算力时，这个函数的开销接近于零。

4.2 发票：watcher 线程的 PID 控制

static void change_token(int64_t delta, int device_id) {
  int64_t cuda_cores_before = 0, cuda_cores_after = 0;

  LOG_DEBUG("device %d: delta: %ld, curr: %ld", device_id, delta, g_cur_cuda_cores[device_id]);
  do {
    cuda_cores_before = g_cur_cuda_cores[device_id];
    cuda_cores_after = cuda_cores_before + delta;

    if (cuda_cores_after > g_total_cuda_cores[device_id]) {
      cuda_cores_after = g_total_cuda_cores[device_id];    // 封顶，防止攒票
    }
  } while (!CAS(&g_cur_cuda_cores[device_id], cuda_cores_before, cuda_cores_after));
}
static int64_t delta(int up_limit, int user_current, int64_t share, int device_id) {
  int utilization_diff =
      abs(up_limit - user_current) < 5 ? 5 : abs(up_limit - user_current);   // 最小步长 5
  int64_t increment =
      (int64_t)g_sm_num[device_id] * (int64_t)g_sm_num[device_id] *
      (int64_t)g_max_thread_per_sm[device_id] * (int64_t)utilization_diff / 2560;
      //  ↑ 步长跟 GPU 的 SM 数量和每 SM 线程数挂钩 —— 大卡步长更大

  /* Accelerate cuda cores allocation when utilization vary widely */
  if (utilization_diff > up_limit / 2) {
    increment = increment * utilization_diff * 2 / (up_limit + 1);           // 偏差大就加速
  }

  if (user_current <= up_limit) {
    share = (share + increment) > g_total_cuda_cores[device_id]
            ? g_total_cuda_cores[device_id]
            : (share + increment);                     // 用少了 → 多发票
  } else {
    share = (share - increment) < 0 ? 0 : (share - increment);   // 用多了 → 少发票
  }

  return share;
}

5. 劫持失效的场景（最重要的一节）

场景为什么会失效对策
特权容器 能直接访问 /dev/nvidia*，可以自己 dlopen 真 libcuda，或者干脆改掉 ld.so.preload webhook 直接拒绝（第 03 章）
静态链接 CUDA 符号在编译期就绑定了，动态链接器插不进来 无解。极少见
CUDA Graph find_symbols_in_table 显式跳过 cuGraph*；图内的分配不经过劫持点 已知缺口
新版 CUDA 的新 API NVIDIA 加了新的分配路径或新的 _v4 后缀，HAMi 还没跟进 持续跟进；hack/check_cuda_hook_consistency.py
应用直接改 /etc/ld.so.preload 容器内有 root 就能改，改完重启进程即绕过 非特权 + 只读挂载可缓解
非 CUDA 路径占显存 比如通过 NVENC/NVDEC 视频编解码、或直接 ioctl 不在劫持范围内
这决定了 HAMi 的安全模型

HAMi-core 是「防君子不防小人」的用户态限制， 不是硬件级隔离（那是 MIG 干的事，第 10 章）。
它适合可信租户之间的资源公平共享， 不适合作为多租户之间的安全边界。
这个定位一定要清楚 —— 在生产环境做技术选型时， 「用 HAMi 共享还是用 MIG 硬隔离」取决于你的租户是否互信。

6. vGPUmonitor：读共享内存出指标

HAMi-core 把用量写在共享内存里，vGPUmonitor 这个 DaemonSet 定期去读， 转成 Prometheus 指标： 

type headerT struct {
	// 跟 C 侧共享内存布局严格对齐的结构体
	...
}
Go 结构体必须和 C 结构体逐字节对齐

pkg/monitor/nvidia/ 下有 v0/spec.go 和 v1/spec.go 两个版本， 对应 C 侧共享内存格式的两个版本。共享内存头已经包含 magic 和 major/minor version， loadCache() 也会校验 magic、版本和最小尺寸。
不过，如果 C 侧改了布局却没升级版本、Go 侧也没同步，已有校验仍无法识别这种错误， 指标就可能被错读。
改 multiprocess/multiprocess_memory_limit.h 里的 shared_region_t 时， 必须同步检查 pkg/monitor/nvidia/v*/spec.go、升级版本并补布局断言。

症状先看什么

B因为它也会分配显存
CCUDA 12+ 通过它动态查询函数地址，这条路径完全绕过动态链接器，ld.so.preload 拦不住
D为了兼容旧版驱动
ld.so.preload 只在符号解析时起作用。 如果应用用 cuGetProcAddress("cuMemAlloc", &fn, ...) 主动查地址， 拿到的是驱动里的真实地址，之后直接通过函数指针调用 —— 劫持完全失效。
所以必须把这个「查询函数」本身也劫持掉，在它返回地址时换成 HAMi 的版本。
每个 CUDA 大版本都可能引入新的绕过路径，这是劫持类方案的固有维护成本。
算力限制的令牌桶里，谁消耗令牌？消耗多少？
A每次 kernel launch 消耗 grids 个令牌；没令牌就 nanosleep 阻塞等待
B每次显存分配消耗，按字节数
Cwatcher 线程按时间消耗
D驱动自动消耗
看 rate_limiter(int grids, int blocks)： kernel_size = grids，然后 CAS 循环把 g_cur_cuda_cores 减掉这个数。 令牌为负时 nanosleep 后重试。
这也解释了「HAMi 会让训练变慢」。真的在阻塞调用线程。gpucores 设得越低，阻塞越频繁。
发令牌的是 watcher 线程，按「实际利用率 vs 目标利用率」的偏差动态调整发放量。
下面哪种情况 HAMi-core 的显存限制不会失效？
A容器以 privileged: true 运行
B应用使用 CUDA Graph 里的显存分配
C应用在容器里以 root 身份清空了 /etc/ld.so.preload
D容器里同时跑了 4 个 Python 进程
多进程正是 HAMi-core 专门设计了跨进程共享内存来处理的场景： 限额是给整个容器的，4 个进程共享同一个额度，记账写在 mmap 的共享文件里 （CUDA_DEVICE_MEMORY_SHARED_CACHE）。
A、B、C 都是真实的失效场景： A 被 webhook 拒绝（第 03 章）；B 是代码里显式跳过的已知缺口； C 说明 HAMi-core 是「防君子不防小人」的用户态限制，不是安全边界。

10. 小结

  • 劫持靠 /etc/ld.so.preload 让 libvgpu.so 抢先导出 CUDA 符号， 再用 dlsym(RTLD_NEXT) 拿真身转发。
  • CUDA 12+ 的 cuGetProcAddress 绕过动态链接器，必须连它一起劫持。
  • 显存限额 0 = 不限制。这是 Go 侧用 101 当哨兵的根本原因。
  • OOM 检查前会清理死进程的残留记账，清出空间就重试。
  • 算力用令牌桶：kernel launch 花票（花完 nanosleep 阻塞），watcher 按利用率偏差发票。
  • 失效场景要牢记：特权容器、CUDA Graph、静态链接、新 API、改 ld.so.preload。
  • HAMi-core 是资源公平共享机制，不是多租户安全边界。需要硬隔离就用 MIG。
  • Go 侧 pkg/monitor/nvidia/v*/spec.go 必须和 C 侧结构体逐字节对齐；布局变化要升级版本并补断言。
