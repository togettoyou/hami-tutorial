第 08 章 · 第三阶段 硬骨头

Device Plugin：把注解翻译成环境变量

场景切到 GPU 节点上。设备插件做两件事： 把 1 张物理卡上报成 10 张虚拟卡， 以及把调度器写的 Pod 注解翻译成容器里的环境变量。 后者是整个协议里最脆弱的一环。

学完这章你应该能

  • 说清楚「一张卡变十张」是怎么骗过 kubelet 的，以及这个谎言的边界
  • 解释 Allocate() 怎么知道「这次请求是给哪个 Pod 的」—— 以及为什么这很危险
  • 列出注入到容器里的关键环境变量，说出每个的作用
  • 解释注解「消费即擦除」的机制，以及它防的是什么
  • 说清楚节点锁在设备插件这一侧是怎么被释放的

1. 设备插件的三个身份

① 对 kubelet：一个标准 Device PlugingRPC
实现 K8s Device Plugin API：ListAndWatch 上报设备、 GetPreferredAllocation 建议选哪几个、Allocate 返回容器配置
＋
② 对调度器：一个设备清单上报器Node 注解
每 30 秒调 NVML 扫一遍卡，把清单 JSON 写进 hami.io/node-nvidia-register
＋
③ 对容器：一个环境变量注入器Allocate 响应
注入 CUDA_DEVICE_MEMORY_LIMIT_0 等，挂载 libvgpu.so 和 ld.so.preload

2. 「一张卡变十张」：善意的谎言

对 kubelet 报的是切分后的虚拟设备

kubelet 只懂「有几个设备可用」，不懂「显存分片」。 所以设备插件对 kubelet 撒了个谎：把一张 UUID 为 GPU-abc 的卡， 上报成 10 个 ID 分别为 GPU-abc-0 … GPU-abc-9 的「设备」。

kubelet 于是可以像分配普通资源一样，把「10 个设备」分给 10 个容器。 至于每个容器实际能用多少显存 —— 那是 HAMi-core 在容器里管的事（第 09 章）。 

func (plugin *NvidiaDevicePlugin) ListAndWatch(e *kubeletdevicepluginv1beta1.Empty, s kubeletdevicepluginv1beta1.DevicePlugin_ListAndWatchServer) error {
	err := s.Send(&kubeletdevicepluginv1beta1.ListAndWatchResponse{Devices: plugin.apiDevices()})
	if err != nil {
		klog.Errorf("Failed to send ListAndWatch response: %v", err)
		return err
	}

	for {
		select {
		case <-plugin.stop:
			return nil
		case d := <-plugin.health:                  // 健康状态变化才重新上报
			// FIXME: there is no way to recover from the Unhealthy state.
			d.Health = kubeletdevicepluginv1beta1.Unhealthy
			klog.Infof("'%s' device marked unhealthy: %s", plugin.rm.Resource(), d.ID)
			if err := s.Send(&kubeletdevicepluginv1beta1.ListAndWatchResponse{Devices: plugin.apiDevices()}); err != nil {
				klog.Errorf("Failed to send health-update ListAndWatch response: %v", err)
				return nil
			}
		}
	}
}
注意那个 FIXME

「there is no way to recover from the Unhealthy state」 —— 一张卡一旦被标记为不健康，就再也回不到健康状态了， 除非重启设备插件 Pod。
如果是临时性的 XID 错误（比如 ECC 可纠正错误）， 这张卡就被永久浪费了。
这是一个开发者自己标注的已知缺陷。修它需要在 里加上恢复检测逻辑 —— 是个有分量的贡献。

		}

	annos[nvidia.RegisterAnnos] = encodeddevices                    // hami.io/node-nvidia-register

	}

	if err != nil {
		klog.Errorln("patch node error", err.Error())
		util.EmitNodeWarningEvent(node, "RegistrationFailed",
			fmt.Sprintf("Failed to patch node annotation: %v", err),
			10*time.Minute)

两个实现细节
  • 内容对比去重（plugin.deviceCache）：设备清单 30 秒扫一次， 但绝大多数时候内容不变。不写就不产生 apiserver 请求，也不会触发调度器那边的 informer 事件。 在大集群里这个优化很关键。
  • 限频的 Warning Event：EmitNodeWarningEvent(..., time.Hour)、 10*time.Minute。带了去重窗口， 避免每 30 秒刷一条相同的事件把 etcd 淹了。

4. Allocate()：整个协议最脆弱的地方

核心难题：kubelet 不告诉你这是给哪个 Pod 的

K8s Device Plugin API 的 AllocateRequest 里只有设备 ID 列表， 没有 Pod 名、没有命名空间、没有 UID。
但 HAMi 必须知道是哪个 Pod，才能读出调度器写的分配注解。
怎么办？去 apiserver 上「猜」。 

func GetPendingPod(ctx context.Context, node string) (*corev1.Pod, error) {
	pod, err := GetAllocatePodByNode(ctx, node)       // 先看 Node 注解里有没有明确指定
	if err != nil {
		return nil, err
	}
	if pod != nil {
		return pod, nil
	}
	// filter pods for this node.
	selector := fmt.Sprintf("spec.nodeName=%s", node)
	podListOptions := metav1.ListOptions{
		FieldSelector: selector,
	}
	podlist, err := client.GetClient().CoreV1().Pods("").List(ctx, podListOptions)
	if err != nil {
		return nil, err
	}
	for _, p := range podlist.Items {
		if p.Status.Phase != corev1.PodPending {
			continue                                   // ① 必须是 Pending
		}
		if _, ok := p.Annotations[BindTimeAnnotations]; !ok {
			continue                                   // ② 必须有 bind-time
		}
		if phase, ok := p.Annotations[DeviceBindPhase]; !ok {
			continue                                   // ③ 必须有 bind-phase
		} else {
			// Allow both "allocating" and "success" phases for multi-container pods
			// where some containers have already been allocated but others are still pending
			if phase != DeviceBindAllocating && phase != DeviceBindSuccess {
				continue
			}
		}
		if n, ok := p.Annotations[AssignedNodeAnnotations]; !ok {
			continue                                   // ④ vgpu-node 必须等于本节点
		} else {
			if strings.Compare(n, node) == 0 {
				return &p, nil                         // 就是你了
			}
		}
	}
	return nil, fmt.Errorf("no binding pod found on node %s", node)
}
getPendingPod 猜谁模拟器互动

节点上有多个 Pod，看筛选条件怎么一层层过滤。试试让两个 Pod 同时满足条件， 看会发生什么。

这个设计的两个致命隐患
  1. 如果有两个 Pod 同时满足条件，会选到列表里的第一个 —— 而 List 的顺序是不保证的。 结果就是 Pod A 拿到了 Pod B 的显存配置。
    唯一的防线是节点锁（第 06 章）：它保证同一时刻只有一个 Pod 处于 allocating。
    但注意条件 ③ 里 DeviceBindSuccess 也被接受了 —— 注释解释是为了多容器 Pod，但这也扩大了误配的窗口。
  2. 每次 Allocate 都要 List 全节点的 Pod，是一次实打实的 apiserver 请求。 节点上 Pod 密集时这是热点。

4.1 Allocate 主流程

func (plugin *NvidiaDevicePlugin) Allocate(ctx context.Context, reqs *kubeletdevicepluginv1beta1.AllocateRequest) (*kubeletdevicepluginv1beta1.AllocateResponse, error) {
	// Kubelet may issue Allocate calls concurrently. The pending-pod
	// annotation protocol and dynamic MIG preparation are node-global, so keep
	// pod selection, GI/CI creation, and annotation consumption atomic.
	plugin.applyMutex.Lock()                          // 节点内串行化
	defer plugin.applyMutex.Unlock()

	klog.InfoS("Allocate", "request", reqs)
	responses := kubeletdevicepluginv1beta1.AllocateResponse{}
	nodename := os.Getenv(util.NodeNameEnvName)

	for idx, req := range reqs.ContainerRequests {
		...

plugin.applyMutex 那段注释值得细读

「Kubelet may issue Allocate calls concurrently.」 —— kubelet 可能并发调 Allocate。而「猜 Pod」+「消费注解」+「MIG 实例创建」 这三件事都是节点全局的操作，必须原子完成。
所以这里加了一把整个设备插件进程级的大锁。 代价是同节点的容器分配完全串行 —— 但正确性优先。

4.2 「消费即擦除」

注解里按容器顺序排着好几份分配。每处理一个容器，就把对应那一段清空： 

// popNextContainerDevices finds and erases the first non-empty ContainerDevices
// from podSingleDev in place, returning the corresponding pod container and the
// popped devices. The container resolution uses the same init-then-regular
// ordering convention as the annotation encoder. It does NOT touch the API
// server — the caller is responsible for patching the annotation once after the
// loop completes.
func popNextContainerDevices(pod *corev1.Pod, podSingleDev device.PodSingleDevice) (corev1.Container, device.ContainerDevices, error) {
	initContainerCount := len(pod.Spec.InitContainers)
	for i, ctrDevs := range podSingleDev {
		if len(ctrDevs) > 0 {                          // 找第一个非空的
			podSingleDev[i] = device.ContainerDevices{} // 就地擦除
			if i < initContainerCount {
				return pod.Spec.InitContainers[i], ctrDevs, nil     // init 容器
			}
			regularIdx := i - initContainerCount        // 减去偏移量
			if regularIdx >= len(pod.Spec.Containers) {
				return corev1.Container{}, nil, fmt.Errorf("container index %d out of range (init=%d, regular=%d)", i, initContainerCount, len(pod.Spec.Containers))
			}
			return pod.Spec.Containers[regularIdx], ctrDevs, nil    // 普通容器
		}
	}
	return corev1.Container{}, nil, errors.New("no pending device allocation found")
}
这里印证了第 01 章说的「空容器也要占位」

i 是注解里的容器序号， i < initContainerCount 决定它是 init 还是普通容器， i - initContainerCount 是普通容器的下标。
如果编码时跳过了不用 GPU 的容器，这里的索引换算就全错了。第 3 个容器会拿到第 1 个容器的卡。这就是为什么必须编码成 ;; 保留空位。 

// patchErasedAnnotation patches the pod's device annotation with the given
// podSingleDev (which has had some containers popped). It also updates
// pod.Annotations in place so that subsequent Allocate calls within the same
// kubelet invocation see the erased state.
func patchErasedAnnotation(pod *corev1.Pod, dtype string, podSingleDev device.PodSingleDevice) error {
	klog.V(5).Infof("After erase annotation, remaining devices: %v", podSingleDev)
	encoded := device.EncodePodSingleDevice(podSingleDev)
	annoKey := device.InRequestDevices[dtype]          // hami.io/vgpu-devices-to-allocate
	newAnnos := map[string]string{annoKey: encoded}
	if err := util.PatchPodAnnotations(pod, newAnnos); err != nil {
		return err
	}
	pod.Annotations[annoKey] = encoded                 // 内存里也同步更新
	return nil
}
为什么要「擦除」：防止容器重启时重复分配

容器崩溃重启时，kubelet 会再次调用 Allocate。 如果注解还在，插件会以为这是一个新容器， 把同一份显存再分配一次。
擦除之后，to-allocate 变空， 但 allocated（第 01 章说的「留档」那条）保持不变， 调度器的账本依然正确。两条注解各司其职的价值就体现在这里。

4.4 挂载劫持库

光有环境变量不够，还要把 libvgpu.so 挂进容器， 并通过 /etc/ld.so.preload 让它在任何程序启动时被优先加载： 

/usr/local/vgpu/libvgpu.so
换掉门口的接待员

ld.so.preload 是 Linux 动态链接器的一个机制： 里面列出的 .so 会在所有其他库之前被加载。
于是当应用调用 cuMemAlloc() 时， 动态链接器先在 libvgpu.so 里找到这个符号， 应用以为自己在调 CUDA，其实调的是 HAMi 的劫持函数。
劫持函数检查完额度，再转发给真正的 libcuda.so。
—— 第 09 章会详细拆这个机制。

5. 释放节点锁：闭环的最后一步

func PodAllocationSuccess(nodeName string, pod *corev1.Pod, lockName string) {
	klog.Infof("Pod allocation successful for pod %s/%s on node %s", pod.Namespace, pod.Name, nodeName)
	updatePodAnnotationsAndReleaseLock(nodeName, pod, lockName, util.DeviceBindSuccess)
}

func updatePodAnnotationsAndReleaseLock(nodeName string, pod *corev1.Pod, lockName string, deviceBindPhase string) {
	newAnnos := map[string]string{util.DeviceBindPhase: deviceBindPhase}
	if err := util.PatchPodAnnotations(pod, newAnnos); err != nil {
		klog.Errorf("Failed to patch pod annotations for pod %s/%s: %v", pod.Namespace, pod.Name, err)
	}
	if err := nodelock.ReleaseNodeLock(nodeName, lockName, pod, false); err != nil {   // 放锁
		klog.Errorf("Failed to release node lock for node %s and lock %s: %v", nodeName, lockName, err)
	}
}

var podAllocationFailed = func(nodeName string, pod *corev1.Pod, lockName string) {
	klog.Infof("Pod allocation failed for pod %s/%s on node %s", pod.Namespace, pod.Name, nodeName)
	updatePodAnnotationsAndReleaseLock(nodeName, pod, lockName, util.DeviceBindFailed)
}

func PodAllocationFailed(nodeName string, pod *corev1.Pod, lockName string) {
	podAllocationFailed(nodeName, pod, lockName)
}
var podAllocationFailed = func(...) 这个写法是为了测试

它被声明成包级变量而不是普通函数， 这样测试里可以直接替换掉它（podAllocationFailed = func(...) { called = true }）， 验证「某个错误分支有没有正确释放锁」。
这是 Go 里做轻量级依赖注入的常用手法， 比引入 mock 框架简单得多。getPendingPod = util.GetPendingPod （）也是同样的套路。

找找看：哪条错误路径漏了放锁？

Allocate() 里几乎每个 return err 前面都跟着 PodAllocationFailed(...)。但第一个不是： 

	current, err := getPendingPod(ctx, nodename)
	if err != nil {
		//nodelock.ReleaseNodeLock(nodename, NodeLockNvidia, current)   ← 被注释掉了
		return &kubeletdevicepluginv1beta1.AllocateResponse{}, err
	}

逻辑上说得通：连是哪个 Pod 都不知道，没法定向放锁。 结果是这条路径只能等 5 分钟锁超时。
被注释掉的代码 + 没有解释的注释，通常意味着「这里有个已知问题但没想好怎么修」。 这是找贡献机会的经典信号 —— 但动手前先去 issue 里搜一下，可能已经有人讨论过。

8. 本章自测

设备插件的 Allocate() 怎么知道这次请求是给哪个 Pod 的？
Akubelet 在 AllocateRequest 里传了 Pod UID
B从设备 ID 反查
C去 apiserver List 本节点的 Pod，找 bind-phase=allocating 且 vgpu-node 等于本节点的那个
D通过 CRI socket 问容器运行时
K8s Device Plugin API 的 AllocateRequest 里 只有设备 ID 列表，没有任何 Pod 信息（这是 API 设计的历史遗留）。 HAMi 只能靠注解组合去「猜」。
这是整个协议最脆弱的地方：如果两个 Pod 同时满足条件， 会选到 List 返回的第一个，而顺序不保证 → 配置串台。
节点锁的全部意义就是保证「同一时刻只有一个 Pod 处于 allocating」。
为什么 Allocate() 处理完一个容器后要把注解里对应那段擦掉？
A为了节省 etcd 空间
B容器崩溃重启时 kubelet 会再次调 Allocate，不擦除会导致同一份显存被重复分配
C为了触发调度器的 informer 事件
D为了让 vGPUmonitor 知道分配完成了
擦的是 hami.io/vgpu-devices-to-allocate（「工单」）， 而 hami.io/vgpu-devices-allocated（「留档」）保持不变， 所以调度器的账本不受影响。
这就是第 01 章讲的「两条注解各司其职」的价值： 一条是待办事项（消费即销毁），一条是事实记录（永久保留）。
一个 Pod 有 1 个 InitContainer（用 GPU）、2 个普通容器（第 1 个用 GPU，第 2 个不用）。注解是 {init};{ctr0};;。popNextContainerDevices 第二次被调用时，i=1，它返回哪个容器？
Apod.Spec.Containers[0]，因为 i - initContainerCount = 1 - 1 = 0
Bpod.Spec.Containers[1]
Cpod.Spec.InitContainers[1]
D报错，索引越界
i=1，initContainerCount=1， 所以 i < initContainerCount 不成立 → 走普通容器分支， regularIdx = 1 - 1 = 0 → pod.Spec.Containers[0]。
这个索引换算依赖「注解里每个容器都占一个位置，包括不用 GPU 的」。 如果编码时跳过空容器，这里就会全部错位 —— 这就是第 01 章强调「空容器也要占位」的原因。
容器里的应用调用 cudaMalloc(4GB)，而 CUDA_DEVICE_MEMORY_LIMIT_0=3000m。谁来拦住它？
Akubelet
B调度器
CNVIDIA 驱动
D容器里通过 ld.so.preload 加载的 libvgpu.so（HAMi-core）
设备插件只负责把限额告诉容器（环境变量）和 把执行者塞进容器（libvgpu.so + ld.so.preload）。 真正的拦截发生在容器内的用户态： libvgpu.so 抢先导出了 cuMemAlloc 等符号， 应用调它时先经过额度检查，超了就返回 CUDA_ERROR_OUT_OF_MEMORY。
A、B、C 都不参与运行时限制 —— 下一章详细拆这个机制。

9. 小结

  • 设备插件有三个身份：对 kubelet 是标准 DP、对调度器是清单上报器、对容器是环境注入器。
  • 「一张卡变十张」是给 kubelet 看的善意谎言，真正的限制在容器里执行。
  • 清单上报有内容去重（deviceCache）和限频事件两个优化。
  • Allocate() 不知道请求属于哪个 Pod，靠 bind-phase=allocating 猜 —— 这是全协议最脆弱的一环，靠节点锁保证唯一性。
  • 消费即擦除 to-allocate，防止容器重启时重复分配；allocated 保留做账本。
  • 容器序号换算依赖空容器也占位的编码约定。
  • 节点锁在 PodAllocationSuccess/Failed 里释放，闭环到第 06 章。
